# 구현과 독립 테스트 리뷰

사용자가 `$implement-with-test-review` 또는 이 다중 에이전트 작업 방식을 명시적으로
요청한 경우에만 실행한다. 일반 코드 수정은 단일 에이전트가 처리한다. 필요하면 이
스킬의 사용을 제안할 수 있지만, 사용자 동의 전에 작업 에이전트를 호출하지 않는다.

상위 조정자가 [개발 작업 명세](../../../docs/spec/three-agent-implementation-workflow.md)를
읽고 실행한다. 기존 GDD 생성 단계·에이전트 구성·재시도 예산은 변경하지 않는다.
별도 스케줄러나 관리 시스템을 만들지 않는다.

이미 구현·테스트 작성·리뷰 역할을 배정받았다면 자기 역할만 수행한다. 이 스킬이나
AGENTS.md를 다시 적용해 하위 팀을 생성하지 않는다. 문서 전용 변경은 기존 문서 검사를
따른다. 테스트 전용 과제는 구현 담당 없이 작성·리뷰 두 역할을 분리한다.

## 시작 계약과 소유권

조정자는 기존 변경을 확인하고 다음 공통 입력을 작업자에게 전달한다.

- 사용자 목표·제약, 관련 spec·ADR의 정확한 경로, 범위 밖 항목
- 관찰 가능한 기대 동작과 허용·거부 사례, 미결정 요구
- 기준 revision, 보존할 dirty 변경, 작업 디렉터리
- 공개 함수·CLI·파일 형식 등 호출 계약과 기존 테스트 명령
- 역할별 쓰기 가능 파일, 공유 설정 담당자, 필수 검증

기존 인터페이스를 우선한다. 새 인터페이스는 조정자가 최소 공개 계약을 정해 구현·테스트
작성 양쪽에 동시에 전달한다. 내부 알고리즘을 테스트가 강제하도록 정하거나 추측한 기대값·
구현자의 설계 결론을 요구사항에 섞지 않는다.

각 역할은 `collaboration.spawn_agent`의 `fork_turns="none"`으로 별도 시작한다.
공통 입력·역할 지시·필요한 경로를 초기 메시지에 직접 담는다. 같은 에이전트의 이름만
바꾸어 역할을 겸임시키지 않는다. 서로 다른 모델은 필수 조건이 아니다.

| 역할 | 쓰기 소유권 | 인계 내용 |
| --- | --- | --- |
| 구현 담당 | 제품 코드·배정된 설정·필요한 구현 문서 | 변경 파일, 구현 동작, 한계, 고정 여부 |
| 테스트 작성 담당 | 테스트·테스트 전용 fixture와 helper | 요구 근거·기대값, 대상 버전, 실행 결과·한계 |
| 테스트 리뷰 담당 | 읽기 전용 | 대상 버전, 지적·근거, 처리 확인, 승인 여부 |
| 조정자 | 시작 시 배정한 통합·진행 기록 | 소유권, 인계·실행 버전, 최종 판정 |

조정자는 대체 구현자나 테스트 작성자가 아니다. 결함은 해당 담당자에게 돌려보낸다.
리뷰 담당은 파일을 직접 고치거나 자신의 변경을 승인하지 않는다. 공용 설정·혼합 파일은
한 사람에게 배정하고 다른 역할은 변경을 요청한다. 분리가 어려운 편집만 직렬화하거나
별도 checkout을 사용한다. 기존 dirty 변경을 덮어쓰지 않는다.

## 병렬 시작과 직렬 인계

1. 구현 담당과 테스트 작성 담당을 병렬 시작한다. 리뷰 담당도 별도로 시작할 수 있으나
   테스트 인계 전에는 대기시킨다. 조정자 포함 최대 네 에이전트이며 배정 역할은 새 팀을 만들지 않는다.
2. 작성 담당은 요구사항과 기준 코드로 사례·기대값을 먼저 도출한다. 새 구현의 상수·출력을
   복사하지 않는다. 이후 실행·진단용으로 구현을 읽어도 달라진 결과를 곧바로 정답으로 삼지 않는다.
3. 작성 담당이 파일 목록과 diff·revision 또는 파일 해시로 리뷰 버전을 식별하고 쓰기를
   멈춘다. 조정자는 그 버전·요구사항·필요한 기준 코드·공개 계약을 리뷰 담당에게 전달한다.
   첫 검토 전에 구현자의 완료 주장이나 작성자의 자기 승인을 정답으로 전달하지 않는다.
4. 구현 미완료여도 테스트 리뷰를 시작한다. 미구현 실패·테스트 실행 오류·미실행 항목을
   구분한다. 병렬 수정이 실행에 영향을 주면 고정 사본을 쓰거나 구현 담당을 잠시 멈춘다.
   공유 파일 시스템을 기술적으로 완전한 격리라고 표현하지 않는다.
5. 리뷰 결과를 받은 뒤에만 작성 담당이 수정한다. 지적별 수정 내용 또는 미반영 이유와
   근거를 회신하고 새 버전을 고정해 재인계한다. 리뷰와 해당 테스트 수정은 동시 실행하지 않는다.
6. 리뷰 담당은 실제 변경과 영향 범위를 재검토한다. 반영 보고만으로 승인하지 않는다.
   근거 있는 이견은 요구사항과 대조하고 해결되지 않으면 조정자에게 올린다.
7. 구현 완료와 테스트 승인이 모두 준비되면 쓰기를 고정한다. 조정자는 승인 버전과 통합본을
   대조한 뒤 과제에 맞는 테스트·필수 검사를 실행한다. 서로 다른 시점의 결과를 합쳐 보고하지 않는다.
8. 구현 결함은 구현 담당이 수정하며 테스트 기대값을 유지한다. 테스트 결함은 작성→리뷰로
   되돌린다. 리뷰 담당이 최종 통합본의 테스트 차이와 실행 근거를 확인한 뒤 조정자가 완료를 판정한다.

승인은 인계된 테스트 버전에만 유효하다. 테스트·fixture·assertion·mock·스냅샷·실행 설정이
달라지면 영향 부분을 재검토한다. 요구사항·공개 계약 변경은 양쪽에 동시에 전달하고
기존 승인 적용 여부를 다시 판단한다.

## 테스트와 리뷰 판정

작성 담당은 주요 사례의 요구 근거·입력·기대 동작·실패 영향을 설명한다. 공통 근거는
묶어도 된다. 정상·오류·경계·오탐·회귀·공개 경계의 통합을 과제에 맞게 다루고 mock이
가리는 범위를 밝힌다. 버그 수정은 변경 전 실패·변경 후 통과를, 리팩터링은 관찰 동작
보존을 확인한다. 실패 종료만 확인한다면 무관한 오류로도 통과하는지 검토한다.

리뷰 담당은 요구사항과 실제 assertion을 대조한다.

- 기대값이 구현자의 가정이나 출력 복사가 아닌 요구사항에서 도출됐는가?
- 테스트 이름과 실제 검증 범위가 일치하며 결함이 남아도 통과할 여지가 없는가?
- 짧지만 완결된 설명·부정문·선택적 값 등 정상 입력을 부당하게 거부하지 않는가?
- 숫자·길이·금지어 임계값에 명시된 정책 근거가 있는가?
- 의도한 진단·부수 효과·실제 경계를 확인하며 fixture·mock이 결함을 가리지 않는가?
- 검토·실행 버전, 재현성, 기존 변경 보존이 확인되는가?

길이만으로 깊이·재미·가독성을 판정하지 않는다. 대리 지표의 한계와 경고·필수 계약을
구분하고 근거 없는 임계값을 필수 조건으로 승격하지 않는다. 구조 계약 검사와 자동
확인할 수 없는 의미 품질은 분리하고 후자는 별도 수용 검토로 남긴다. 합성 fixture는
로컬 아티팩트 없이 재현 가능해야 하며 개인정보·영구 문서 경계는 저장소 지침을 따른다.

리뷰 지적은 대상·문제·요구 근거·영향·필요한 수정 또는 확인을 포함한다. 판정은 `승인`,
`수정 필요`, `요구사항 확인 필요`로 구분하고 미실행 항목·한계를 기록한다.
필수 검증이 불가능하면 단순 승인으로 완료하지 않는다.

## 중단·진행 보고와 완료

실패는 구현 결함·테스트 결함·요구 모호성·환경 문제로 분류한다. 명확한 요구는 조정자가
담당자에게 돌려보내고 새 제품 정책이나 모호한 요구만 사용자에게 확인한다.
assertion 삭제·무근거 skip·스냅샷 일괄 갱신으로 통과시키지 않는다.

담당자가 중단되면 같은 역할에 후속 작업을 배정하고 입력·소유권·인계 버전을 보존한다.
도구나 동시 실행 한도로 필요한 역할을 유지할 수 없으면 한계와 미완료 범위를 보고한다.
조용히 조정자의 단독 구현으로 전환하거나 리뷰 담당을 작성자로 바꾸지 않는다.
같은 이견이 진전 없이 반복되거나 환경 문제를 해결할 수 없으면 근거·남은 일을 보고하고
해당 경로를 중단한다. 회차를 채웠다고 승인하거나 무제한 반복하지 않는다.

진행 기록에는 역할별 주체, 파일 소유권, 인계 버전, 리뷰 판정·반영 여부, 실행 명령·결과,
남은 문제를 남긴다. 현재 로컬 기록을 GDD manifest나 영구 근거로 취급하지 않는다.
완료 보고는 핵심 변경, 독립 리뷰·수정 결과, 최종 통합본 검증, 미검증 범위·한계를
요약한다. 필수 검사와 최종본 승인이 모두 있어야 완료이며 에이전트 수·테스트 수만으로
품질을 보장하지 않는다. 이 절차는 커밋·배포 권한을 추가하지 않는다.
