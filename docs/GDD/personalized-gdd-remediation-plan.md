# 개인화 GDD 직역 문제 개선 계획

## 목표와 성공 기준

이 계획의 목표는 현실 직무 소재를 금지하는 것이 아니라, 현실 해석의 표면 명사를 장르 소재로 직역하지 않는 생성 파이프라인을 만드는 것이다.

성공 기준은 다음과 같다.

1. 통합 해석은 차트 근거와 삶의 해석을 충실하게 보존한다.
2. 통합 해석이 특정 직업·도구·행정 소재를 최종 게임 디자인처럼 선점하지 않는다.
3. GDD는 해석의 동기·갈등·행동 패턴을 사용하되 현실 직무를 능력으로 직역하지 않는다.
4. 주인공의 힘에는 기원, 초기 한계, 숙련 과정, 확장 계기, 비용, 적의 대응 수단이 존재한다.
5. 성장 억제가 아니라 납득 가능한 성장 곡선이 제시된다.
6. 차트의 한 영역이 세계관·전투·경제·서사 전체를 독점하지 않는다.
7. 기존 ID 추적성과 산출물 분리 검증은 계속 통과한다.
8. `docs/legacy/`는 읽거나 수정하지 않는다.

## 1단계 — 현재 상태와 실패 사례 고정

목적: 수정 전 문제를 재현 가능한 기준점으로 남긴다.

작업:

- 현재 작업 트리의 관련 변경을 확인하되 덮어쓰지 않는다.
- 커밋된 합성 사례를 실패 기준으로 사용한다. 원래 로컬 GDD와 개인 출생 입력은 필수 재현 자료로 사용하지 않는다.
- 문제를 다음 세 유형으로 분류한다.
  - 표면 직역: `심사 → 심사관`, `문서 → 헌장 마법`
  - 주제 과점: 행정 은유가 전투·경제·세계·성장을 모두 장악
  - 성장 대체: 강함의 설계 대신 책임과 절차를 성장으로 제시
- [합성 직역 평가 사례](../../scripts/fixtures/gdd-translation-cases.json)의 실패·허용 쌍과 아래 평가표로 회귀 기준을 고정한다. 이는 원본 전체 재현이 아니다.
- 기존 미커밋 변경은 사용자 작업으로 간주하고 관련 파일별 diff를 기준점으로 보존한다.

검증:

- 문서만 읽어도 무엇이 실패인지 일관되게 판정할 수 있어야 한다.
- `문서`, `계약`, `관리`라는 단어가 등장했다는 이유만으로 실패 처리하지 않는다.
- 실제 실패 기준은 해석 명사의 직접 치환과 소재 과점으로 한정한다.

## 2단계 — 통합 해석과 게임 설계의 경계 복원

목적: 게임 소재가 통합 해석 단계에서 너무 일찍 확정되는 것을 막는다.

대상 파일:

- `docs/prompts/interpretation-guidelines.md`
- `.agents/skills/interpret-chart-report/SKILL.md`
- `.agents/skills/interpret-chart-report/references/interpretation-format.md`
- 관련 validator 및 테스트

### 2.1 `창작 시드`의 역할 재정의

현재처럼 구체적인 직무 소재를 생산하지 않도록 제한한다.

```text
나쁜 시드:
공동 금고의 누수를 추적하는 심사자

좋은 시드:
신뢰하던 공동 기반에서 숨은 대가를 발견하고,
동맹 유지와 독립 사이에서 선택하는 갈등
```

허용 범주:

- 핵심 동기
- 반복 갈등
- 관계 구조
- 행동 패턴
- 환경 압력
- 성장 방향
- 반전 구조

금지 범주:

- 주인공의 확정 직업
- 확정 무기나 마법
- 특정 게임 규칙
- 확정 세력·지역·던전
- 현실 업무 도구를 변형한 판타지 소품

### 2.2 해석 완전성과 창작 강제를 분리

- 전문 해석 ID 보존은 유지한다.
- 모든 전문 ID를 통합 문서에서 근거로 사용하는 조건도 필요하면 유지한다.
- 모든 해석 항목이 게임 소재를 만들어야 한다는 조건은 제거한다.
- `창작 시드`를 선택 항목으로 낮추거나 추상적 `서사적 잠재력` 필드로 변경한다.
- 직업·재물·건강 해석은 삶의 해석으로 보존하되 곧바로 게임 시스템으로 연결하지 않는다.

### 2.3 통합 문서의 책임 명문화

통합 단계는 다음까지만 책임진다.

```text
차트 근거
→ 성향과 동기
→ 행동 패턴
→ 갈등과 조건
→ 가능한 성장 방향
```

다음 변환은 하지 않는다.

```text
→ 주인공 직업
→ 능력 외형
→ 전투 시스템
→ 세계관 법칙
```

검증:

- 기존 통합 해석 테스트가 통과해야 한다.
- `창작 시드` 필수 여부를 변경한다면 validator 테스트를 먼저 수정한다.
- 추상적 관계 갈등은 허용하고, 확정 게임 소재는 통합 단계에서 거부한다.
- 직업 적성 해석은 허용하되 그것을 확정 주인공으로 만드는 문장은 허용하지 않는다.
- 의미 기반 금지를 TypeScript 정규식으로 과도하게 검사하지 않는다.

## 3단계 — GDD 변환 규칙을 직역에서 재창작으로 교체

목적: 해석과 게임 표현 사이에 한 단계의 추상화를 강제한다.

대상 파일:

- `.agents/skills/generate-gdd-from-interpretation/SKILL.md`
- `.agents/skills/generate-gdd-from-interpretation/references/design-prompt.md`
- `.agents/skills/generate-gdd-from-interpretation/references/light-mode.md`
- `.agents/skills/generate-gdd-from-interpretation/references/deep-mode.md`

### 3.1 변환 절차 교체

1. 선택한 해석 항목에서 표면 명사를 제거한다.
2. 그 아래의 동기·갈등·선택 패턴을 추출한다.
3. 독립적인 Action RPG 플레이어 판타지를 선택한다.
4. 추출한 패턴으로 그 판타지를 개인화한다.
5. 세계관 안에서 힘의 기원과 한계를 연결한다.
6. 해석 ID는 행동·갈등의 근거로만 인용한다.

### 3.2 직접 치환 금지 규칙 추가

다음 취지의 규칙을 명시한다.

> 현실 직업, 업무 절차, 문서, 계약, 회계, 품질관리, 조직 운영 도구를 주인공 직업·마법·무기·세계 법칙으로 직접 치환하지 않는다. 해당 표현 아래의 동기와 행동 패턴을 추출하여 장르 고유 소재로 재창작한다.

예외:

- 행정이나 계약이 세계관의 일부로 등장하는 것은 허용한다.
- 주인공의 핵심 능력과 주요 시스템 전체를 지배하면 실패로 본다.
- 해당 소재를 선택하려면 다른 판타지보다 적합한 독립적인 장르상 이유가 있어야 한다.

### 3.3 플레이어 판타지 우선 규칙 추가

GDD 설계 순서를 다음처럼 정의한다.

```text
플레이어 판타지
→ 핵심 행동 동사
→ 전투 정체성
→ 능력의 세계관적 기원
→ 성장 곡선
→ 해석 기반 개인화
→ 관계·세계·결말 확장
```

필수 질문:

- 플레이어는 매 순간 무엇을 하는가?
- 이 행동은 Action RPG로서 촉각적이고 시각적인가?
- 차트 해석을 제거해도 기본 판타지가 매력적인가?
- 다시 해석을 적용했을 때 다른 주인공과 구별되는가?

### 3.4 표면 다양성보다 구조 다양성 요구

단순히 검사 마법을 검사 검술로 바꾸는 수준을 피한다.

```text
결함 탐지와 검증 성향
→ 적의 자세와 리듬을 읽는 검객
→ 불완전한 소환수를 안정시키는 조율사
→ 위험한 변신을 단계적으로 통제하는 사냥꾼
→ 동료의 서로 다른 힘을 전장에서 연결하는 지휘형 전사
```

검증:

- 디자인 프롬프트에 현실 직무 직역 금지와 예외가 모두 존재해야 한다.
- `light`와 `deep`이 같은 핵심 경계를 공유해야 한다.
- `deep`은 문서 길이가 아니라 관계·성장·세계 반응의 깊이 증가로 정의한다.

## 4단계 — 납득 가능한 파워 성장 계약 추가

목적: 강해지지 않는 주인공을 만드는 대신 성장의 인과관계를 설계한다.

각 핵심 능력에서 결정할 항목:

1. 힘의 기원
2. 최초 발현 계기
3. 초기 가능 범위
4. 초기 불가능 범위
5. 플레이를 통한 숙련 방식
6. 중간 확장 계기
7. 후반 능력 규모
8. 사용 비용 또는 위험
9. 적과 세계의 대응 수단
10. 최종 능력이 초기 능력에서 이어지는 방식

좋은 성장 예:

```text
초기: 한 종류의 적 행동만 감지
중기: 감지한 패턴에 맞춰 무기 형태를 전환
후기: 여러 적의 패턴을 연결해 전장 흐름을 바꿈
최종: 축적한 숙련으로 지역 규모의 위협에 개입
```

피해야 할 성장:

```text
초기: 문서를 검토함
후기: 더 많은 책임을 짐
최종: 권한을 위임함
```

전투 숙련 성장과 인물·관계 성장을 별도 축으로 설계한다.

검증:

- 두 성장축이 각각 존재해야 한다.
- 후반 능력은 강해도 되지만 중간 단계 없이 도약해서는 안 된다.
- 비용은 힘을 무효화하는 처벌이 아니라 플레이 선택을 만드는 요소여야 한다.
- 모든 강한 기술이 피로·관계 악화·도덕적 손실로만 귀결되지 않아야 한다.

## 5단계 — 주제 과점 방지 규칙 추가

목적: 하나의 해석 영역이 모든 시스템의 외형을 지배하지 않게 한다.

평가 영역:

- 주인공 정체성
- 핵심 능력
- 전투
- 성장
- 세계관
- 경제
- 동료 관계
- 퀘스트 해결
- 결말

규칙:

- 하나의 현실 영역에서 나온 표면 은유가 위 항목 대부분을 장악하면 재설계한다.
- 동일한 해석 항목을 여러 시스템에 사용할 수는 있지만 서로 다른 표현으로 변환한다.
- 직업 적성은 전투 정체성을 보조할 수 있지만 세계 전체의 존재론을 자동 결정하지 않는다.
- 재물 해석은 경제 갈등에 사용할 수 있지만 모든 보스와 마법을 회계 구조로 만들지 않는다.
- 관계 해석은 동료 시스템에 사용할 수 있지만 전투 비용 전체를 호감도나 신뢰로 환원하지 않는다.

내부 재검토 신호:

```text
핵심 게임 요소 8개 중 같은 표면 은유가 4개 이상을 지배하는가?
```

이 수치는 기계적인 실패 조건으로 사용하지 않는다.

## 6단계 — 검증 책임 재설계

### 6.1 결정론적 validator의 책임

현재 검사를 유지한다.

- 파일 비어 있음
- 원본 보고서 통째 복사
- 모티프 존재
- 해석 ID 유효성

필요한 경우에만 다음 형식 조건을 추가한다.

- 플레이어 판타지 존재
- 핵심 전투 행동 존재
- 전투 성장과 인물 성장의 구분 존재
- 능력의 기원·한계·확장·비용 존재

고정 제목을 강요하게 된다면 validator에 넣지 않고 스킬 계약으로만 유지한다.

### 6.2 validator가 맡지 않을 것

- 재미
- 판타지 매력
- 사무직 직역 여부
- 성장의 정서적 설득력
- 세계관 독창성

### 6.3 생성 단계의 의미 검토표

GDD 저장 전에 생성 에이전트가 다음을 점검한다.

- 현실 직무 명사를 핵심 능력으로 직역했는가?
- 차트 해석의 명사보다 행동 패턴을 사용했는가?
- 해석을 제거해도 Action RPG로서 매력적인가?
- 능력의 기원과 한계가 세계 안에서 설명되는가?
- 후반 강함이 초기 능력의 확장으로 보이는가?
- 인물 성장과 전투력 성장을 혼동했는가?
- 하나의 은유가 게임 전체를 독점하는가?
- 플레이어가 실제로 수행할 전투 행동이 구체적인가?

검토 결과 자체는 GDD에 출력하지 않는다.

## 7단계 — 테스트 우선 수정

순서:

1. 현재 validator 테스트를 실행한다.
2. 변경할 계약을 테스트로 먼저 표현한다.
3. 테스트 실패를 확인한다.
4. validator 또는 포맷 계약을 최소 수정한다.
5. 테스트 통과를 확인한다.
6. 전체 관련 테스트를 다시 실행한다.

대상 테스트:

- `.agents/skills/interpret-chart-report/scripts/validate-interpretation.test.ts`
- `.agents/skills/generate-gdd-from-interpretation/scripts/validate-gdd.test.ts`
- `.agents/skills/generate-personalized-gdd/scripts/validate-gdd.test.ts`
- 전문 해석 validator 테스트

추가 사례:

- 추상적 시드가 있는 정상 통합 해석
- 창작 시드가 없는 항목의 허용 여부
- 유효하지 않은 전문 ID 또는 누락
- 잘못된 GDD 근거 ID
- 전투 성장과 인물 성장 계약을 구조적으로 표시할 경우 해당 필드 누락
- 원본 차트 또는 통합 문서의 과도한 복사

성공 기준:

- 기존 근거 추적성이 약화되지 않는다.
- 모든 문서에 획일적인 고정 목차를 강요하지 않는다.
- 의미 판단을 정규식으로 가장하지 않는다.

## 8단계 — 합성 해석 기반 회귀 평가

절차:

1. 기존 로컬 산출물은 수정하거나 필수 입력으로 읽지 않는다.
2. 합성 사례의 해석·실패안·허용안과 아래 품질 평가표를 사용한다.
3. 구조 검증은 기존 GDD validator의 합성 테스트로 수행한다.
4. 실제 모델의 설계 품질 검증이 필요하면 합성 통합 해석으로 별도 새 생성을 실행한다.
5. 새 결과는 원본 GDD 대신 평가표와 합성 실패·허용 사례를 기준으로 평가한다.
6. 상세 실험 결과는 로컬 run에 보존하고 영구 문서에는 판정 기준·비식별 요약·한계만 남긴다.

평가표:

| 평가 항목 | 0점 | 1점 | 2점 |
|---|---|---|---|
| 표면 직역 | 직무가 곧 능력 | 일부 잔존 | 행동 패턴만 변환 |
| 플레이어 판타지 | 업무 수행처럼 보임 | 혼합됨 | 독립적으로 매력적 |
| 전투 행동 | 추상적 절차 | 일부 액션화 | 명확한 액션 동사 |
| 힘의 인과 | 갑작스럽거나 은유적 | 일부 설명 | 기원부터 최종 성장까지 연결 |
| 성장 곡선 | 성장 억제·대체 | 부분적 확장 | 전투와 인물 성장 모두 존재 |
| 주제 균형 | 한 은유가 전체 지배 | 일부 과점 | 영역별 표현이 분화 |
| 개인화 | 직업 적성 복제 | 일부 성향 반영 | 동기·갈등·선택으로 개인화 |
| 근거 추적 | 부정확 | 형식상 유효 | 설계 선택과 실질적으로 연결 |

통과 조건:

- `표면 직역` 2점 필수
- `플레이어 판타지`와 `힘의 인과` 각각 2점 필수
- 전체 16점 중 최소 13점
- 어느 항목도 0점이면 재검토
- 기존 validator 전부 통과

## 9단계 — 편향 회귀용 추가 사례

최소 세 유형을 추가로 확인한다.

1. 직업·관리 언어가 강한 해석
2. 관계·감정 언어가 강한 해석
3. 재물·위험 언어가 강한 해석

확인할 실패:

- 관리형 → 행정 마법
- 관계형 → 호감도 마법
- 재물형 → 회계 전투
- 건강형 → 피로 페널티 게임

처음에는 실제 전체 차트를 반복 계산하기보다 작은 합성 `chart-interpretation` fixture로 GDD 단계만 시험한다. 전체 파이프라인의 별도 생성 실험은 새로운 합성 입력으로 수행하고 과거 개인 입력의 보존을 전제하지 않는다.

## 10단계 — 별도 디자인 비평 단계 도입 여부 판단

처음부터 새 에이전트를 추가하지 않는다. 다음 조건 중 하나가 반복될 때만 도입한다.

- 프롬프트 수정 후에도 표면 직역이 두 번 이상 발생
- 서로 다른 입력에서 같은 세계관 은유가 반복
- validator는 통과하지만 평가표가 연속 두 번 실패
- 생성 에이전트의 자체 점검이 결과에 반영되지 않음

도입한다면 비평 단계는 GDD를 직접 고치지 않고 다음만 반환한다.

- 실패 유형
- 문제 구절 위치
- 위반한 품질 기준
- 유지해야 할 강점
- 재생성 필요 여부

그 후 원래 GDD 단계가 한 번만 수정하도록 제한한다.

## 실제 구현 순서

1. 관련 작업 트리와 테스트 상태 확인
   검증: 기존 테스트 결과와 관련 diff 확보
2. 품질 기준 문서 확정
   검증: 실패·허용 예시와 점수표 완성
3. 통합 해석 계약 테스트 수정
   검증: 의도한 새 사례가 먼저 실패
4. 통합 해석 지침·포맷 최소 수정
   검증: 테스트 통과, 근거 보존 유지
5. GDD 디자인 프롬프트 수정
   검증: 추상화, 플레이어 판타지, 성장 계약 명시
6. 필요한 경우에만 GDD validator 수정
   검증: 기존 및 신규 테스트 통과
7. 관련 전체 테스트 실행
   검증: 모든 validator 테스트 통과
8. 커밋된 합성 자료로 GDD validator 회귀 실행
   검증: 이전 로컬 결과 없이 관련 테스트 통과
9. 필요한 별도 생성 실험의 결과를 합성 사례·품질 평가표로 평가
   검증: 필수 항목 2점, 총점 13점 이상
10. 추가 합성 사례로 편향 검사
    검증: 행정·관계·재물 어휘의 직접 마법화가 반복되지 않음
11. 결과에 따라 비평 단계 필요 여부 결정
    검증: 추가 복잡성이 실제 반복 실패로 정당화되는지 확인

## 변경 범위 원칙

이번 수정에서 건드리지 않을 것:

- 차트 계산 로직
- 전문 체계의 점성·명리 해석 규칙
- 버전 할당 방식
- 이전 아티팩트
- `docs/legacy/`
- 관련 없는 문서와 포맷
- 기존 사용자의 미커밋 변경 중 이번 문제와 무관한 부분

핵심 변경 범위는 통합 해석의 창작 경계, GDD 변환 규칙, 관련 계약 테스트로 한정한다.
