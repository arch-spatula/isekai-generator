# 개인화 게임의 공통 화면·아트 계약

> 상태: 구현 완료 — 선언·입력 검증과 의미 검토 지침 연결, 실제 모델 생성 평가는 별도
> 작성일: 2026-11-06
> 목적: 확정된 인게임 스타일을 전투·세계 선택과 GDD 생성·검증에 일관되게 전달한다.

## 1. 문제와 원인

조사 당시 [원본 컨셉 프롬프트](../prompts/personalized-action-rpg-concept.md)는 이세계 판타지,
인디 규모, 2D, RPG, 픽셀아트를 확정 전제로 지정했다. 그러나 실제 GDD 생성 스킬은
별도의 `references/design-prompt.md`를 읽었고 이 문서에는 화면·아트 제약이 없었다.
전투·세계 선택 단계와 GDD validator에도 이 제약을 전달·확인하는 계약이 없었다.
격리된 에이전트는 대화 이력으로 빠진 조건을 보충할 수 없었다. 현재는 아래 공통 입력과
검증으로 연결했고 원본 프롬프트도 공통 문서를 참조한다.

조사 당시 로컬 GDD들에서 다음 최소 사례를 관찰했다.

- 장르 문장에 `3D 이세계 액션 RPG`를 명시했다.
- 카메라를 `보행교 아래층이 보이는 어깨 너머 시점`으로 설계했다.
- 여러 결과가 `3인칭 액션 RPG`를 선택했으며 2D와 픽셀아트를 명시하지 않았다.

이는 과거 관찰이며 원본은 커밋된 회귀 자료가 아니다. 원본 없이 전체 집계나 생성 경위를
독립적으로 재검증할 수 있다고 주장하지 않는다. 아래 테스트는 별도의 합성 자료로 작성한다.
`3인칭`이라는 단어만으로 3D를 확정하거나, 수직 지형이라는 이유로 2D 위반으로 판단하지 않는다.

## 2. 목표와 범위

개인화는 공통 제작 조건 안에서 이루어진다. 캐릭터, 능력, 적, 세계의 연결 구조와 서사는
달라질 수 있지만 각 생성이 화면 차원과 기본 아트 매체를 다시 선택하지 않는다.

이번 구현 범위는 공통 계약 문서, 생성 스킬·reference, 브리프와 GDD의 출력 계약,
validator, 합성 회귀 테스트, 파이프라인 문서다. 차트 계산·해석 단계에는 게임 스타일을
주입하지 않는다. 런타임 구현이나 실제 스프라이트 제작은 별도 작업이다.

기존 로컬 아티팩트와 레지스트리는 수정하지 않는다. 이번 spec 작성과 후속 구현만으로
새 생성 실행, 활성 series 변경, 기존 결과의 소급 실패 처리를 수행하지 않는다.

## 3. 고정 조건과 개인화 범위

### 3.1 세피리아를 기준으로 삼는 범위

사용자가 제시한 세피리아를 화면·아트·액션 감각의 기준으로 채택한다. 조사일은
2026-11-06이며 다음 개발사 자료를 사용했다.

- [TEAM HORAY 공식 소개](https://teamhoray.com/games/sephiria): 무기별 전투 차이,
  아이템 수집과 배치에 의한 강화, 적과 보스, 협동 플레이를 소개한다.
- [개발사 itch.io 소개](https://team-horay.itch.io/sephiria): 탑다운 픽셀 액션,
  빠르고 직관적인 조작, 공격·방어, 귀여운 픽셀 그래픽, 아이템 간 인접 강화와
  등장인물과의 교류를 명시한다. 데모 소개이므로 최신 수치나 지원 범위의 근거로 삼지 않는다.

아래는 위 특징을 이 프로젝트의 제작 조건으로 번역한 설계 결정이다. 원작의 엔진 내부,
정확한 판정·프레임·해상도·카메라 수치를 확인한 결과로 해석하지 않는다.

| 참고 특징 | 이 프로젝트에 적용할 방향 | 개인화 범위 |
| --- | --- | --- |
| 탑다운 픽셀 액션 | 위에서 비스듬히 내려다보는 2D 탑다운, 바닥 평면에서 이동·조준 | 구역 구조, 장애물, 공격 방향과 범위 |
| 귀여운 픽셀 그래픽 | 작고 단순화된 인물 비례, 뚜렷한 실루엣, 통일된 픽셀 밀도 | 종족, 의상, 팔레트, 지역 분위기 |
| 빠르고 직관적인 전투 | 이동·주 공격·방어 대응을 중심으로 짧고 명료한 행동과 즉각적인 피드백 | 회피·막기·받아치기 등 대응 방식, 고유 동사와 리듬 |
| 개성 있는 무기와 강화 | 선택된 전투 원형 안에서 공격 범위·연계·위치 선택이 달라지는 성장 | 무기 외에 신체·주문·소환 등 기존 powerMedium 유지 |
| 아이템 조합에 의한 빌드 | 획득과 조합이 실제 전투 선택을 바꾸고 효과를 화면에서 식별 가능하게 설계 | 투사체, 범위, 조건부 발동, 자원 운용 등의 조합 |
| 탐험 중 등장인물과 교류 | 액션 구간 사이에 대화·거래·귀환의 호흡 배치 | 관계, 문화, 생활 거점과 이야기 |

캐릭터·전장·위험 표시는 효과가 겹쳐도 구별돼야 한다. 공격의 준비·유효 범위·피격 결과를
짧은 동작, 형태, 색 대비와 소리로 전달한다. 작은 캐릭터가 배경이나 효과에 묻히지 않게
하고, 보스의 크기가 커져도 플레이어와 안전한 이동 공간이 화면에서 읽히게 한다.
이 가독성 규칙은 참고작의 내부 구현에 대한 주장이 아니라 본 프로젝트의 수용 기준이다.

탑 하강, 토끼 주인공, 고정 무기 목록, 석판 인접 배치, 사망 후 초기화, 랜덤 방 생성,
온라인 협동은 공통 필수 조건으로 채택하지 않는다. 특히 로그라이트 진행 채택은 별도
결정이며, 개인화된 액션 RPG의 서사·성장·세계 구조를 참고작과 동일하게 고정하지 않는다.

### 3.2 공통 조건

| 항목 | 공통 조건 | 허용되는 개인화 |
| --- | --- | --- |
| 세계관 장르 | 이세계 판타지 | 문화, 생태, 인물, 갈등, 세계 구조 |
| 제작 규모 | 인디 게임 | 재사용 가능한 규칙 안의 콘텐츠와 연출 |
| 게임 장르 | 실시간 액션 RPG | 전투 원형, 능력, 성장, 적 대응 |
| 화면 구성 | 2D 탑다운, 고정된 관찰 각도 | 같은 시점 안의 구역 구성과 공간 표현 |
| 인게임 아트 | 픽셀아트 | 팔레트, 실루엣, 재질 표현, 배경과 효과의 분위기 |
| 인물 표현 | 작고 단순화된 비례와 선명한 실루엣 | 종족·외형·장비, 개인별 개성 |
| 기본 액션 감각 | 빠른 반응과 읽기 쉬운 전조·타격 피드백 | 원형별 속도 차이, 방어 방식, 빌드 |

실시간 액션 RPG는 기존 생성 파이프라인의 장르를 유지한다. 해석이 다른 장르나 3D를
연상시켜도 공통 조건을 바꾸는 근거로 사용하지 않는다.

인게임의 캐릭터·적·플레이 배경·전투 효과는 픽셀아트로 설계한다. 회화적 배경 위에
캐릭터만 픽셀로 놓는 혼합 매체를 기본값으로 선택하지 않는다. UI 글꼴과 편의 기능까지
모두 픽셀로 제한하지는 않는다. 별도의 대화 일러스트 매체는 아직 확정하지 않는다.

다음 항목은 이번 결정에 포함되지 않는다.

- 기준 해상도, 타일·스프라이트 크기, 팔레트 수, 애니메이션 프레임 수
- 대화 초상화·컨셉아트·컷신의 매체와 상세 UI 스타일
- 로그라이트 초기화 규칙, 인벤토리 배치 퍼즐, 온라인 협동

생성마다 탑다운을 횡스크롤·벨트스크롤·별개의 등각 투영 방식으로 바꾸지 않는다.
여기서 탑다운은 바닥과 인물의 앞·옆면을 함께 읽는 내려다보기이며 수학적인 정수직
투영이나 특정 카메라 각도 수치를 요구하지 않는다. 정확한 각도·화면 배율은 프로토타입에서
정하되 플레이어가 카메라를 회전해 적을 찾는 조작은 요구하지 않는다.

## 4. 단일 기준 문서와 전달 경로

[공통 프롬프트](../prompts/game-presentation-contract.md)를 공통 제작 조건의 단일
기준 문서로 사용한다. 3절의 고정 조건, 허용 범위, 미결정 항목과 아래 표현 규칙을 담는다.
개인별 생성 결과가 아니라 저장소에 커밋하는 공통 입력이다.

기존 `docs/prompts/personalized-action-rpg-concept.md`는 이 문서를 명시적으로 참조하도록
정비한다. 각 스킬 reference에 조건 전문을 따로 복제하지 않고 공통 문서를 읽도록 연결한다.
현재 두 프롬프트가 연결되지 않은 문제를 또 다른 독립 프롬프트 추가만으로 해결하지 않는다.

오케스트레이터는 다음 세 에이전트에 공통 계약의 정확한 절대 경로를 필수 입력으로 전달한다.

1. `select-gameplay-concept`: 모든 전투 후보를 2D 조작·표현으로 구성한다.
2. `select-world-concept`: 모든 세계 후보의 이동·공간 연결을 2D 화면에서 설명한다.
3. `generate-gdd-from-interpretation`: 공통 계약과 선택된 두 브리프를 함께 읽는다.

독립 스킬 호출에도 동일 입력이 필요하다. 경로 누락·파일 부재·빈 파일이면 후보 작성 전에
실패한다. 대화 이력, 이전 GDD, 개인 해석에서 제작 조건을 추정하지 않는다.
`light`와 `deep`은 같은 계약을 사용하며 설명 깊이만 다르다.

## 5. 공간·카메라 설계 규칙

- 플레이를 설명할 때 화면상의 이동, 공격 방향, 회피, 높이 차와 가림의 처리 방식을 명시한다.
- 어깨 너머 추적 카메라, 플레이어가 자유롭게 회전하는 3D 카메라, 원근 깊이를 따라
  자유롭게 조준·이동하는 전투를 필수 플레이 문법으로 선택하지 않는다.
- 수직 도시, 공중전, 거수 등반, 층 전환, 깊이감 있는 배경은 허용한다. 다만 실제 조작은
  탑다운 바닥 평면의 위치, 연결 지점과 명시적 층 전환으로 설명한다. 별도의 횡스크롤
  플랫폼 조작이나 자유 3D 비행을 필수로 추가하지 않는다.
- 바닥 평면상의 상하좌우 이동과 공격 범위를 기준으로 설계한다. 점프·부유를 사용할
  경우 그림자·착지 표시와 높이 판정 규칙으로 위치를 읽게 한다. 장식적 높이가 숨은
  3D 조준을 요구해서는 안 된다. `2.5D`라는 이름만으로 계약 충족을 선언하지 않는다.
- 패럴랙스, 화면 흔들림, 확대·축소는 2D 표현과 양립할 수 있다. 사용 여부만으로 실패시키지 않는다.
- `3인칭`처럼 차원을 판별하기 어려운 표현 대신 구체적인 2D 시점을 기술한다.

세계 지문의 `vertical`, `celestial`, `layers`, `gravity` 등을 금지하거나 변경하지 않는다.
세계의 연결 구조와 화면 표현은 서로 다른 조건이다. 공통 스타일은 전투·세계 지문의
다양성 점수나 중복 회피 축에 포함하지 않는다.

## 6. 산출물 계약

전투 브리프, 세계 브리프, 최종 GDD는 각각 다음 블록을 정확히 한 번 포함한다.

````markdown
```game-presentation
{
  "schemaVersion": 1,
  "dimension": "2d",
  "view": "top-down",
  "artStyle": "pixel-art",
  "productionScale": "indie",
  "settingGenre": "otherworld-fantasy",
  "gameGenre": "action-rpg"
}
```
````

키와 값은 위 계약과 정확히 같아야 한다. 탑다운을 새 고정 값으로 검사하고, 구체적인
화면 구도는 본문에 설명한다. 공통 조건의 근거를 개인 해석 ID에 억지로 연결하지 않는다.

전투 후보마다 핵심 루프를 2D로 어떻게 조작하는지 설명하고, 세계 후보마다 이동·해금·
귀환을 화면에 어떻게 표현하는지 설명한다. 기존 필드의 설명에 포함해 별도 후보 스키마를
불필요하게 늘리지 않는다. 선택되지 않은 후보도 공통 조건을 위반해서는 안 된다.

GDD에는 세부 시점과 이동 평면, 타격·높이 판정, 가림 처리, 픽셀 실루엣·전조의 가독성,
인디 규모에서 우선 구현할 핵심 조우를 기술한다. 색이나 분위기만으로 픽셀아트 설계를
대신하지 않으며 모든 시스템의 세부 제작 수치를 요구하지는 않는다.
추가로 기본 공격과 방어 대응의 즉각적인 피드백, 일반 적 여러 개체와 보스의 가독성,
성장 전후에 조작이나 전투 선택이 달라지는 사례를 적어도 하나씩 설명한다. 원거리·설치·
소환 원형도 직접 조작과 피드백이 명료하면 허용하며 모두 근접 무기로 바꾸지 않는다.

## 7. 검증과 실패 처리

결정적 검증과 자연어 검토의 책임을 구분한다.

| 검증 | 책임 |
| --- | --- |
| 공통 입력 누락·빈 파일 | 단계 시작 전 입력 확인 |
| 선언 블록 누락·중복·JSON 오류·알 수 없는 키·값 불일치 | 공통 parser와 각 validator |
| 브리프·GDD 사이 계약 불일치 | 최종 파이프라인 검증 |
| 선언은 2D인데 본문은 어깨 너머 3D 전투인 모순 | 각 생성 단계의 의미 검토 및 수용 검토 |
| 모든 후보의 2D 조작성, 픽셀 가독성, 인디 제작 범위 | 후보 선택 전 의미 검토 및 수용 검토 |

공통 parser는 세 validator에서 재사용한다. 원본 프롬프트를 읽으라는 지시와 검사 가능한
출력 블록을 함께 도입한다. 블록 일치만으로 자연어 본문까지 검증됐다고 보고하지 않는다.
키워드 검사를 추가하더라도 `3D 카메라를 사용하지 않는다` 같은 부정문이나 예시를
오판하는 단순 단어 금지 검사를 필수 통과 기준으로 삼지 않는다.

의미 검토에서는 본문이 선언과 충돌하면 같은 단계의 수정 사유로 처리한다. 수정·재검증
횟수는 기존 단계별 정책을 따른다. 해결되지 않으면 해당 단계를 실패시키고 종속 단계를
진행하지 않는다. 최종 검증 전에 지문을 등록하거나 run을 성공 처리하지 않는다.

## 8. 테스트와 수용 사례

실제 개인 입력이나 과거 GDD를 복제하지 않고 최소 합성 fixture를 만든다.

결정적 테스트는 다음을 확인한다.

- 정상 블록을 세 산출물 validator가 통과시킨다.
- 블록 누락·중복, 잘못된 JSON, `3d`, 다른 아트 매체, 누락·추가 키를 실패시킨다.
- `view` 누락이나 `side-scrolling` 등 탑다운이 아닌 선언을 실패시킨다.
- 기존 전투·세계 지문 및 해석 근거 검증이 계속 동작한다.
- 공통 입력이 없는 단계 호출을 거부하고 격리된 세 단계에 정확한 경로가 전달된다.
- 실패 단계 이후 GDD 생성·지문 등록·성공 처리가 진행되지 않는다.

자연어 수용 검토용 합성 사례는 다음과 같다. 이는 자동 의미 검증 완료를 뜻하지 않는다.

| 사례 | 기대 판정 |
| --- | --- |
| 2D 선언 + 어깨 너머 카메라로 깊이 방향 자유 조준 | 실패: 본문과 선언 충돌 |
| 픽셀아트 선언 + 사실적인 3D 캐릭터 모델을 기본 매체로 선택 | 실패: 매체 충돌 |
| 횡스크롤 수직 도시 + 발판 점프를 핵심 조작으로 선택 | 실패: 탑다운 공통 시점 위반 |
| 탑다운 수직 도시 + 연결 지점·층 전환·그림자 표시 | 허용 |
| 탑다운 픽셀 전투 + 패럴랙스·확대·축소 | 허용 |
| 탑다운 선언 + 자유 회전 카메라로 가려진 적 조준 | 실패: 본문과 관찰 각도 계약 충돌 |
| 작은 픽셀 캐릭터 + 과도한 효과로 전조와 플레이어가 보이지 않음 | 보완 필요: 전투 가독성 |
| 탑다운 소환 원형 + 직접 이동·소환 지시·공격 범위가 명료함 | 허용: 근접 무기는 필수가 아님 |
| 아이템 조합 뒤 공격 궤적과 발동 조건이 바뀌고 피드백으로 구별됨 | 허용: 빌드 체감 |
| 2D 선언만 있고 전투·공간 표현 설명 없음 | 보완 필요 |
| 2D 전투에 인디 규모로 감당할 근거 없는 다수의 고유 제작 체계 추가 | 범위 축소 필요 |

실제 모델 생성 실험은 별도 로컬 평가로 수행할 수 있지만 필수 회귀가 특정 과거
아티팩트나 출생 입력에 의존해서는 안 된다.

## 9. 구현 순서와 완료 조건

1. 공통 프롬프트를 작성하고 원본 컨셉 프롬프트·세 스킬 reference의 참조를 연결한다.
   - 검증: 서로 다른 고정 조건 사본이 없고 확정·미결정 항목이 구분된다.
2. 오케스트레이터와 독립 호출의 필수 입력을 연결한다.
   - 검증: 격리된 세 단계의 입력 전달 및 누락 실패 테스트를 통과한다.
3. 공통 블록 parser와 세 산출물 validator를 연결한다.
   - 검증: 정상·오류 합성 fixture 및 기존 검증 테스트를 통과한다.
4. 후보·GDD의 의미 검토 지침과 합성 수용 사례를 연결한다.
   - 검증: 선언과 본문의 모순, 허용되는 2D 공간 표현을 구분해 평가한다.
5. 파이프라인 문서와 관련 전투·세계 spec의 입력·출력 계약을 갱신한다.
   - 검증: 문서와 실제 호출 계약이 일치하며 `bun run test`, `bun run check:docs --review`를 통과한다.

완료 시 새 생성은 공통 스타일을 필수 입력으로 받고, 모든 후보와 GDD가 2D 탑다운 픽셀아트의
조작·공간 표현을 설명해야 한다. 결정적 검사와 의미 검토의 한계를 명시하고 기존
아티팩트의 소급 수정 없이 적용한다. 해상도·픽셀 규격·로그라이트 진행 등의 추가 고정은
별도 결정으로 남긴다.

## 10. 구현 결과와 검증 범위

- [공통 입력 검사·선언 parser](../../scripts/game-presentation.ts)를 세 단계에서 재사용한다.
  단계 시작 전 공통 파일을 검사하며 전투·세계·GDD 검증 CLI의 마지막 인수로도 필수다.
- 원본 컨셉 프롬프트, 세 스킬과 reference, 격리 오케스트레이터의 단계별 전달 경로를 연결했다.
  오케스트레이션은 기존과 같이 스킬 지침으로 실행하며 별도 자동 스케줄러를 추가하지 않았다.
- 전투·세계 브리프와 GDD의 선언이 빠지거나 고정 값과 다르면 실패한다. 두 등록 CLI도
  잘못된 선언을 거부하지만, 등록 CLI만으로 전체 단계 검증·의미 검토의 완료를 증명하지 않는다.
- 모든 후보의 조작성과 GDD의 가독성·빌드 피드백·제작 범위를 공통 프롬프트의 의미 검토로
  연결했다. 이 검토 실패도 기존 수정 한도와 단계 실패 절차를 따른다.
- [합성 의미 검토 사례](../../scripts/fixtures/game-presentation-cases.json)는 카메라·매체 모순,
  수직 공간의 탑다운 표현, 소환 조작, 효과 가독성, 빌드 변화와 제작 범위를 비교한다.
- [공통 계약 테스트](../../scripts/game-presentation.test.ts)와 전투 validator 테스트는
  정상 선언, 형식·값 오류, 공통 입력 누락·부재·공백, 상위 선언 전파와 등록 거부를 확인한다.
  기존 세계 CLI 회귀도 새 필수 입력과 선언으로 갱신했다.

자동 테스트는 실제 에이전트를 실행하지 않는다. 입력 경로 전달, 의미 검토 실패 후 종속
작업 중단·성공 처리 금지는 스킬 지침과 수용 검토의 계약이며 자동 스케줄러의 실행 테스트가
아니다. 선언만 맞춘 부적합 본문을 parser가 자동 판정한다고 주장하지 않는다.
실제 모델의 전체 생성 품질과 스타일 일관성 평가는 별도 로컬 실행으로 남긴다.

검증 기록:

- `bun run test`: 20개 파일, 158개 테스트 통과, 실패 0개.
- `bun run check:docs --review`: 오류 0개. 기존 검토 후보 10개는 버전 정책·가상 예제·
  과거 문제 설명이며 이번 변경에서 새 로컬 근거 의존을 추가하지 않았다.
- 전투·세계 선택, GDD 생성, 전체 오케스트레이션 스킬의 `quick_validate.py` 통과.
- `git diff --check` 통과. 기존 로컬 산출물·레지스트리와 활성 series는 변경하지 않았다.
