# 편집 제출 메타데이터의 도구 소유권

> 상태: 제안 — 구현 전
> 작성일: 2026-11-16
> 관련: [이슈 #22](https://github.com/arch-spatula/isekai-generator/issues/22)
> 선행: [고정 제작 조건과 채택값의 문서 자동 조립](deterministic-design-document-assembly.md)
> 작업 브랜치: `feat/deterministic-design-assembly`

## 1. 문제와 목표

편집 제출에서 도구가 이미 아는 `sourceSha256`, `review.system`, `review.attempt`,
`review.scope`를 모델이 다시 출력한다. 해시의 일부 누락이나 숫자 회차와 UUID의 혼동이
의미 검토와 무관한 제출 실패 및 모델 재호출을 만든다. 검증을 없애지 않고 이 중복 전달을
제거한다. 모델에게 해시 계산 함수를 추가로 호출시키는 작업도 필요하지 않다.

개인정보 없는 최소 사례는 다음과 같다. 이 예시는 합성 재현 조건이며 실제 생성물의
보존이나 특정 실행 이력을 전제로 하지 않는다.

| 조건 | 기존 실패 | 목표 |
| --- | --- | --- |
| DB의 원본 SHA-256은 64자이나 응답에 일부만 복사 | `integrity-error`와 운영 차단 | 모델 응답에 해시를 요구하지 않고 함수가 원본을 검증 |
| DB의 편집 회차는 숫자이나 응답에 attempt UUID 사용 | `Review input mismatch` | 함수가 예약된 숫자 회차를 전달 |
| 검토 대상과 범위는 예약 시 확정 | 모델이 `system`·`scope` 재출력 | 해당 시도의 고정값을 함수가 사용 |

성공 기준은 **메타데이터 없는 정상 제안을 그대로 제출·검증·채택하고, 원본 변조와 잘못된
claim은 계속 거부하는 것**이다. 해석 품질 향상이나 전체 비용 절감률을 이 변경의 자동
검증 결과로 주장하지 않는다.

## 2. 책임과 최소 제출 계약

기존 `prepare/input/submit/finish`와 편집 평가 함수를 사용한다. 새 스케줄러, 범용
메타데이터 조립 프레임워크, 별도 JSON/JSONL 운영 파일을 만들지 않는다.

| 값 | 단일 원본·소유자 |
| --- | --- |
| 원본 경로와 `sourceSha256` | 예약된 입력 snapshot과 실제 원본 바이트, 제출·검증 함수 |
| `system` | 예약된 편집 대상 단계, 함수 |
| `attempt` | DB가 할당한 해당 종류의 숫자 회차, 함수 |
| `scope` | DB가 할당한 편집 범위, 함수 |
| 편집 대상·원문·대체문과 진단 연결 | 모델 |
| 수정·보존·미해결 판단과 이유, 의미 보존 확인 | 모델 |

모델은 다음 형태만 반환한다. 자동 진단과 의미상 추가 대상이 없는 무수정 검토의 합성
예시이며, 진단이 있을 때 이를 빈 배열로 무시해도 된다는 뜻은 아니다.

```json
{
  "edits": [],
  "review": {
    "primary": [],
    "secondary": [],
    "preservationConfirmed": true,
    "unresolved": []
  },
  "reviewMarkdown": "자동 진단과 추가 의미 대상을 검토하고 원문의 의미 보존을 확인했다."
}
```

`nextScopeReason`은 기존 미해결 조건에 따라 사용한다. `system`·`scope`와 대상 목록은
판단에 필요한 입력 제약으로 계속 제공하지만 응답에서 복사하지 않는다. 원본 해시와 회차의
출력·계산 지시는 편집 스킬·호출 예시·프롬프트에서 제거한다. 사용량은 실제 도구 계측값이
있을 때만 기록하며 모델에게 추정시켜 채우지 않는다. 새 계측 시스템은 이 범위에 포함하지 않는다.

검토의 의미를 가진 필드는 자동 생성하지 않는다. `preservationConfirmed`, 상태·이유,
수정문과 미해결 판단을 도구가 통과하도록 바꾸거나 없는 의미 검토를 승인으로 채우지 않는다.

편집 계약 안내에는 다음 기존 상태값과 대상 형식을 명시한다.

- primary: `fixed`, `unresolved`, `false-positive`
- secondary: `fixed`, `preserved`, `needs-expansion`, `deferred`
- 대상: 해당 단계의 기존 파서 또는 입력이 제공하는 실제 식별자. 임의 설명 문구를
  target으로 사용하지 않는다. 단계별 오탐 허용 정책은 변경하지 않는다.

## 3. 제출·원본 검증·저장

1. 기존 CLI의 attempt ID와 claim으로 유효한 편집 시도를 확인한다. 모델 제안으로
   run·체계·원본·회차·범위를 선택하거나 바꾸지 않는다.
2. 기존 validator revision과 입력 snapshot을 확인하고, 고정된 원본 경로에서 바이트를
   읽어 해시를 함수로 계산한다. snapshot의 해시 및 기존 원본 연결과 대조한다.
3. 검토 평가에 필요한 고정 메타데이터는 DB에서 가져와 함수 인자로 전달한다. 기존 내부
   평가·결과 형식을 유지해야 한다면 함수 내부에서만 합친다. 모델이 이 값을 생성하거나
   반환해야 하는 새로운 중간 단계를 추가하지 않는다.
4. 제안의 대상·원문 일치·범위·진단 연결·리뷰를 기존 기준으로 검사하고 후보를 조립한다.
   정상적인 무수정 검토도 허용한다. 원본·후보·검토·채택의 해시 연결을 유지한다.
5. 제출 payload에는 모델의 실제 제안을 보존한다. 별도로 이미 저장된 DB 값을 복제하는
   테이블을 추가하지 않는다. 재전달·재개·게시 복구도 같은 시도와 고정 원본을 사용한다.

새 계약의 모델 출력에 제거한 제어 필드가 다시 들어오면 위치를 식별하는 제출 계약 오류로
거부한다. 서로 다른 메타데이터를 조용히 덮어써 제안의 불일치를 숨기지 않는다. 실제 원본
해시 변조·claim 불일치·revision 변경은 계속 기존 무결성·실행 계약으로 차단한다.
원본 변조나 I/O 오류를 해결하려고 모델을 다시 호출하거나 새 run을 만들지 않는다.

제출 형식 오류와 실제 원본 무결성 오류를 진단에서 구분한다. 호출 예산·범위 확대·수정 및
의미 보존 정책 자체는 이 변경에서 바꾸지 않는다. 새로운 자동 재시도 경로도 추가하지 않는다.

## 4. 적용 범위와 기존 제출

대상은 공유 편집 제출·평가 경로와 이를 사용하는 현재 지원 단계다. 다른 브랜치의 별도
통합 편집 기능을 이 작업 때문에 병합하거나 새 단계를 추가하지 않는다. 통합 편집이 이미
지원되는 기준에서 구현한다면 같은 도구 소유권을 적용하고 기존 단계별 차이를 보존한다.

편집 스킬·호출 지침, 관련 SQLite·편집 명세, 테스트 전용 fixture를 함께 갱신한다.
차트·해석의 내용, 설계 문서 조립 계약, 전투·세계 선정 규칙과 게시 경로는 변경하지 않는다.
전투 성향 일곱 축의 프롬프트 전달 누락과 형식 실패에 따른 범위 확대 정책은 별도 검토 사항이다.

이미 채택된 제안·원본·검토 기록은 수정하지 않는다. 구형 진행 중 시도는 기존
validator revision 차단을 유지한다. 그 기록을 새 모델 출력으로 조용히 재해석하지 않는다.
이를 위해 별도의 이중 프로토콜이나 범용 호환 계층을 만들지 않는다.

## 5. 구현 순서와 검증

1. **모델 출력과 도구 인자 분리** → 검증: 모델 계약에 네 제어 필드가 없고 DB 값이
   기존 평가 경로에 연결된다. 편집 스킬과 소비자의 요구가 일치한다.
2. **제출·저장·복구 연결** → 검증: 제안을 바꾸지 않고 같은 원본·후보·검토·채택에
   연결하며 claim·revision·무결성 거부를 보존한다.
3. **합성 회귀와 문서 검토** → 검증: 아래 사례와 기존 관련 테스트, 문서 검사를 통과한다.

[테스트 작성 가이드](test-writing-guide.md)에 따라 실제 개인 차트나 과거 GDD 없이
모델 호출 없는 합성 fixture로 검증한다.

- 메타데이터 없는 정상 수정과 무수정 검토가 공개 `submit/finish` 경로에서 채택된다.
- 서로 다른 체계·숫자 회차·scope에서도 해당 시도의 DB 값을 사용한다. 기본값 고정
  구현이 통과하지 않도록 기본 예제 외의 유효한 조합을 포함한다.
- 실제 원본 변조, 다른 시도의 claim, 잘못된 원본 연결과 revision 변경은 의도한
  진단으로 거부하고 원본 및 기존 채택 결과를 보존한다.
- 제거된 필드의 재제출, 잘못된 상태 enum·target·진단 연결·빈 의미 검토는 구체적인
  계약 오류로 거부한다. 관계없는 오류만 확인하는 테스트를 만들지 않는다.
- 정상적인 짧은 설명과 보존 판단은 허용한다. 의미 품질을 길이·금지어로 판정하지 않는다.
- 재전달·중단 재개·게시 복구가 다른 원본이나 잘못된 해시에 승인을 연결하지 않으며,
  도구 오류 때문에 새 모델 호출이나 예산 초기화가 발생하지 않는다.
- 구형 진행 중 시도의 revision 불일치는 차단하고 과거 DB 기록을 변환하지 않는다.

구현 후 `bun run test`, `bun run check:docs`, `bun run check:docs --review`,
`git diff --check`를 실행하고 검토 후보의 의미를 확인한다. 실제 모델 생성·비용 재측정은
별도 실험이며 필수 구현 회귀 검증으로 요구하지 않는다.

이 문서는 후속 구현 계획이다. 문서 작성이나 PR 게시만으로 구현·에이전트 호출·GDD
재생성을 실행하지 않는다. 이슈 #22는 후속 구현 완료 전까지 열린 상태로 유지한다.
