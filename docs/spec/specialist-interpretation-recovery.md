# 전문 해석 실패 기록 및 재시도 작업 계획

> 상태: 구현 완료 — 실제 모델 회귀 생성은 후속 작업
> 작성일: 2026-11-05
> 범위: 개인화 GDD 파이프라인의 사주·자미두수·서양 점성술 전문 해석 검증 실패 복구

## 1. 문제와 목표

현재 전문 해석 스킬은 검증 실패 후 현재 문서를 한 번 수정하고, 두 번째 실패를
그대로 반환한다. 오케스트레이터는 이를 받으면 전체 실행을 실패로 종료한다.
검증 오류는 포괄적인 메시지만 반환하므로 수정 에이전트가 정확한 위반 위치를
알기 어렵고, 같은 파일을 수정하므로 시도별 실패 문서도 남지 않는다.

책임 회피 문구를 감지하는 기존 정책은 유효하다. 감지를 완화하거나 금지 표현을
동의어로 바꾸어 통과시키는 것이 아니라, 실패를 먼저 기록하고 해당 체계만 다시
실행하여 유효한 해석을 얻는 흐름을 설계한다.

성공 조건은 다음과 같다.

- 재시도 전에 실패 로그와 해당 시도의 문서가 보존된다.
- 실패한 체계만 재실행하고 이미 통과한 다른 체계는 유지한다.
- 수정 결과는 전체 검증을 다시 통과해야 다음 단계로 전달된다.
- 실패 시도와 최종 채택 문서를 구분할 수 있다.
- 재시도 한도, 취소, 기록 실패와 병렬 실행의 종료 처리가 명확하다.

이 명세는 새 실행의 전문 해석 복구를 다룬다. 이미 종료된 로컬 실행을 재개하거나
상태를 되돌리는 작업은 포함하지 않는다.

## 2. 실패 문서 처리 대안

| 안 | 처리 | 장점 | 부담 |
| --- | --- | --- | --- |
| A | 실패 문서를 삭제하고 해당 체계를 새로 생성 | 이전 해석의 영향을 줄임 | 실패 분석 자료와 유효한 해석을 잃음 |
| B | 실패 문서를 보존하고 해당 체계의 수정·재해석을 요청 | 기존 근거와 유효한 해석을 활용 | 단순한 표현 우회 대신 해석 자체를 수정하도록 지시해야 함 |
| C | 실패 문서를 보존하고 새 해석과 누적 결합 | 여러 해석을 축적 | 중복·모순·근거 연결 및 결합 결과를 별도로 검증해야 함 |

기본 복구 정책으로 B안을 채택한다. 실패 원본은 변경하지 않고 수정 결과를 별도 시도로 저장한다.
재시도 에이전트에는 불필요한 책임 회피 서술을 제거하고 해당 부분을 근거에 기반한
직접적인 해석으로 다시 작성하도록 요구한다. 수정 이후 다른 계약이 깨질 수 있으므로
문구 검사만이 아니라 체계 전체 검증을 수행한다.

A의 삭제 방식과 C의 누적 결합은 기본 흐름에서 제외한다.
새로 생성할 필요가 있는 경우에도 실패 문서는 보존한다. 에이전트 실행 실패나 문서
미생성은 원천 자료에서 새로 생성한다. 문서의 검증 실패는 B안으로 수정하며, 반복됐다는
이유만으로 새 생성이나 자동 결합으로 전환하지 않는다.

### 시도 횟수

- 최초 생성을 포함한 체계별 시도 한도는 우선 3회로 둔다.
- 전면 생성은 해당 체계의 해석만 원천 자료에서 새로 쓰는 동작이며 같은 3회 한도를 소비한다.
- 두 한도는 초기 운영을 위한 잠정 값이다.
- 향후 무제한 실행을 허용하는 명시적 플래그를 추가할 예정이다. 이번 구현 범위에는 넣지 않는다.
- 생성 1회와 수정 2회 또는 새 생성 3회 등 모든 조합에서 체계별 전체 실행은 최대 3회다.
  별도의 생성 세트나 중첩 예산은 없다.

## 3. 제안하는 실행 흐름

1. 오케스트레이터가 체계별 시도 번호와 출력 경로를 지정해 격리 에이전트를 실행한다.
2. 에이전트가 해석을 작성하고 전체 검증 결과를 반환한다.
3. 실패하면 해당 시도 문서를 보존하고 구조화된 실패 로그를 먼저 기록한다.
4. 로그 기록이 완료되고 재시도 여유가 있을 때 해당 체계의 새 격리 에이전트를 실행한다.
5. 수정에는 같은 원천 자료·계약, 직전 실패 문서와 구체적 검증 오류만 전달한다.
   실행 실패 후 새 생성에는 원천 자료·계약만 전달한다.
6. 새 출력에 대해 전체 검증을 다시 실행한다. 실패하면 기록부터 반복한다.
7. 통과한 결과만 기존 정식 경로에 게시하고 그 체계의 완료를 기록한다.
8. 세 체계 모두 통과한 뒤 통합 단계를 시작한다.

재시도 중 부모 run의 상태는 `running`으로 유지한다. 재시도 한도 소진 또는 복구할 수
없는 오류가 발생하면 의존 작업을 중단하고 부모 run을 `failed`로 종료한다.
이미 실행 중인 다른 전문 에이전트는 안전하게 완료하게 한 뒤 최종 상태를 기록한다.
사용자 취소는 `cancelled`로 처리하며, 비정상 종료 상태를 자동 추정하지 않는다.

최종 검증이나 지문 등록의 실패까지 자동 재시도하는 범위 확장은 이번 작업에서 제외한다.

## 4. 저장 및 입력 계약

실패 문서와 실행 로그는 게임 개발 참고 자료가 아니라 저장소의 생성·검증 도구가
참조하는 자료다. 버전 루트의 `garbage/` 아래에 시도별 기록을 두고 `docs/`와 분리한다.
`garbage/`라는 이름은 자동 삭제를 뜻하지 않으며 실패 기록 보존 정책을 그대로 적용한다.
기존 후속 단계의 정식 입력 경로는 유지한다.

```text
artifacts/<version>/
├── artifact-run.json
├── garbage/
│   └── attempts/
│       └── saju/
│           ├── accepted.json
│           ├── 001/
│           │   ├── input.json
│           │   ├── interpretation.md
│           │   └── result.json
│           └── 002/
│               ├── input.json
│               ├── interpretation.md
│               └── result.json
└── docs/GDD/
    └── saju-interpretation.md
```

- 각 시도의 `input.json`에는 체계, 시도 번호, 시작 시각, 생성·수정 구분과 출력 경로를 기록한다.
- `result.json`에는 체계, 시도 번호, 종료 시각, 생성·수정 구분, 결과, 출력 상대 경로와 구조화된 오류를 기록한다.
- 오류에는 규칙 코드, 문서 행 또는 항목 ID, 짧은 설명을 포함한다.
- 출생정보, 생성 문서 본문, 일치한 문장 전체, 원시 계산기 stderr는 로그에 복제하지 않는다.
- 실패 문서의 내용 확인은 기록된 경로를 통해 수행한다.
- 시도 문서와 완료된 결과 기록은 이후 시도에서 덮어쓰지 않는다.
- 로그 기록에 실패하면 다음 에이전트를 실행하지 않고 기록 오류를 보고한다.
- 정식 경로에는 전체 검증을 통과한 시도만 원자적으로 게시한다.
- 게시 실패는 검증 통과와 구분해 보고하며 후속 단계를 실행하지 않는다.
- 체계별 `accepted.json`에 최종 채택한 시도 번호, 원본·정식 경로, 내용 해시와 채택 시각을 기록한다.
- `garbage/`는 게임 개발 문서 탐색이나 후속 설계 에이전트의 입력에서 제외한다.
  해당 체계의 복구 에이전트와 생성·검증 도구만 필요한 기록을 참조한다.

재시도 에이전트에도 `fork_turns="none"`을 유지한다. 수정에는 같은 run의 해당 체계 직전
실패 문서와 결과 기록만 추가로 허용한다. 새 생성에는 실패 내용을 전달하지 않는다.
대화 이력·다른 체계의 결과·이전 버전은 전달하지 않는다.
새 버전을 예약하거나 부모 run의 상태를 변경할 권한도 부여하지 않는다.

## 5. 구현 작업 순서와 검증

### 1단계: 복구 정책 반영

- 채택된 B안과 생성·수정을 합한 전체 3회 한도를 반영한다.
- 재시도 소유자는 오케스트레이터로 단일화하고 스킬 내부의 별도 수정 루프를 제거한다.
- 검증: 최초 생성과 재시도를 포함한 최대 실행 횟수를 하나의 규칙으로 설명할 수 있다.

### 2단계: 구체적인 검증 진단 추가

- `interpret-chart-system/scripts/validate-system-interpretation.ts`에 규칙별 진단을 추가한다.
- 책임 회피 문구, 필수 섹션, 항목 순서, 영역·해상도, 근거 누락 등을 구분한다.
- 기존 호출자와 boolean 판정의 호환성을 유지하고 감지 기준을 완화하지 않는다.
- 검증: 각 위반을 재현하는 테스트에서 올바른 규칙·위치를 반환하고 기존 판정이 유지된다.

### 3단계: 시도 보존 및 로그 기록 구현

- 시도 경로 할당, 결과 기록과 통과 문서 게시에 필요한 최소 도구를 추가한다.
- 한 체계의 기록이 다른 병렬 체계와 충돌하지 않게 한다.
- 검증: 실패 문서 보존, 덮어쓰기 거부, 로그 기록 실패 시 재실행 차단을 확인한다.

### 4단계: 격리 재시도 연결

- `generate-personalized-gdd/SKILL.md`와 `interpret-chart-system/SKILL.md`의 입력·종료 계약을 맞춘다.
- 오케스트레이터가 실패 기록 후 해당 체계의 에이전트만 다시 실행하도록 한다.
- 다른 체계가 통과해도 실패 체계가 복구되기 전에는 통합하지 않는다.
- 검증: 임시 run과 에이전트 실행 대역으로 실패→수정→통과 흐름 및 호출 횟수를 확인한다.

### 5단계: 종료 및 회귀 검증

- 한도 소진, 반복 실패, 취소, 게시 실패와 병렬 체계 완료 처리를 검증한다.
- `scripts/update-artifact-run.ts`의 기존 상태 전이와 충돌하지 않는지 확인한다.
- 스킬·파이프라인 문서에 로그 경로, 재시도 횟수와 최종 보고 규칙을 반영한다.
- 검증: 전체 관련 테스트와 기존 전문 해석 validator 테스트를 통과한다.
- 실제 모델을 이용한 새 run의 회귀 생성은 구현 이후 별도 검증으로 수행한다.

## 6. 핵심 수용 시나리오

- 책임 회피 문구 감지 시 실패 로그가 재시도 시작보다 먼저 남는다.
- 재시도 결과에서도 같은 위반이 있으면 통과시키지 않는다.
- 책임 회피 문구를 고쳤더라도 근거가 누락되면 다시 실패한다.
- 사주만 실패하면 자미두수와 서양 점성술의 통과 문서는 변경·재생성되지 않는다.
- 복구 후 통합에는 실패 문서가 아닌 최종 채택 문서만 전달된다.
- 한도 소진 시 모든 실패 시도가 남고 부모 run은 `failed`가 된다.
- 기존 종료 run과 등록된 지문은 변경되지 않는다.

## 7. 실행 인터페이스

```text
bun scripts/manage-specialist-attempt.ts prepare <run-directory> <saju|ziwei|natal>
bun scripts/manage-specialist-attempt.ts finish <run-directory> <system> <attempt>
bun scripts/manage-specialist-attempt.ts error <run-directory> <system> <attempt>
```

`prepare`는 run 상대 출력 경로와 시도 번호, 실행 방식(`generate` 또는 `repair`)을 반환한다.
수정이면 직전 실패 문서 및 결과 경로도 반환한다. 에이전트에 전달할 때 절대 경로로 바꾼다.

`finish`는 전체 검증과 결과 기록을 수행하며 `passed`, `validation-failed`,
`execution-failed` 중 하나를 반환한다. `error`는 에이전트 실행 실패를 민감한 본문 없이
기록한다. 기록된 실패는 정상 복구 결과이므로 종료 코드 0이며, 오케스트레이터는 반드시
반환된 `status`를 확인한다. 도구 자체의 오류는 종료 코드 1로 반환한다.

미완료 시도나 기록 오류가 있으면 다음 예약을 거부한다. 체계별 락은 동시에 두 기록자가
수정하는 것을 막는다. 비정상 종료 후 남은 락과 미완료 시도는 자동 삭제·복구하지 않는다.
검증은 통과했지만 게시가 실패한 경우도 자동 재시도하지 않고 오류로 보고한다.

부모 run 상태 변경과 에이전트 실행은 `generate-personalized-gdd` 오케스트레이터가 맡는다.
시도 관리 도구는 부모 run이 `running`인 경우에만 동작하며 종료된 실행을 다시 열지 않는다.

## 8. 향후 작업

- 명시적인 무제한 실행 허용 플래그
- 실제 모델을 이용한 새 run 회귀 검증
- 기존 실패 run을 재개하는 별도 기능은 이번 구현 범위에 포함하지 않음
