# 취합 전 전문 해석 방어문구 편집

> 상태: 구현 — 합성 회귀·계약 수용 smoke 확인, 전체 생성 품질·비용 평가 후속
> 작성일: 2026-11-10
> 범위: 전문 해석 생성 이후, 취합 에이전트에 전달하기 전 방어문구 검사·부분 편집

## 1. 문제와 결정

현재 흐름은 전문 해석의 검증 실패를 기록한 뒤 해당 체계의 해석 에이전트에 수정을
맡긴다. 문서 전체를 입력·출력하는 복구는 방어문구 몇 개를 고칠 때도 비용이 크다.
또한 기존 `RESPONSIBILITY_AVOIDANCE` 검사는 특정 표현을 감지하며, 의미가 같은
다른 표현까지 판별하지는 못한다.

방어문구는 전문 해석을 다시 생성하는 대신 별도의 편집 에이전트가 대상을 선정하고
부분 대체한다. 기존 validator의 진단을 1차 대상으로 사용하고, 에이전트의 추가 의미
검토는 2차 리포트로 남긴다. 각 체계는 이 단계를 거쳐야 취합 입력으로 게시할 수 있다.

이 문서는 [전문 해석 실패 복구 명세](specialist-interpretation-recovery.md)의
방어문구 복구와 통과 문서 게시 시점을 변경하는 후속 제안이다. 실제 관리 도구와 스킬은 아래 계약을 따른다. 다른 구조·근거 오류의 복구 정책을 전면 교체하지 않는다.

성공 조건은 다음과 같다.

- 방어문구만 있는 실패에서 전문 해석 생성 에이전트를 다시 호출하지 않는다.
- 자동 진단과 추가 의미 검토를 구별하고, 수정 대상·이유·결과를 추적할 수 있다.
- 재시도할 때 편집 허용 범위를 넓히되 정상 해석과 근거를 보존한다.
- 전체 validator 통과와 편집 완료 확인을 모두 얻은 결과만 취합에 전달한다.
- 검사 통과를 방어적 의미 전체의 자동 판정 성공으로 보고하지 않는다.

## 2. 역할과 입력 경계

| 역할 | 책임 | 변경 권한 |
| --- | --- | --- |
| 전문 해석 에이전트 | 체계별 해석 생성, 구조·근거 오류 복구 | 해당 체계의 시도 문서 |
| 방어문구 편집 에이전트 | 대상 선정, 부분 대체안, 추가 검토 리포트 | 해당 체계의 편집 제안과 리포트 |
| 오케스트레이터·관리 도구 | 검사, 범위·변경 검증, 적용, 시도 기록, 게시 | 같은 run의 관리 기록과 채택 문서 |
| 취합 에이전트 | 편집 완료된 세 체계 해석 취합 | 통합 해석 문서 |

체계별로 독립된 편집 에이전트를 `fork_turns="none"`으로 실행한다. 입력은 같은 run의
해당 체계 해석, 전체 validator 진단, 해석 지침, 모드, 편집 범위, 출력 경로다.
근거 확인용으로 해당 체계의 차트 자료와 evidence manifest만 허용하며, 다른 체계의
해석·이전 버전·대화 이력·원시 출생 인수는 전달하지 않는다. 원천 차트 보고서가 여러
체계를 담으면 해당 체계 부분만 전달한다.

재시도 입력에는 직전 편집 결과와 리포트, 현재 진단, 기존에 확인한 대상 목록을 추가한다.
시도 이력 전체를 반복 전달하지 않는다. 편집자는 버전 할당·부모 상태 변경·정식 경로
게시 권한을 갖지 않는다. 취합에는 채택된 해석만 전달하며 편집 리포트는 전달하지 않는다.

## 3. 실행 순서

1. 전문 해석 시도 문서를 보존하고 기존 전체 validator를 실행한다. 진단을 먼저 기록한다.
2. 방어문구 외 구조·근거 오류가 있으면 기존 전문 해석 복구로 먼저 해결한다.
   혼합 오류도 이 경로를 사용한다. 이 복구에서 본문이 바뀌면 이전 편집 승인은 무효다.
3. 방어문구만 남거나 validator가 통과하면 전담 편집자를 실행한다.
   자동 진단이 0개여도 취합 전 의미 검토를 한 번 수행한다.
4. 편집자는 1차 자동 진단의 각 위치를 확인하고 최소 대체안을 만든다.
   이어 2차로 문서 전체를 읽어 추가 대상·보존 대상·판단 보류를 리포트에 남긴다.
5. 관리 도구가 제안의 원문 일치와 허용 범위를 확인하고 별도 후보 문서에 적용한다.
6. 후보에 기존 전체 validator를 실행하고, 리포트의 미해결 대상 및 변경 보존 조건을 확인한다.
7. 통과하면 해시와 원본·편집 시도 연결을 기록하고 정식 경로에 게시한다.
   실패하면 기록을 완료한 뒤 다음 범위로 편집을 재시도한다.
8. 세 체계 모두 편집 완료·게시된 뒤에만 취합 에이전트를 실행한다.

추가 검토는 리포트만 생성하고 무시하는 단계가 아니다. 명확한 추가 방어문구는 현재
범위 안에서 함께 고치고, 범위를 벗어난 대상은 다음 시도로 넘긴다. 판단 보류는 원문을
유지하고 이유를 기록하며, 미해결 상태로 취합에 넘기지 않는다. 대상이 없는 경우에는
무수정 결과와 검토 완료 리포트를 남긴다.

## 4. 방어문구 선정과 보존 기준

편집 대상은 요소·관계·발현 조건을 설명하지 않고 요청하지 않은 예측·진단을 부정하거나
결과의 책임을 회피하는 절·문장이다. 금지 단어를 동의어로 치환하는 방식은 허용하지 않는다.
필요 없는 절은 제거하고, 연결이 끊기면 기존 근거에 있는 해석으로 짧게 대체한다.
채울 내용이 없으면 억지로 새 해석을 만들지 않는다.

다음은 보존한다.

- 계산 전제에서 실제 자료의 범위나 부재를 설명하는 문장
- 환경과 조건에 따라 다른 발현을 설명하는 문장, 가능성을 나타내는 표현
- 항목 ID, evidence ID, 체계별 필수 섹션, 해상도와 항목 순서
- 기존 유효 해석의 의미, 관계, 창작 시드와 계산 근거

[합성 평가 사례](../../scripts/fixtures/interpretation-quality-cases.json)를 기준으로
예측을 불필요하게 부정하는 뒤 절은 수정하고, 계산 범위와 조건부 발현 사례는 보존한다.
이 사례들은 목표 판정 자료이며 현재 의미 검사가 구현됐다는 증거는 아니다.

자동 검사 오탐이 의심되면 리포트에 기록하되 검사 규칙을 임의로 완화하거나 통과 처리하지
않는다. 근거 보강이나 해석 재작성 없이는 수정할 수 없는 항목도 편집 권한 밖의 문제로
보고한다. 단순한 단어 삭제로 구조 검사만 통과시키지 않는다.

## 5. 시도별 범위와 비용 한도

편집자는 매 시도 문서 전체를 검토할 수 있다. 넓어지는 것은 읽기 범위가 아니라
실제로 바꿀 수 있는 범위다. 추가 대상의 수에는 임의의 제한을 두지 않는다.

| 편집 시도 | 허용 범위 | 다음 시도로 넘기는 경우 |
| --- | --- | --- |
| 1 | 자동 진단 및 추가 검토가 지목한 절·문장 | 주변 문맥까지 손봐야 하거나 미해결 대상이 남음 |
| 2 | 미해결 문장이 속한 해석 항목 전체, 항목 밖 문장은 해당 문단 | 항목 간 반복·연결 때문에 국소 수정만으로 해결 불가 |
| 3 | 해당 체계 문서의 관련 항목·문단 전반 | 여전히 실패하면 종료·보고 |

3차도 문서 전체 재작성은 아니다. 관련 대상만 편집하고 무관한 문단을 유지한다.
범위를 넓히는 이유와 대상 ID를 리포트에 남기며, 오류 없이 완료된 경우 후속 시도는 없다.
반복 실행 실패·기록 실패 등 운영 오류는 범위 확대의 이유로 사용하지 않는다.

전문 해석 생성·구조 복구는 기존 체계별 최대 3회 호출을 유지한다. 편집은 그와 별도로
체계별 최대 3회 호출이며, 최초 무수정 검토도 1회로 센다. 편집 예산은 원문 시도가
바뀌어도 초기화하지 않는다. 편집 완료 후에는 해당 체계의 상위 복구를 다시 시작하지 않는다.
최악의 경우 체계별 생성·복구 3회와 편집 3회가 실행된다. 추가 호출을 도입하는 만큼
실제 토큰 절감은 측정 전 가설로 취급한다.

후보 문서 전체를 모델이 재출력하지 않도록 변경 제안만 반환한다. 관리 도구가 후보를
조립한다. 모델 입력·출력 토큰과 호출 수를 가능할 때 기록하고, 제공되지 않은 값은
미측정으로 남긴다. 토큰 확인을 위한 별도 모델 호출은 하지 않는다.

## 6. 변경 제안과 리포트 계약

변경 제안에는 원본 문서 해시, 대상 항목 ID 또는 섹션, 원문 문자열, 대체 문자열,
진단 코드 또는 추가 검토 대상 ID를 포함한다. 행 번호는 탐색 힌트이며 단독 적용 기준이 아니다.
원문이 해당 범위에서 정확히 한 번 일치해야 적용한다. 해시 불일치·중첩 변경·중복 일치는
적용하지 않고 오류로 남긴다. 빈 대체 문자열은 불필요한 절·문장 제거에 사용할 수 있다.

리포트에는 다음을 남긴다.

- 제안 최상위 sourceSha256로 연결한 원문, 체계, 편집 시도 번호와 허용 범위
- 1차 자동 진단별 처리: 수정·미해결·오탐 의심과 이유
- 2차 의미 검토별 처리: 추가 수정·보존·범위 확대 필요·판단 보류와 이유
- 각 변경의 대상, 제안 연결, 기존 근거를 보존한 이유
- 적용 후 전체 검증 결과, 미해결 대상 목록, 다음 범위가 필요한 이유
- 호출 수와 측정 가능한 토큰 사용량

로컬 경로 계약 예시는 다음과 같다. 파일명·명령의 실제 인터페이스는 구현에서 확정한다.

```text
artifacts/<version>/garbage/defensive-editing/<system>/
├── 001/
│   ├── input.json
│   ├── edits.json
│   ├── review.md
│   ├── candidate.md
│   └── result.json
└── accepted.json
```

입력 기록은 원본 전문 해석 시도 경로·해시와 진단을 연결한다. 시도별 제안·리포트·후보·
결과는 덮어쓰지 않는다. `accepted.json`은 전문 해석 원본 시도와 채택한 편집 시도,
최종 문서 해시를 함께 가리킨다. 기존 전문 해석 채택 기록과 편집 채택 기록은 구별한다.

원문·대체문은 로컬 편집 제안에만 필요한 만큼 보관한다. 관리 로그·진행 TODO·최종
채팅에는 본문이나 출생정보를 복제하지 않는다. 리포트는 로컬 결과이며 영구 문서의
필수 근거로 삼지 않는다. [로컬 아티팩트 경계](local-artifact-document-boundary.md)를 따른다.

## 7. 완료·실패·진행 기록

편집 제출의 형식·대상·링크·범위·리뷰 계약 오류는 `editing-contract` 진단과
`editing-failed` 결과로 기록한다. 원본과 같은 후보 및 해시를 보존하고, 다음 허용 scope를
준비할 때 실패 사유와 진단을 `retry_scheduled` 이벤트로 남긴다. 준비된 input·원본·source
해시 불일치와 기록·게시 I/O 실패는 계속 예외로 중단하며 범위 확대를 허용하지 않는다.
전문 해석의 `editing-required` 인계는 `validation_succeeded`로 기록하며 최종 게시를 뜻하지 않는다.


완료 조건은 전체 validator 통과, 모든 확정 대상 해결, 판단 보류 없음, 변경 범위 및
보존 조건 확인이다. ID·evidence·순서 등 기계 검증과 의미 보존에 대한 편집자의 확인을
구별해 기록한다. validator만으로 의미 보존을 증명했다고 주장하지 않는다.

기존 `finish`의 즉시 정식 게시를 분리해야 한다. 전문 해석 검증 결과만으로 해당 체계를
최종 완료하지 않고, 편집 검증과 채택 기록까지 성공한 뒤 게시·완료한다. 체계별 편집
체크포인트는 원본 해시, 현재 시도, 상태, 결과 경로를 갖는다. 진행 TODO에는 해석 생성과
편집 완료를 구분한다. 재개 시 원본·후보 해시와 검증 결과를 재확인한다.

한도 소진, 해결할 수 없는 판단 보류, 기록·검증 도구·게시 오류는 취합을 차단한다.
실패 원인을 방어문구 미해결과 운영 오류로 구분한다. 기록 실패 뒤 다음 편집자를 실행하지
않으며 실패를 이유로 전면 재생성에 자동 전환하지 않는다. 부모 상태·취소·병렬 작업 종료는
기존 정책을 따른다. 기존 종료 run과 이전 아티팩트를 자동 수정하지 않는다.

## 8. 구현 순서와 검증 계획

1. 진단 분류와 게시 분리 → 검증: 방어문구 단독·혼합 오류·무진단의 경로와 취합 차단 확인.
2. 변경 제안 적용 및 시도 기록 → 검증: 해시·원문 불일치, 중첩, 범위 초과, 기록 실패 거부.
3. 편집 스킬과 오케스트레이션 연결 → 검증: 격리 입력, 단계별 범위 확대와 총 호출 한도 확인.
4. 합성 fixture 회귀 및 문서 반영 → 검증: 관련 테스트와 `bun run check:docs` 통과.

코드 구현은 [3개 에이전트 작업 흐름](three-agent-implementation-workflow.md)을 적용한다.
스킬·validator·시도 관리·게시·진행 기록의 계약을 함께 변경하되 취합 입력 경로는 유지한다.

필수 수용 시나리오는 다음과 같다.

- 자동 진단이 있는 문장은 1차 대상으로 편집되며 전문 해석 재호출은 없다.
- 자동 검사를 통과한 다른 표현의 방어문구는 2차 리포트에 남고 편집된다.
- 계산 범위 설명과 조건부 발현 문장은 유지되며 대상이 없으면 본문 해시가 같다.
- 문장 수정만으로 해결되지 않으면 이유를 기록하고 항목, 체계 문서 순서로 확대한다.
- 근거·ID·필수 해석이 사라진 후보는 방어문구 검사를 통과해도 채택되지 않는다.
- 사주 편집 실패가 다른 체계의 통과 문서를 바꾸지 않으며 취합은 시작되지 않는다.
- 3회 소진·취소·기록 실패 후 추가 호출이나 자동 재생성이 없다.
- 취합에는 최종 해시가 일치하는 채택 문서만 전달되고 리포트는 전달되지 않는다.

실제 모델 평가는 후속 작업이다. 개인정보 없는 동일 합성 입력과 동일 모델 조건에서
기존 복구와 부분 편집의 호출 수·입출력 토큰·보존 품질을 비교한다. 운영 테스트 통과와
실제 생성 품질·비용 개선의 확인을 별도로 보고한다.

## 9. 구현 인터페이스와 한계

전문 시도 CLI `scripts/manage-specialist-attempt.ts`는 prepare/finish/error를 유지하며,
구조·근거 오류는 validation-failed, 방어문구 단독 또는 무진단은 editing-required를 반환한다.
이 단계에서는 게시하지 않는다. 편집 CLI는
`scripts/manage-defensive-edit.ts <prepare|finish|error> <run-directory> <system> [attempt]`다.
prepare는 체계·시도·scope, source의 output/sha256/전문 attempt, originalSha256, 진단,
input/edits/review/candidate/result/chart/evidence의 run 상대 경로를 반환한다.
재시도는 previous의 직전 candidate/review/result만 연결한다.

edits.json은 sourceSha256, edits 배열과 review 객체다. sourceSha256는 input.source.sha256를
그대로 사용하며 edits와 review 모두를 같은 원문에 연결한다. input.json 파일 자체의
해시를 계산하지 않는다. review에는 별도 해시를 두지 않는다. 변경은 id/target/original/replacement와
진단 코드 diagnosticCode 또는 의미 대상 reviewTargetId를 갖는다. target은 실제 항목 ID나
정확한 heading이다. heading은 다음 heading 전의 직접 본문만 포함한다. 자식 항목은
각 항목 ID로 따로 지정하며 3차에서도 관련 항목별 여러 제안을 사용한다.
review 객체는 system/attempt/scope, primary/secondary, preservationConfirmed,
unresolved와 미해결 시 nextScopeReason을 갖는다. primary는 diagnosticIndex/status/reason/
editIds, secondary는 id/target/status/reason/editIds다. 정확한 타입은
[관리 모듈](../../scripts/artifacts/defensive-edit.ts)에 정의되어 있다.
review.md는 별도 의미 검토 설명이며 result.json은 적용 후 전체 validator 결과·해시·
미해결·호출 수와 측정 가능 사용량을 관리 도구가 기록한다.

통합 단계 진입은 두 accepted 기록의 일치, 원본·후보·정식 문서 해시, 채택된 결과와
전체 validator를 다시 검사한다. 진행 기록은 생성 시도와 편집 시도·해시·상태·결과 경로를
구분한다. 의미 보존은 편집자의 확인이며 자동 의미 판별 증명이 아니다. 실제 모델 호출의
해석 품질·동의어 회피·토큰 절감 평가는 아직 수행하지 않았다.

해시 계약 수정과 실제 편집자 제출 실패, 합성 테스트의 검증 경계는
[해시 계약 인시던트](../incidents/2026-11-10-defensive-editor-hash-contract.md)에 기록한다.
실제 편집자의 합성 사례 제출·적용·채택은 확인했으며, 일반 의미 품질과 전 구간 비용
평가는 후속 작업이다.
