# 고정 제작 조건과 채택값의 문서 자동 조립

> 상태: 제안 — 구현 전
> 작성일: 2026-11-15
> 관련: [이슈 #22](https://github.com/arch-spatula/isekai-generator/issues/22) — [이슈 #12](https://github.com/arch-spatula/isekai-generator/issues/12)에서 분리
> 작업 브랜치: `feat/deterministic-design-assembly`
> 분기 기준: `docs/ccgs-workflow-evaluation` (PR #4)

## 1. 문제와 목표

2D 탑다운·픽셀아트 같은 확정된 제작 조건을 모델이 매번 다시 쓰거나 복사하고 있다.
이미 채택된 전투·세계 값과 검증용 선언의 재출력에도 모델을 사용한다. 고정 문구와 값의
전달·문서 조립은 스크립트로 처리하고 모델은 새로운 설계와 의미 판단에 집중하도록 한다.

현재 공통 계약은 전투 브리프·세계 브리프·GDD에 `game-presentation` 블록을 복사하도록
요구하고, GDD 템플릿은 선정된 전투 지문을 다시 복사하도록 요구한다. 개요에도 공통
조건의 재서술을 요구한다. 이 책임을 도구로 옮긴다. 비용 절감량은 아직 측정하지 않았다.

## 2. 첫 구현 범위와 원본

| 대상 | 원본 | 조립 책임 |
| --- | --- | --- |
| GDD 개요의 고정 제작 사양 | 공통 화면·아트 계약의 명시적 템플릿 | 스크립트가 정해진 위치에 삽입 |
| 세 설계 문서의 `game-presentation` | 공통 계약의 기존 JSON 블록 | 스크립트가 각 문서에 정확히 한 번 삽입 |
| GDD `combat-fingerprint` | 같은 run의 채택 전투 브리프 최종 지문 | 파싱한 일곱 축을 그대로 직렬화 |
| GDD `world-structure` 각 축의 `value` | 같은 run의 채택 세계 fingerprint | 스크립트가 여섯 축의 값을 채움 |
| GDD `world-structure` 각 축의 `manifestation` | 모델이 작성한 이번 게임의 공간 구현 | 모델 작성 후 구조 검사·의미 검토 |

공통 사양의 단일 원본은 [공통 화면·아트 계약](../prompts/game-presentation-contract.md)이다.
별도 코드 상수에 같은 정책 문장을 복제하지 않는다. 해당 문서에 삽입용 고정 문단을
명시적으로 구분하고, 기존 블록 파서와 검증 코드를 가능한 한 재사용한다.

고정 사양은 장르·차원·시점·매체·제작 규모처럼 이미 정해진 조건만 포함한다.
팔레트·종족·의상·지역 분위기·구체적인 실루엣은 고정 문구로 만들지 않는다.
아직 확정하지 않은 해상도·스프라이트 규격·카메라 각도도 임의로 고정하지 않는다.

## 3. 모델의 입력과 출력 책임

### 모델에 계속 제공할 입력

공통 화면·아트 계약은 설계 제약으로 계속 제공한다. 2D 문구의 출력을 생략한다고
세계의 높이·가림·조준·조작 조건까지 숨기지 않는다. 각 단계의 기존 입력 격리와
같은 run의 채택 문서 allowlist를 유지한다.

### 모델이 작성할 내용

- 게임명, 한 문장 소개, 핵심 판타지와 게임을 관통하는 중심축
- 선정된 전투·세계가 이번 게임에서 작동하는 방식과 구체적인 인물·규칙·서사·지역
- 팔레트·실루엣·전조·가림 처리 등 게임별 표현과 조작성·가독성의 설명
- 세계 여섯 축의 구체적 공간 구현인 `manifestation`

모델에게 고정 제작 사양 문단, `game-presentation`, 최종 전투 지문과 세계 축 값을
복사하거나 재서술하도록 지시하지 않는다. 필요한 게임별 설명에서 2D 조건을 자연스럽게
언급하는 것은 허용한다. `2D` 같은 단어의 출현 자체를 금지하는 검사를 만들지 않는다.

### 스크립트가 작성할 내용

고정 사양과 선언, 채택된 축 값은 도구가 채운다. 모델 초안에서 관리 영역은 생략하거나
템플릿의 명시적인 삽입 지점을 사용한다. 구현 시 가장 작은 방식 하나를 선택하고
프롬프트·조립기·테스트에 같은 계약을 적용한다. 모호한 위치에 정규식으로 덧붙이지 않는다.

고정 영역이 중복되거나 모델이 원본과 충돌하는 관리값을 제출하면 명확한 조립 진단으로
거부한다. 충돌 값을 몰래 덮어써 본문과 선언의 불일치를 숨기지 않는다. 모델의 일반
설계 본문과 `manifestation`은 조립기가 바꾸지 않는다.

## 4. SQLite 제출·검증·채택 연결

흐름은 `모델 초안 → 결정적 조립 → 최종 후보 검증·의미 검토 → 채택·게시`로 한다.
조립 전 초안에 최종 문서용 필수 선언 검사를 적용해 모델을 재호출하지 않는다.

- 대상 단계는 `selection`, `world-selection`, `gdd`다. 차트와 해석 단계는 변경하지 않는다.
- 기존 예약 output을 모델 초안으로 사용한다. 조립 결과는 같은 attempt의 별도 후보로
  보존하고, 초안·조립 후보·실제 사용한 공통 계약 및 채택 문서를 해시로 연결한다.
  SQLite를 사용하며 JSON/JSONL 중간 운영 파일이나 별도 스케줄러를 만들지 않는다.
- 조립 원본은 해당 attempt의 고정 입력과 일치해야 한다. 제출 이후 바뀐 원본으로
  조립하거나, 다른 run·미채택 브리프를 사용하지 않는다. 계약 revision 불일치의 기존
  차단 정책을 우회하지 않는다.
- 검증·채택·게시 및 다음 단계의 입력은 조립된 최종 후보와 그 해시를 가리킨다.
  최종 GDD의 열한 절·파일명·게시 폴더·선언 형식은 유지한다.
- 재시도·응답 재전달·게시 복구는 저장된 입력과 후보를 재사용한다. 고정 문단을 중복
  삽입하거나 초안을 최종본으로 게시하지 않는다. 남의 파일·이미 게시한 결과를 덮어쓰지 않는다.
- 누락된 원본·모호한 삽입 위치·조립 I/O 오류는 모델 설계 오류와 구분한다. 도구 오류를
  고치려고 새 모델 호출이나 새 run을 자동 생성하지 않는다. 기존 호출 예산을 늘리지 않는다.

화면 조건을 선언하는 작업은 결정적이지만, 새 설계가 그 조건 안에서 성립하는지의
의미 검토는 계속 필요하다. 2D 선언을 자동 삽입해도 본문이 자유 3D 조준을 요구하면
채택할 수 없다. 기존 단계의 의미 검토를 사용하고 고정 문구만을 위한 모델을 추가하지 않는다.

## 5. 후속 범위

모티프·근거 ID를 구조화된 필드로 받아 `설계 모티프:`와 `해석 근거:` 행을 도구로
조립하는 작업은 후속 단계다. 현재 자유 Markdown을 구조화된 설계 데이터 전체로
바꾸거나 새 문서·에이전트별로 쪼개는 일은 첫 구현에 포함하지 않는다.

기존 로컬 아티팩트의 이동·수정·재생성, 과거 DB 이력의 일괄 변환, 의미 검토 승인
재사용 시스템과 버전 승격도 별도 요청 사항이다. 구형 제출·진행 중 attempt가 있다면
형식과 validator revision을 확인하고 기존 경로를 보존하거나 명확히 차단한다.
무조건 새 형식으로 재해석하지 않는다.

## 6. 구현 순서와 검증

1. **원본과 조립 경계 확정**
   - 공통 계약의 삽입용 고정 문단, 모델이 생략할 관리 영역과 도구 소유 후보를 정한다.
   - 검증: 같은 조건을 중복 정의하지 않고 모델 출력 지침에서 복사 요구를 제거한다.
2. **순수 조립 함수와 제출 경로 연결**
   - 기존 parser로 원본을 읽고 세 설계 문서의 최종 후보를 조립한다. 프롬프트·스킬과
     SQLite 제출·검증·게시를 함께 갱신한다.
   - 검증: 모델을 호출하지 않고 합성 초안·채택 브리프·계약으로 최종 문서를 재현한다.
3. **채택·복구와 오류 회귀 확인**
   - 초안과 최종 후보의 해시, 입력 snapshot, 재시도·복구의 동일 후보 사용을 확인한다.
   - 검증: 불완전한 조립본은 게시되지 않고 후속 입력에도 전달되지 않는다.
4. **최종 계약과 의미 검토 경계 확인**
   - 기존 템플릿·지문·화면·세계 구조 검증을 조립 후보에 적용한다.
   - 검증: 전체 테스트, 문서 검사와 독립 테스트 리뷰를 통과한다. 구조 검사를 의미
     품질이나 실제 비용 절감의 증거로 보고하지 않는다.

[테스트 작성 가이드](test-writing-guide.md)에 따라 다음 합성 사례를 확인한다.

- 초안에 고정 문구·선언이 없어도 도구가 정확히 한 번 삽입하고 최종 검증을 통과한다.
- 전투 일곱 축과 세계 여섯 축의 값은 채택 원본과 일치하고 모델의 창작 본문은 보존된다.
- 게임마다 다른 팔레트·실루엣·manifestation 및 짧고 완결된 설명은 그대로 유지된다.
- 잘못된 축·누락된 manifestation·중복 삽입점·충돌 관리값·존재하지 않는 근거는
  의도한 진단으로 거부한다. 관계없는 다른 오류만으로 통과하는 테스트를 만들지 않는다.
- 다른 run·미채택 원본·해시 변조·계약 변경은 채택을 막고 원래 초안을 보존한다.
- 중단·재개·응답 재전달이 이중 삽입이나 초안 게시를 만들지 않는다.
- 의미상 3D 조준을 요구하는 사례는 별도 의미 검토의 거부 사례로 남긴다. 단순
  단어 검사로 조작성 전체를 자동 판정할 수 있다고 주장하지 않는다.

실제 개인 차트·과거 GDD 없이 재현해야 한다. 필수 검증에 모델 호출을 넣지 않는다.
개발용 역할 분리와 생성 단계의 모델 호출은 별개다.

## 7. 실행 명령과 완료 기준

`feat/deterministic-design-assembly` 브랜치의 이 문서를 기준으로 다음 Codex 스킬을 명시적으로 호출한다.
문서 작성만으로 구현이나 하위 에이전트를 자동 실행하지 않는다.

```text
$implement-with-test-review docs/spec/deterministic-design-document-assembly.md
```

구현 후 저장소 루트에서 실행한다.

```sh
bun run test
bun run check:docs
bun run check:docs --review
git diff --check
```

고정값 재작성 없이 최종 문서를 조립하고, 원본·본문·해시·채택·복구 연결과 기존
검증 계약을 보존하며 독립 리뷰까지 통과하면 첫 구현 완료다. 현재는 계획 문서만
작성한 상태이며 위 구현 검증이나 모델 생성은 수행하지 않았다.
