# 생성 실행의 실패·재시도 이벤트 로그

## 목적과 기록 위치

실행마다 루트 `events.jsonl` 하나에 사건을 발생 순서대로 append한다. 각 줄은 완결된
JSON 객체다. 무엇을 하다 어디서 왜 실패했고, 왜 재시도하거나 중단했는지 이 파일에서
확인할 수 있어야 한다. 진행 중 표시만 남기는 것은 실패 로그를 대신하지 못한다.

`artifact-run.json`은 전체 상태, `TODO.md`와 체크포인트는 진행 요약이다. 전문 해석의
시도별 문서·result는 재시도 입력과 게시 복구를 위해 유지하지만 실패 원인을 찾기 위해
그 파일들을 먼저 순회할 필요가 없도록 이벤트에 진단을 함께 담는다.

신규 예약은 빈 로그를 생성한다. 진행 중인 기존 실행은 첫 이벤트부터 기록할 수 있지만
과거 사건을 추정해 소급 생성하지 않는다. 종료된 실행을 다시 열지 않는다.

## 이벤트 계약

모든 이벤트는 `timestamp`, `event`, `stage`, `operation`을 가진다. 시도가 있는 작업은
`attempt`를 기록하고, 실패·재시도·중단은 구체적인 `reason`과 가능한 `issues`를 담는다.
진단은 `code`, `message`와 필요한 `item`, `field`, `line`을 포함한다. 관련 산출물은
`output`, 자식 프로세스 종료 코드는 `exitCode`로 기록할 수 있다.

- `validation_failed`: 위반 조건과 위치를 기록하고 수정 전에 append한다.
- `execution_failed`: 실행·파일 쓰기·도구 호출 실패와 확인 가능한 원인을 기록한다.
- `retry_scheduled`: 다음 시도와 직전 실패에 따른 수정·재생성 이유를 실행 전에 기록한다.
- `stage_stopped`: 시도 한도 소진·미해결 의미 충돌·인프라 오류 등 중단 이유를 기록한다.
- `validation_succeeded`: 해당 시도의 검증 성공을 기록한다.
- `run_started`, `run_succeeded`, `run_failed`, `run_cancelled`: 전체 실행의 경계를 기록한다.

예를 들어 합성 진단은 다음과 같다. 원문 대신 위반한 필드와 요구 조건을 남긴다.

```json
{"timestamp":"2026-11-08T00:00:00.000Z","event":"validation_failed","stage":"integration","attempt":1,"operation":"validate-interpretation.ts","reason":"Required interpretation field is empty.","issues":[{"code":"item-field","message":"Required field must contain non-whitespace content.","item":"I-01","field":"해석","line":40}]}
```

구체적인 원인이 제공되지 않았다면 진단이 제공되지 않았다는 사실과 종료 코드를 남긴다.
코드나 에이전트가 확인하지 않은 원인을 꾸며 쓰지 않는다. 출생 인자·보고서·해석 본문·
대화·자식 stdout·전체 명령 인자는 복사하지 않는다. 차트 runner는 원시 계산기 stderr 대신
계산 실패·누락된 체계·근거 생성·파일 쓰기 등 확인한 오류 범주와 안전한 진단을 기록한다.

## 공통 기록 도구와 호출

`scripts/artifacts/artifact-events.ts`가 완성된 한 줄을 잠금 안에서 append한다. 병렬
프로세스가 기존 줄을 덮어쓰거나 조각을 섞지 않게 한다. 잠금 대기는 제한하며 남은 잠금을
자동으로 지우지 않는다. 기록 실패를 성공으로 숨기지 않고 후속 작업을 중단한다.
로그와 상태 파일은 단일 트랜잭션이 아니므로 쓰기 중단 시 실제 기록을 대조한다.

검증과 지문 등록은 다음 래퍼로 실행한다. `attempt`는 실제 시도 번호이며 일반 작성은
1, 허용된 한 번의 수정은 2다. 전문 해석은 기존 관리자의 총 3회 예산을 유지한다.

```text
bun scripts/run-logged-step.ts <run-directory> <stage> <attempt> -- bun <validator-or-registration-script> <arguments...>
```

래퍼는 명령을 한 번 실행하고 stdout/stderr와 종료 코드를 호출자에게 전달한다. 실패 시
구조화된 stderr의 `issues`를 보존하고, 구조화되지 않은 검증기 오류는 실제 메시지를
기록한다. 임의 명령이나 원시 출생 인자를 다루는 계산기를 이 래퍼에 넣지 않는다.
등록은 비멱등 작업이므로 로그 기록 실패 후 무조건 재실행하지 않고 레지스트리를 확인한다.

에이전트의 의미 검토 실패와 수정 결정처럼 자식 프로세스로 표현되지 않는 사건은 다음
명령으로 기록한다. JSON은 셸에서 안전하게 인용하며 원문을 포함하지 않는다.

```text
bun scripts/log-artifact-event.ts <run-directory> '<JSON-event>'
```

각 단계는 실패 기록 후에만 기존 예산 안에서 재시도한다. 오류를 보고받은 상위
오케스트레이터도 실행 실패와 중단 결정을 기록한다. 이미 래퍼가 기록한 검증 오류를
진행 상태 이벤트로 대체하거나 같은 검증을 기록 목적으로 다시 실행하지 않는다.

## 진단과 검증 범위

통합 검증기는 `diagnoseInterpretation`으로 위반 항목·필드·행을 반환하고 기존 boolean
API는 같은 진단 결과로 판정한다. 길이로 의미 품질을 판단하는 조건은 다시 도입하지 않는다.
구조화되지 않은 다른 검증기는 실제 제공한 오류 메시지 수준으로 기록하며, 이 로그가
모든 검증기의 원인 해상도를 자동 개선한다고 주장하지 않는다.

합성 실행으로 병렬 append·기존 내용 보존·실패 전후 순서·재시도 이유·진단 위치·CLI 종료
코드·로그 쓰기 실패의 전파를 검증한다. 차트 runner와 전문 해석 관리자의 자동 연결,
통합 진단 및 검증 래퍼를 확인한다. 실제 생성·종료 실행의 소급 변경은 요구하지 않는다.

구현·독립 테스트 작성·읽기 전용 리뷰와 수정 후 재검토를 거쳤다. 최종 통합 검증은
`bun run test`에서 24개 파일, 286개 테스트 통과, 실패 0개다. 병렬 쓰기는 합성 실행의
16개 프로세스로 검증했고, 차트 실패는 실제 계산기의 필수 옵션 오류를 사용했다.
차트 성공 로그는 합성 출력으로 확인했으며 실제 개인화 GDD 생성 실험은 하지 않았다.
