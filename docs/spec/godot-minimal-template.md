# Godot 최소 전투 방 템플릿

> 상태: 제안 — 9절 결정 확정(2026-11-17), 구현 전
> 작성일: 2026-11-17
> 관련: [Godot과 PixelFX를 이용한 게임 제작 경로 평가](../ADR/2026-11-11-godot-pixelfx-evaluation.md),
> [Godot 게임 제작용 에이전트 도구 생태계 도입](../ADR/2026-11-17-godot-agent-tooling-ecosystem.md)

## 1. 문제와 목표

평가 ADR은 Godot 프로젝트 전체를 매번 자유 생성하지 않고, **검증된 최소 템플릿의 슬롯만
채우는 방식**을 먼저 평가하기로 했다. 에이전트가 `project.godot`, 씬, 스크립트, 리소스 경로와
입력 설정을 매번 새로 만들면 텍스트 리소스 충돌과 끊어진 참조가 생기고, 같은 기획에서 같은
프로젝트가 나온다는 보장도 없다.

이 명세의 목표는 다음과 같다.

1. 평가 ADR의 비교 프로토타입 범위인 **전투 방 하나**를 실행하는 Godot 4.7 템플릿을 만든다.
2. 템플릿의 씬과 스크립트는 고정하고, 기획에 따라 달라지는 값은 **데이터 슬롯**으로 분리한다.
3. 채우기 도구는 슬롯 입력을 검증한 뒤 프로젝트를 출력한다. 같은 입력이면 같은 출력이 나와야 한다.
4. 템플릿이 표현하지 못하는 전투 축 값은 조용히 대체하지 않고, 지원하지 않는다고 실패한다.

## 2. 범위

### 2.1 포함

평가 ADR의 비교 프로토타입 범위를 따른다.

- 정수 픽셀 이동을 하는 플레이어 한 명과 회피 동작
- 일반 적 세 개체와 피격·사망 상태
- 공격 형태 슬롯(근접 찌르기, 근접 원호, 투사체, 지면 범위)과 형태 전환
- 타일 기반 충돌을 가진 고정 배치의 방 하나와 간단한 적 추적
- 체력 UI, 일시정지, 입력 재매핑의 최소 경로
- PixelFX 스프라이트시트를 재생하는 공통 `EffectPlayer`와 타격 시점 알림
- headless 가져오기, 파싱 검사, 스모크 실행

### 2.2 제외

- 세계 구조(층, 승강기, 지역 이동), 정착지, 대화, 성장과 보스 — 전투 방 검증 이후의 범위
- 효과음 — [효과음 도구 후보 ADR](../ADR/2026-11-17-game-sound-effect-tool-candidates.md)의 선택 이후
- 캐릭터·타일 픽셀아트 — 제작 도구 결정 전까지 팔레트 색의 단순 도형을 자리표시자로 쓴다
- 생성 파이프라인(GDD 생성 이후 단계)과의 자동 연결 — 9절 D4에 따라 템플릿 검증 이후
- LÖVE2D 비교 프로토타입 — 평가 ADR이 요구하지만 별도 명세로 다룬다
- Orrery 계산과 개인 출생정보 — 템플릿은 슬롯 입력만 받는다

## 3. 구성

```text
템플릿(커밋, 고정)            슬롯 입력(JSON)          출력 프로젝트(로컬)
  project.godot          ┐
  scenes/*.tscn          │      채우기 도구
  scripts/*.gd           ├──→  (검증 → 복사 → 데이터 기록)  ──→  godot --headless 검사
  assets/effects/        │
  data/*.json (예시값)   ┘
```

- **템플릿**은 그 자체로 열고 실행할 수 있는 Godot 프로젝트다. `data/`에는 합성 예시 입력을 둔다.
- **슬롯 입력**은 하나의 JSON 파일이다. 템플릿의 씬·스크립트는 실행 시 `data/`의 JSON만 읽는다.
- **채우기 도구**는 입력을 검증하고, 템플릿을 출력 위치에 복사한 뒤 `data/`만 입력값으로 바꾼다.
  씬·스크립트·`project.godot`은 수정하지 않는다.
- **출력 프로젝트**는 로컬 생성 결과다. 커밋하지 않으며 `.godot/` 가져오기 캐시는 비교 대상이 아니다.

### 3.1 데이터를 `.tres`가 아니라 JSON으로 두는 이유

`.tres`는 `format=` 헤더, UID와 리소스 경로를 함께 맞춰야 하므로 생성 결과의 결정성과 검증이
어렵다. JSON은 Bun/TypeScript에서 스키마를 검증하고 바이트 단위로 비교할 수 있으며, Godot은
`FileAccess`와 `JSON`으로 읽는다. 대가로 편집기 인스펙터에서 슬롯 값을 바로 고칠 수 없다.
이 선택은 9절 D2로 확정했다.

## 4. 슬롯

모든 길이 단위는 픽셀, 시간 단위는 초다.

| 슬롯 | 내용 | 비고 |
|---|---|---|
| `fingerprint` | 기획서의 `combat-fingerprint` 7개 축 값 | 5절의 지원 범위 판정에만 사용 |
| `player` | 이동 속도, 최대 체력, 회피 거리·시간·무적 구간 | 방어 수단은 v1에서 회피만 |
| `forms` | 공격 형태 1~2개. 각 형태는 `shape`(`thrust`, `arc`, `projectile`, `area`), 사거리, 폭 또는 각도, 피해, 준비·유효·회복 시간, 연타 수, 효과 ID | 2개일 때 전환 가능 |
| `formSwitch` | 전환 시간, 성급한 전환으로 보는 구간, 그때의 공격·회피 지연, 전환 직후 측면 이동 거리 | `forms`가 2개일 때만 |
| `enemies` | 세 개체 각각의 유형(`charger`, `shielder`, `ranged`), 체력, 이동 속도, 전조 시간 | 개체 수는 3으로 고정 |
| `palette` | 자리표시자 도형과 바닥·벽에 쓸 색 램프 | 픽셀아트 도입 시 대체 |
| `labels` | 형태·적의 표시 이름 | 기획서 고유 명칭을 화면에 표시 |

다음 값은 슬롯이 아니라 템플릿에 고정한다. 기준 해상도, 타일 크기, 방 배치, 입력 동작 이름,
카메라. 기준 해상도와 타일 크기는 공통 화면 계약에서 미결정이었으므로 9절 D3으로 320×180, 16px 타일을 고정한다.

## 5. 전투 축 지원 범위

채우기 도구는 `fingerprint`의 각 축 값을 아래 표로 판정한다. **지원하지 않는 값이 하나라도
있으면 출력하기 전에 실패하고, 해당 축과 값을 모두 보고한다.** 가장 가까운 값으로 바꾸지 않는다.

| 축 | v1 지원 | v1 미지원 | 슬롯 대응 |
|---|---|---|---|
| `combatRange` | `close`, `mid`, `long` | — | `forms`의 사거리·`shape` |
| `powerMedium` | `body`, `weapon`, `spell`, `device` | `summon`, `environment` | 표시 이름과 효과만 다르고 같은 공격 슬롯 사용 |
| `initiative` | `direct`, `transform` | `reactive`, `command`, `prepare` | `transform`은 `forms` 2개와 `formSwitch` 필수 |
| `spaceUse` | `pursuit`, `swap` | `fortify`, `expand`, `aerial` | `pursuit`는 회피 거리, `swap`은 전환 직후 측면 이동 |
| `combatRhythm` | 모든 값 | — | 별도 메커니즘 없이 준비·회복 시간과 적 전조로만 반영 |
| `mastery` | `timing`, `aim`, `form_shift` | `resource_combo`, `placement`, `command` | `form_shift`는 `formSwitch` 필수 |
| `risk` | `health`, `focus_break` | `overheat`, `summon_loss`, `terrain_collapse` | `focus_break`는 성급한 전환 지연 |

축 간 일관성도 검사한다. 예를 들어 `initiative: transform`인데 `forms`가 1개이거나,
`spaceUse: swap`인데 `formSwitch`의 측면 이동 거리가 없으면 실패한다.

미지원 값을 지원 범위로 옮기는 것은 별도 변경이다. 지원을 추가할 때는 이 표, 템플릿 스크립트,
수용 사례를 함께 바꾼다.

## 6. 검증

평가 ADR의 성공 기준 1–3을 이 템플릿에서 확인할 수 있는 형태로 구체화한다.

1. **입력 검증 (Bun 테스트)** — 스키마 위반, 알 수 없는 열거값, 미지원 축 값, 축 간 불일치를
   출력 전에 거부하고, 실패한 항목을 모두 보고한다.
2. **결정성** — 같은 입력으로 두 번 채운 출력이 `.godot/`를 제외하고 바이트 단위로 같다.
3. **가져오기** — `godot --headless --path <출력> --import`가 종료 코드 0으로 끝난다.
   엔진 참조 문서에 Windows 4.7.1·4.7.2의 첫 가져오기 크래시 기록이 있으므로, Linux에서 재현
   여부를 기록하고 재시도 정책을 숨기지 않는다.
4. **파싱 검사** — `.claude/vendor/claude-code-game-studios/scripts/godot-parse-check.gd`를
   템플릿에 복사해 모든 `.gd`를 검사한다. `--check-only`는 오토로드를 모르므로 쓰지 않는다.
5. **스모크 실행** — headless 테스트 러너가 슬롯 데이터를 읽어 방을 만들고, 적 3개체·형태 수·
   전환 가능 여부가 입력과 같은지 확인한 뒤 실패 시 0이 아닌 코드로 끝난다.
6. **수동 확인** — 사람이 편집기에서 열어 실행하고 조작, 전조, 타격 가독성을 본다. 자동 검사는
   조작감과 재미를 판정하지 않는다.

## 7. 수용 사례

개인 출생정보나 로컬 생성 결과를 쓰지 않고 합성 입력으로 만든다.

| 사례 | `fingerprint` | 기대 |
|---|---|---|
| 형태 전환형 | `mid`, `weapon`, `transform`, `swap`, `cycle`, `form_shift`, `focus_break` | 출력·검증 통과, 형태 2개와 전환·측면 이동 동작 |
| 단일 형태 원거리형 | `long`, `spell`, `direct`, `pursuit`, `pressure`, `aim`, `health` | 출력·검증 통과, 형태 1개, 전환 없음 |
| 미지원 값 | `close`, `summon`, `command`, `fortify`, `prepare_execute`, `command`, `summon_loss` | 출력 전 실패, 미지원 축 5개를 모두 보고 |
| 축 간 불일치 | 형태 전환형과 같지만 `forms` 1개 | 출력 전 실패, `initiative`·`mastery`와 `forms` 불일치 보고 |

## 8. 구현 순서

```
1. 9절 결정 확정 → 완료 (2026-11-17)
2. 템플릿 Godot 프로젝트와 예시 데이터 작성 → 검증: 6절 3–5를 템플릿 자체에 실행
3. 슬롯 스키마와 지원 범위 판정을 Bun으로 구현 → 검증: 7절 실패 사례 2개의 테스트 통과
4. 채우기 도구(복사 + 데이터 기록) 구현 → 검증: 7절 통과 사례 2개의 출력에 6절 2–5 실행
5. 사람이 출력 프로젝트를 열어 조작 확인 → 검증: 6절 6의 관찰 기록
```

PixelFX 효과 연결은 2단계에 포함하되, 효과 ID가 템플릿의 렌더된 스프라이트시트에 존재하는지는
3단계 검증에서 확인한다.
