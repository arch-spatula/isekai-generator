# Claude 게임 설계 흐름

> 상태: 구현 완료(1~4단계, 2026-11-23). 실제 생성 관찰(8절 5단계) 전
> 작성일: 2026-11-23 (같은 날 Claude 흐름 기준으로 다시 씀)
> 결정: [차트부터 GDD까지 하나의 Claude 흐름으로 만든다](../ADR/2026-11-23-claude-gdd-flow.md)
> 관련: [일생 해석의 게임 번역 규칙](life-to-game-translation.md), [인물과 환경 해석 구분](../ADR/2026-11-10-person-environment-world-story.md), #55

## 1. 목표

`life.md`에서 GDD까지의 게임 단계를 Claude 스킬로 만든다. 기존 Claude 일생 해석 스킬의 방식을 그대로 이어 쓰고, Codex 흐름의 실행 기반은 쓰지 않는다.
Codex 흐름에서는 두 실패만 참고해 구조로 막는다.

- **기호 직역:** 게임 단계는 차트 기호를 보지 않고, 산출물에 차트 명칭이 나오면 검증기가 거부한다.
- **배경 부재:** 체계별 일생 해석이 차트의 환경 자리에서 배경(뿌리·자란 집·떠남의 조건)을 읽고, 통합 해석이 합치고, 번역 브리프가 출신지·성장 환경·가족 구조·떠남의 계기로 옮긴다.
  세계와 GDD는 그 배경에서 출발한다. 처음에는 브리프가 `life.md`에서 배경을 해석하게 했으나 `life.md`에 배경이 없어 성향이 배경 자리에 들어갔다
  (#97, [ADR](../ADR/2026-11-24-chart-background-interpretation.md)).

성공 조건:

- 서로 다른 `life.md`에서 출신지·세계의 성격·동료 구성이 서로 다르게 나온다.
- 게임 단계 산출물 어디에도 차트 명칭이 없다(결정적 검사).
- 일생의 사실에서 왔다고 말하는 요소는 출처를 인용하고, 지어낸 요소는 일생의 사실과 모순되지 않는다(4.2).
- 필수 검증은 합성 fixture로 하며 모델을 호출하지 않는다.

## 2. 흐름의 단위

기존 일생 해석 스킬(`/saju-judgment` … `/life-integration`)의 방식이 이 흐름의 단위다. 게임 단계도 같은 방식으로 만든다.

- **스킬 하나가 파일 하나를 쓴다.** 차트 폴더(`bun scripts/allocate-artifact-path.ts`가 할당한 `chartDir`) 하나에 모든 산출물이 모인다.
- **선행 확인:** 스킬은 시작할 때 `test -e`로 입력 파일을 확인한다. 없으면 만드는 방법(앞 단계 스킬이나 스크립트)을 알리고 멈춘다. 대신 실행하지 않는다.
- **덮어쓰지 않는다:** 산출 파일이 이미 있으면 멈추고 알린다.
- **읽는 파일을 스킬이 정한다:** 스킬 본문에 읽을 파일을 적고, 그 밖의 파일은 읽지 않는다.
- **검증:** 쓰고 나서 `bun scripts/check-<단계>.ts <디렉터리>`를 실행한다. 위반 줄만 고쳐 다시 실행하고, 3번 고쳐도 통과하지 못하면 멈추고 남은 위반을 알린다.
  검증을 통과시키려고 판단을 바꾸지 않는다.
- **검토:** 정체성·전투·세계는 검증 뒤 다른 에이전트가 검토한다(4.7). 검토 문서는 단계마다 `<단계>-review-1.md` 하나다(#100).
- **보고:** 파일 경로와 핵심 결정 몇 줄만 알린다. 본문을 다시 옮겨 쓰지 않는다.

진행 상태는 차트 폴더에 어떤 파일이 있고 검증기를 통과하는지가 전부다. 어느 단계가 멈추거나 실패해도 새 버전 폴더를 만들어 처음부터 다시 생성하지 않고, 멈춘 단계와 남은 위반을 알린다(#100, 전체 재생성 비용 사고는 2026-11-12 인시던트). 상태 DB, 단계표 명령, 시도 폴더, 게시, 방어 편집 단계, `run.md`는 두지 않는다.
다음에 할 일은 각 스킬의 선행 확인이 알려 준다.

| 순서 | 스킬·스크립트 | 쓰는 파일 | 읽는 파일 | 검증 |
| --- | --- | --- | --- | --- |
| 1 | `/chart-report` | `<체계>-chart.md`, `<체계>-facts.md` | 출생 입력 | — |
| 2 | `/<체계>-judgment` | `<체계>-judgment.md` | 자기 체계 차트·사실 | `check-<체계>-judgment` |
| 3 | `derive-judgment-facts.ts` | `saju·ziwei-derived-facts.md` | 차트·판단 | 스크립트가 계산 |
| 4 | `/<체계>-life` | `<체계>-life.md` | 자기 체계 차트·사실·판단·파생 사실 | `check-life-document` |
| 5 | `assemble-life-material.ts` | `life-material.md` | 세 일생 해석 | 스크립트가 조립 |
| 6 | `/life-integration` | `life.md` | 재료표 | `check-life-integration` |
| 7 | `/translate-life` | `translation-brief.md` | `life.md`, 동료 후보 계산 결과 | `check-translation-brief` |
| 8 | `/design-identity` | `identity.md` | 번역 브리프 | `check-identity`, 검토(4.7) |
| 9 | `/design-world` | `world.md` | 번역 브리프, `identity.md` | `check-world`, 검토(4.7) |
| 10 | `/design-combat` | `combat.md` | 번역 브리프, `identity.md`, `world.md` | `check-combat`, 검토(4.7) |
| 11 | `/write-gdd` | `gdd.md` | 번역 브리프, `identity.md`, `combat.md`, `world.md` | `check-gdd` |

1~6은 이미 있다. 7·9~11은 2026-11-23에, 8(이세계 정체성)은 2026-11-24에 더했다(#86, [ADR](../ADR/2026-11-24-isekai-identity-design.md)).
2026-11-25에 세계를 전투보다 앞으로 옮겼다. 전투가 세계보다 먼저 적을 정해 어느 세계에나 붙일 수 있는 적이 나왔기 때문이다([재료 부족 정리 ADR](../ADR/2026-11-25-material-gaps.md)).

## 3. 입력 격리

- `/translate-life`는 `life.md`만 읽는다. 차트·사실·1차 판단·파생 사실·체계별 일생 해석·재료표는 읽지 않는다. 동료 후보는 스크립트가 `life.md`에서 계산해 넘긴다.
- `/design-identity`·`/design-combat`·`/design-world`·`/write-gdd`는 `life.md` 원문도 읽지 않고 번역 브리프와 앞 단계 산출물만 읽는다. 번역 규칙을 브리프 한곳에 모으기 위해서다
  ([게임 번역 명세](life-to-game-translation.md) 6절).
- 어떤 스킬도 다른 버전 폴더를 읽지 않는다.

## 4. 공통 규칙

### 4.1 기호 명칭 금지

게임 단계 산출물(번역 브리프, `identity.md`, `combat.md`, `world.md`, `gdd.md`)에 차트 명칭이 나오면 거부한다. 이 검사는 마지막 안전망이다. 첫 방어는 입력 격리(3절)이고,
기호의 뜻을 명사로 직역하는 실패(재물의 별 → 장부 도시)는 이름 검사로 잡을 수 없으므로 해석 경로 인용과 의미 검토가 막는다. 그래서 오탐이 없는 좁은 목록만 쓴다.
오탐은 모델이 괜찮은 문장을 검증 통과를 위해 고치게 만든다.

| 구분 | 대상 | 처리 |
| --- | --- | --- |
| 한자 표기 | 별·궁·십신·신살·천간·지지의 한자 이름 전체(예: 武曲, 命宮, 偏財, 天乙貴人) | 거부 |
| 고유한 한글 독음 | 두 글자 이상이고 일상어와 겹치지 않는 독음(예: 무곡, 탐랑, 칠살, 겁재, 식신, 도화살) | 거부 |
| 차트 문법 | 궁 이름에 `궁`이 붙은 형태(예: 천이궁), 열두 사인의 `○○자리`, `제○하우스`, 운의 한자 표기(大運·大限) | 거부 |
| 일상어와 겹치는 말 | 한 글자 이름, 일상어와 겹치는 독음(예: 달, 태양, 화성, 상관, 비견, 정인, 편재, 명궁(이름난 궁수), 천기, 천부), 대운·대한 | 검사하지 않음 |

- 목록은 계산기 상수에서 만들고(`scripts/chart-names.ts`), 일상어와 겹쳐 빼는 말은 손으로 관리하는 제외 목록에 둔다. 자미두수 별·궁의 한글 독음은
  상수에 없어 손으로 둔 독음표를 쓴다.
- 허용 문장(예: "달이 뜬 밤", "상관없다")을 fixture에 두어 오탐이 다시 생기지 않게 고정한다.

### 4.2 출처와 지어낸 요소

번역 브리프는 `life.md`를 옮기는 단계라 요소마다 `[life:<항목>]`을 인용한다. 정체성·세계 단계는 이세계를 지어내는 단계라 요소마다 인용하지 않는다(#87,
[ADR](../ADR/2026-11-24-isekai-identity-design.md) 4번). 일생의 사실에서 왔다고 말하는 요소와 앞 단계와의 연결(클래스의 재료, 출신지의 배경, 장별 세계의 장,
첫 지역의 출신지, 전장의 전투, 서사 갈등의 축·반복되는 실패)만 `[brief:]`·`[identity:]`·`[combat:]`·`[world:]`로 인용한다.
지어낸 요소에는 근거 줄을 쓰지 않으며, 이전의 `창작:` 표시는 없앴다. 요소마다 인용을 요구하자 옮겨 적기가 가장 안전한 선택이 됐기 때문이다(#81).

경계는 세 가지다: 일생의 사실과 모순되지 않는다, 기호를 직역하지 않는다, 주인공의 재능·성향을 장소 이름이나 성격으로 옮기지 않는다.
차트 명칭(4.1)·필수 절과 형식·인용 대상 실재는 검증기가 보고, 모순과 투영은 의미 판단이라 검토 단계(#72)가 본다.

### 4.3 장르 성격

[ADR](../ADR/2026-11-23-claude-gdd-flow.md) 5번을 따른다. 픽셀 그래픽, 빠른 실시간 액션, 로그라이트(런 반복, 런 중 보상 선택, 런 밖 성장)를 유지하고,
칸 배치 인벤토리·인접 칸 시너지·장비 슬롯 연결·슬롯 퍼즐은 쓰지 않는다. 화면 시점·해상도·아트 규격은 고정하지 않는다. 검증기는 제외 메커니즘의 용어가
시스템 설명에 쓰였는지 확인하되, 의미 판단은 의미 검토로 한다.

### 4.4 다른 run과의 반복 — 관찰 후 결정

Codex 흐름에서는 서로 다른 명식이 같은 모티프로 수렴했다. 붙들기·연결·거리 조절·이동을 한 번에 설명하는 사슬,
고립·연결·이동·거점을 한 번에 설명하는 바다와 군도처럼 적은 말로 많은 기능을 설명하는 이미지가 반복해서 선택됐다
([전투 원형 수렴](../incidents/2026-11-03-combat-archetype-convergence.md), [해양 세계관 수렴](../incidents/2026-11-04-maritime-world-setting-convergence.md)).
수렴은 run 하나만 봐서는 보이지 않고, 그럴듯한 근거는 거의 누구의 재능에서나 댈 수 있으므로 run 안의 검사로는 막지 못한다.

Claude 흐름에서도 같은 수렴이 일어나는지는 확인되지 않았다. 당시 입력은 구체적인 사건이 없는 추상적 통합 해석이었고, Claude 흐름의 입력은 출신지·떠남의
계기·관계 상태·생애 단계별 사건을 담은 `life.md`와 번역 브리프다. 알려진 원인 하나(지침 단어가 결과로 새는 것)는 4.5가 근본에서 막는다.
그래서 run 사이 비교 장치는 지금 만들지 않고, 8절 5단계 관찰에서 수렴이 보이면 그때 비교 기준과 비교 데이터의 위치를 정한다.

### 4.5 지침의 단어가 결과에 새지 않게 하기

스킬 지침·템플릿·필드 이름·예시에 구체적인 사물 이미지(사슬, 닻, 항로, 불씨, 원 등)를 쓰지 않는다. 지침의 단어는 그대로 결과물의 모티프로 새어 나온다.
예를 들어 전투 설계의 일반 동사 `anchor`·`route`가 GDD에서 닻·항로·군도로 번졌다([해양 세계관 수렴](../incidents/2026-11-04-maritime-world-setting-convergence.md)).
필드 이름은 기능을 나타내는 추상어로 쓰고(예: `경로`, `근거`), 예시는 합성 사례를 여러 갈래로 두거나 결과물에 쓰일 수 없는 형식으로 쓴다.

### 4.6 지침에 목표를 적는다

정체성·전투·세계·GDD 스킬은 금지 목록 앞에 `## 목표` 절을 둔다(#87, [ADR](../ADR/2026-11-24-isekai-identity-design.md) 3번). 금지 목록만 있으면
검증 통과가 곧 완료가 되고, 모델은 목표가 아니라 규칙을 형식으로 채운다(#81). 목표는 세 가지다.

- 주인공의 성향은 장소의 성격이 아니라 장소와 부딪치는 갈등이 된다.
- 장소는 주인공 없이도 왜 그렇게 돌아가는지 설명되는 곳이다. 권력·역사는 스토리에 필요한 곳에만 정한다(#121).
- 그 사람다움은 클래스와 부직업의 조합에서 나온다(#120).

스킬마다 그 단계에 해당하는 목표를 적는다. 목표는 의미 판단이라 검증기가 아니라 검토 단계(#72)가 본다.

### 4.7 검토 단계

정체성·전투·세계 단계는 검증기를 통과한 뒤, 작성 에이전트와 다른 에이전트가 검토한다(#72, [ADR](../ADR/2026-11-24-isekai-identity-design.md) 5번).
거의 모든 단계가 첫 작성에서 검증을 통과했고 검증 통과가 곧 완료였다. 검증기는 형식·인용·이름만 보므로, 목표(4.6)와 경계(4.2)는 검토가 본다.

- **검토자:** `.claude/agents/game-step-reviewer.md`. 작성 스킬이 Agent 도구로 부르고, 프롬프트에는 차트 디렉터리와 단계 이름만 넣는다.
  검토자는 작성자와 같은 입력과 산출물만 읽고, 작성자의 판단 과정은 받지 않는다. 같은 에이전트의 두 번째 패스는 자기 판단을 근거로 통과시키기 쉬워 쓰지 않는다.
- **기준:** 재해석·투영·이세계다움·모순·직역, 정체성·전투는 비교(제외 이유가 성격·동료 유무·"주 재능 아님"인지, 정체성은 이세계의 힘이 현실 직업의 동작에 머무는지, 전투는 후보가 같은 네 자리를 채우는지)를 더한다.
  기준은 #65~#71과 #81에서 사람이 잡아낸 문제에서 나왔다. 문장 다듬기·취향·형식은 지적하지 않는다.
- **산출물:** `<단계>-review-1.md`(`## 판정`에 대상·판정, `## 지적`에 지적마다 위치·기준·내용·고칠 방향). `bun scripts/check-review.ts <파일>`이
  판정 값, 판정과 필수 지적(모순·직역)의 유무가 맞는지, 위치가 대상 문서의 제목인지, 기준 값, 파일 번호가 1인지(두 번째 검토 거부)를 확인한다. 판정의 타당성은 검사하지 않는다.
  고칠 방향에는 구체적인 이름을 주지 않는다(4.5와 같은 이유).
- **한 번만 검토한다(#100, [ADR](../ADR/2026-11-25-single-pass-review.md)):** 검토자는 걸리는 곳을 한 번에 모두 적는다. 모순·직역은 필수라 하나라도 있으면 되돌림이고,
  재해석·투영·이세계다움·비교는 권고라 권고만 있으면 통과다. 작성자는 필수를 반드시, 권고는 다른 곳이 어긋나지 않는 한 한 번에 고치고 검증기를 통과시킨 뒤 끝낸다.
  다시 검토하지 않는다. 이전에는 최대 3번 되돌렸으나 거의 모든 단계가 3번까지 갔고, 반복 지적의 대부분은 재료 없는 요구에서 나왔다(ADR 결정 3의 표).
- 다른 run과 구별되는지는 보지 않는다. 다른 버전 폴더를 읽지 않는 규칙 때문이다(9절 1번).

## 5. 단계별 계약

### 5.1 `/translate-life` — 번역 브리프

[게임 번역 명세](life-to-game-translation.md) 3~5절을 따른다. 주인공(축·반복되는 실패), 주인공 능력(재능 재료), 생업, 동료(스크립트가 계산한 후보에서만),
배경 네 항목(환경에 관한 사실과 그것이 남긴 행동·감정), 장(모험이 걸친 생애 단계의 사건·고민·시련), 갈림길(`life.md`의 갈림길 전부, #109), 동기와 퀘스트, 옮기지 않은 인물을 쓴다. 세계·GDD는 `life.md`를 읽지 않으므로 그 단계가 쓸 재료를 브리프가 모두 옮긴다.

### 5.2 `/design-combat` — 전투

- 정체성(5.5)의 클래스 안에서, 클래스 `재료`에 있는 주인공 능력을 출처로 서로 다른 전투 방식 후보 네 개를 만들고 비교해 하나를 고른다(#86, 검증기가 확인). 후보마다 출처 재능을 인용하고, 고르지 않은 후보는
  고르지 않은 이유를 한 줄로 남긴다.
- **후보는 재능의 `다루는 것`에서 먼저 만들고 축은 나중에 붙인다(#75).** 후보마다 `조작하는 것`(출처 능력의 `다루는 것`에서 나온, 전투에서 실제로 다루는 것),
  `플레이`, `혼자일 때`를 쓰고 축 값은 그 뒤 분류용으로 붙인다. 축 목록을 메뉴처럼 먼저 보여 주면 후보가 매번 같은 네 자리(근접 타격·반격·설치·소환 지휘)를
  채운다([전투 방식 수렴](../incidents/2026-11-24-claude-combat-style-convergence.md)).
- **재능 전체를 놓고 고른다(#82).** 주 재능에서 나온 후보를 우선하지 않는다. #75에서 둔 "채택은 주 재능 출처" 규칙은, 능력마다 후보를 하나씩 만드는 습관과
  겹쳐 비교 전에 채택을 정해 버려서 없앴다. 성격 묘사로 고르거나 떨어뜨리지 않고, 성격은 위험 구조와 약점에 쓴다.
- **능력마다 하나씩 만들지 않는다(#82).** 같은 능력의 다루는 것을 다르게 해석한 후보가 적어도 둘 있어야 한다(검증기가 확인).
- **지휘와 보호는 여러 갈래다(#82).** 지휘는 공적인 지휘·관리(스스로 싸우는 병력을 불러 진형을 짜고 불러들이거나 돌격시킴)를 포함한다.
  보호는 회복, 체력·물리·마법 방어 강화, 큰 방패로 막아서기, 곁을 지키는 사역마처럼 방식에 따라 조작이 다르다.
- **동료 유무로 떨어뜨리지 않는다.** 기본 전투는 동료 없이 성립해야 하며, 모든 후보가 `혼자일 때`로 이를 보인다. 소환·지휘형도 혼자 버전으로 성립할 수 있다.
- 동료가 있으면 `동료의 행동`에 동료가 전투에서 스스로 하는 일을 쓴다. 브리프의 `함께 하는 일`에서만 만들고, 플레이어가 쓰는 기술로 만들지 않는다(#71).
- 후보마다 [전투 원형 ADR](../ADR/2026-11-03-personalized-combat-archetype-selection.md) 2.1의 일곱 축에 허용값 하나씩을 선언하고, 어느 두 후보를 골라도
  세 축 이상 달라야 한다(같은 ADR 2.2). 이름과 외형만 바꾼 후보를 막는다.
- 채택한 방식은 `전투 방식`에 핵심 행동, 약점, 적, 런 한 번, 런 중 보상, 런 밖 성장으로 구체화한다. 약점과 런 밖 성장은 브리프의 능력을 인용한다.
- **끌림**은 브리프의 반복되는 실패를 위험과 보상의 구조로 옮긴 플레이 시스템이다(#112, [ADR](../ADR/2026-11-26-draw-system-and-player-names.md)). 쌓는 행동, 보상, 대가, 기록, 극복을 쓰고,
  **장별 끌림**에 브리프의 장마다 그 시기의 의미를 쓴다. 플레이어용 이름은 장르 어휘로 짓는다(#114).

### 5.3 `/design-world` — 세계

- 정체성(5.5)의 출신지를 첫 지역으로 두고(검증기가 확인), 장마다 정체성의 장별 세계를 무대로 그 시기의 사건이 일어나는 지역을 만든다(#86).
  떠난 뒤의 장은 출신지 안의 구역으로 잇지 않고 그 장의 무대에서 지역을 만든다(#121).
- 세력·공동체는 자체 목적과 제약을 가진다. 주인공의 `반복되는 실패`·`축`은 세계의 성격이 아니라 그 세계와 부딪치는 서사 갈등으로 쓴다.
- 전투 방식이 쓰이는 공간(지형, 적, 런 한 번의 길이)은 `combat.md`와 맞춘다.
- 후보 비교는 요구하지 않는다.
- 산출물은 지역(장·성격·사정, 전장과 근거는 선택), 세력(목적·제약·주인공과의 관계, 근거는 선택), 서사 갈등(내용·근거)이다. 첫 지역은 브리프의 첫 장이고
  근거에 출신지를 인용한다. 장마다 전장이 있는 지역이 하나 이상 있다. 싸울 일이 없는 지역에는 전장을 두지 않고, 적은 세력이 아니라 장르의 적이어도 된다(#121). 서사 갈등 전체에서 축과 반복되는 실패를 모두 인용한다. 근거를 쓰면 브리프나 정체성을 인용한다(4.2).

### 5.4 `/write-gdd` — GDD

절은 브리프와 앞 단계가 넘기는 것을 그대로 따른다. 이전 Codex 템플릿을 이어받지 않는다.

1. **게임 개요:** 한 문단. 장르 성격(4.3)과 주인공이 무엇을 하는 게임인지.
2. **주인공:** 배경(출신지·성장 환경·가족 구조·떠남의 계기), 정체성의 클래스와 모든 부직업, 동기.
3. **동료:** 동료마다 합류하는 장과 함께 하는 일. 동료가 없으면 혼자 모험하는 이유를 쓴다.
4. **세계와 장:** 장마다 지역, 세력, 그 장의 퀘스트. 부직업의 의뢰도 퀘스트가 된다(#120).
5. **전투:** 고른 전투 방식, 동료가 스스로 하는 일, 적의 성격.
6. **런과 성장:** 런 한 번의 흐름, 런 중 보상, 런 밖 성장. 성장의 출처는 재능이다.
7. **서사의 변화:** 관계가 장마다 어떻게 바뀌는지, 갈림길.
8. **대표 장면:** 한 번의 런을 처음부터 끝까지 따라가는 장면 하나.
9. **크레딧:** 클래스와 끌림의 플레이어용 이름마다 설계용 이름과 출처(#114).

- 근거는 `[brief:…]`·`[combat:…]`·`[world:…]`로 인용한다.
- 분량 모드(light·deep)는 두지 않는다.
- 본문은 문단으로 쓴다. `동료`는 브리프의 동료마다 `###` 항목을 두고(동료가 없으면 항목 없이 혼자인 이유), `세계와 장`은 브리프의 장마다 `###` 항목을 순서대로 둔다.
- 절마다 인용이 있다. 주인공은 배경 네 항목을, 각 장은 세계 설계에서 그 장으로 정한 지역을, 전투는 전투 설계를, 런과 성장은 전투 설계와 브리프의 능력을,
  서사의 변화는 브리프의 퀘스트나 세계의 서사 갈등을 인용한다. 런과 성장은 전투 설계의 끌림을, 크레딧의 각 항목은 그 설계 항목을 인용한다.
  `의뢰`가 있는 부직업은 세계와 장이나 런과 성장에서 인용한다(#120).

### 5.5 `/design-identity` — 이세계 정체성

흐름에서는 5.1과 5.2 사이에 온다(#86, [ADR](../ADR/2026-11-24-isekai-identity-design.md) 2번). 앞 단계가 모두 옮겨 적기에 최적화돼 있어,
클래스·출신지·그 시대의 세계를 지어내는 일이 어느 단계에도 없었다. 이 단계는 번역이 아니라 설계다.

- 번역 브리프만 읽고 `identity.md`에 클래스·부직업·출신지·장별 세계를 쓴다. 일생의 사실과 모순되지 않는 범위에서 구체적인 이세계를 지어내는 것을 허용한다.
- **클래스 후보**는 클래스를 정하기 전에 견주는 세 후보다([ADR](../ADR/2026-11-25-class-candidates.md)). 후보마다 능력의 `다루는 것`을 현실 명사가 아니라 기능(`영역`)으로 올리고,
  그 기능이 이세계에서 무엇이 되는지(`이세계의 힘`)를 쓴 뒤 하나를 채택한다. 브리프의 `다루는 것`은 현실 명사라, 이 단계 없이는 현실 직업의 동작이
  클래스와 전투까지 그대로 내려갔다("이세계 회계사", #106). 옮김이 이세계다운지는 검토(4.7 비교)가 본다.
  후보는 핵심 동작이 분명한지와, 남는 갈래(부직업·동료·퀘스트)와 함께 이 사람의 조합을 이루는지로 고른다(#120). 재능을 한 동작에 많이 담는지로 고르면
  재능을 억지로 합친 클래스와 흔한 직업을 감춘 이름이 나왔다. 전장 직접성 하나로 고르면 재료를 무기로 바꾸는 힘이 이기고 사람·조직 갈래가 빠졌다(#110).
  제외한 후보에는 그 갈래가 남는 자리(`남는 곳`)를 쓴다.
- **클래스**는 이세계에서 무엇으로 싸우고 어떻게 불리는가다. 재능 전체를 놓고 조합으로 정하고, 브리프 능력의 순서(주·보조)를 따르지 않는다.
  `재료`에 주인공 능력이 하나 이상 있어야 하고, 항목 이름은 채택한 후보이며, 브리프의 생업 이름을 그대로 클래스 이름으로 쓰면 거부한다.
- **부직업**은 싸움 밖에서 하는 일이다. 브리프의 생업이나 능력을 재료로 하고, 하나 이상 둔다. 생업은 클래스로 1:1 옮기지 않고 부직업·출신지의 재료가 된다.
  그 사람다움은 클래스 하나가 아니라 클래스와 부직업의 조합에서 나온다. 부직업 이름은 장르에서 흔한 직업 이름이어도 된다.
  선택 필드 `의뢰`는 그 일로 들어오는 퀘스트이며 GDD가 쓴다([ADR](../ADR/2026-11-26-genre-names-and-sub-jobs.md), #120).
- **출신지**는 형태·생활·주인공의 자리를 쓴다([ADR](../ADR/2026-11-26-open-origin.md), #121). 형태는 도시로 정해져 있지 않고(마을·배·유목 무리·대상 등), 형태는 브리프 배경의 `터전`·`가세`에서 정하고(`근거`에 `[brief:출신지]`), 생활은 그 터전에 맞게 지어내며, 주인공의 성향·능력·생업에서 끌어내지 않는다. 출신지의 생활을 주인공의 능력·생업과 같은 영역으로 짓지 않는다(#122).
  예전에는 `출신 도시`에 산업·권력·역사를 정하게 했는데, 이 설정이 장별 세계·지역·세력·적까지 한 도시의 정치로 묶었다. 권력·역사는 이 단계에서 정하지 않는다.
  브리프 배경의 경로 셋째 단계(장소·공동체의 성격)와 `장소의 사정`은 없앴다. 그 단계가 주인공의 행동·감정에서 장소의 성격을 끌어내 투영을 만들었다.
- **장별 세계**는 브리프의 장마다 그 시기 주인공이 놓인 무대다. 떠나기 전의 장은 출신지의 생활에서, 떠난 뒤의 장은 그 장의 이동과 생활에서 정한다. 항목은 브리프의 장과 같은 순서이고 `근거`에 그 장을 인용한다.
- 뒤 단계는 이것을 입력으로 받는다. 전투는 클래스 안에서 후보를 만들고(5.2), 세계는 출신지에서 시작하며(5.3), GDD 주인공 절은 클래스·부직업을 인용한다(5.4).

| 배경 네 항목과 두 단계 경로, 생업 항목 | 번역 브리프 |
| 클래스 후보 세 개와 채택 하나, 제외한 후보의 남는 곳 형식, 클래스는 채택한 후보, 클래스·출신지는 하나씩, 출신지는 형태·생활·주인공의 자리, 부직업은 하나 이상이고 의뢰는 선택, 클래스 재료에 능력과 플레이어용 이름, 생업 이름 직역 금지, 장별 세계와 브리프의 장 일치 | 정체성 |
| 동료 후보 일치·동행 장 범위 | 번역 브리프 |
| 후보 네 개, 출처 재능 인용, 출처가 클래스 재료 안, 끌림 하나와 반복되는 실패 인용, 장별 끌림과 브리프의 장 일치, 적의 세력·지역 인용 | 전투 |
| 장마다 지역 하나 이상과 전장이 있는 지역 하나 이상, 첫 지역의 출신지 인용, 서사 갈등의 축·반복되는 실패 인용 | 세계 |
| 주인공의 모든 부직업 인용, 의뢰가 있는 부직업 인용, 런과 성장의 끌림 인용, 크레딧의 플레이어용 이름 항목과 설계 항목 인용 | GDD |
| 제외 메커니즘 용어 | 전투·GDD |

합성 fixture로 정상 사례와 거부 사례를 둔다. 거부 사례에는 **기호 직역**(예: 출신지를 재물의 별에서 장부 도시로 만든 설정), 근거 없는 배경, 후보가 아닌
동료, 제외 메커니즘을 넣는다. 의미 품질(배경이 설득력 있는가,
세계가 주인공과 구별되는 논리를 가지는가)은 의미 검토 체크리스트로 본다.

## 7. Codex 기반 제거

Codex는 GDD를 쓰지 않는다. Claude 흐름은 Codex 기반에 의존하지 않으므로(버전 폴더 이름의 `activeSeries` 하나만 읽는다) 게임 단계 구현과 별개로 먼저 지운다.

| 대상 | 처리 |
| --- | --- |
| `.agents/skills/`의 Codex 생성 스킬(차트 실행·체계별 해석·통합 해석·방어 편집·전투·세계·GDD 생성)과 그 스크립트·테스트 | 지운다 |
| `scripts/artifacts/`, `scripts/artifact-*.ts`(상태·할당·시도·입력·편집·게시·지문 명령) | 지운다 |
| `scripts/promote-artifact-series.ts`, `scripts/game-presentation.ts`와 테스트·fixture | 지운다. `activeSeries`는 결정 기록과 함께 손으로 바꾼다 |
| Codex 스킬이 쓰던 `docs/prompts/`·`docs/spec/`·`docs/GDD/` 문서 | `docs/legacy/`로 옮기고 남는 문서의 링크를 고친다 |
| ADR·인시던트 | 그대로 둔다. 실수의 기록이다 |
| `.agents/skills/implement-with-test-review`, `.agents/artifact-series.json` | 남긴다. GDD 생성과 무관하거나 Claude 흐름이 쓴다 |

`scripts/check-document-artifacts.test.ts`가 `scripts/artifacts/test-fixtures.ts`의 저장소 fixture를 쓰므로, 지울 때 필요한 부분을 테스트 안으로 옮긴다.

## 8. 구현 순서

1. **Codex 기반 제거(7절, 2026-11-23 완료):** 지운 뒤 `bun run test`와 `bun run check:docs`가 통과한다.
2. **번역 브리프(2026-11-23 구현):** 동료 후보 계산 스크립트, 차트 명칭 목록과 검사, `check-translation-brief`, `/translate-life` 스킬.
3. **전투·세계(2026-11-23 구현):** `check-combat`·`check-world`, `/design-combat`·`/design-world` 스킬. 세계 단계에 필요한 장별 사건과 주인공의 축·반복되는 실패를
   번역 브리프의 `장`·`주인공` 절로 옮겼다.
4. **GDD(2026-11-23 구현):** `check-gdd`, `/write-gdd` 스킬.
5. **실제 생성 관찰:** 서로 다른 명식 2~3개로 끝까지 생성해 배경·세계·동료가 명식에 따라 갈리고 기호 직역과 모티프 반복이 없는지 본다.
   모티프가 수렴하면 run 사이 비교 장치를 결정한다(4.4).
