# ADR: 실행 상태 저장소를 없애고 진행 상태를 버전 폴더의 파일에서 계산한다

* **Status:** Accepted — 구현 완료(2026-11-23)
* **Date:** 2026-11-21
* **Decision Owners:** Project Owner
* **Supersedes:** [SQLite와 목적별 CLI ADR](2026-11-12-sqlite-agent-state-evaluation.md),
  [버전 폴더별 SQLite ADR](2026-11-21-per-version-sqlite-state.md)

## 결정

생성 실행의 상태 저장소로 SQLite를 쓰지 않는다. 아티팩트 루트에도, 버전 폴더에도 DB를 두지 않는다.

에이전트가 어디까지 작업했고 토큰이 떨어진 뒤 어디서 이어 가야 하는지는 **버전 폴더 안의 파일과 검증기로 계산**한다.
별도의 진행 기록을 원본으로 두지 않는다.

| 알고 싶은 것 | 원본 |
| --- | --- |
| 어느 단계가 끝났고 다음은 무엇인가 | 고정된 단계표 + 산출 파일의 존재 + 검증기 통과 여부 |
| 몇 번 시도했고 왜 실패했나 | 버전 폴더 `garbage/` 아래 시도별 폴더와 그 안의 진단 파일 |
| 다른 run과 전투·세계 지문이 얼마나 가까운가 | 다른 버전 폴더에 게시된 전투·세계 브리프의 지문 블록 |

- **단계표**는 코드 한 곳에 정의한다. 단계마다 산출 파일, 선행 단계, 완료 판정(검증기 또는 결정적 재계산 비교),
  비어 있을 때 실행할 스킬·스크립트를 둔다.
- **상태 명령**은 읽기 전용이다. 버전 폴더를 받아 단계마다 `완료 · 수리 필요(파일은 있으나 검증 실패) · 실행 가능 · 대기`를
  계산하고 다음 행동을 돌려준다. 병렬로 진행할 수 있는 단계는 함께 돌려준다.
- 스크립트가 만드는 결정적 산출물은 다시 계산한 결과와 비교해 앞 단계 변경을 감지한다.
- 이전 SQLite 전환 전의 JSON/JSONL 상태 파일(실행 manifest, 이벤트 로그, 단계 checkpoint, 시도별 입력·결과·채택 JSON)로
  돌아가지 않는다. 계산할 수 있는 상태는 기록하지 않는다.
- 예외는 한 번 쓰고 고치지 않는 입력이다. 실행 설정(`run.md`)과 전투·세계 선택 시도의 지문 레지스트리 스냅샷(`registry.json`)이
  여기에 해당한다. 진행 상태가 아니므로 실제 파일과 어긋날 일이 없다(2026-11-23 보완).

## 이유

SQLite만이 해 줄 수 있는 일이 없었다.

- **진행 위치:** 단계마다 산출 파일과 결정적 검증기가 있으므로 계산할 수 있다. 계산 결과는 실제 파일에서 나오므로
  기록과 실제가 어긋나지 않는다.
- **토큰 소진 시점에 기록은 약하다.** 작업 도중 컨텍스트가 끝나면 DB의 마지막 기록이 실제 파일보다 한 걸음 늦는다.
  재개할 때 결국 파일을 다시 확인해 맞춰야 하며, 이를 위해 `reconcile`, 게시 복구, claim 같은 장치가 필요해졌다.
  원본이 파일 하나면 이 장치들이 필요 없다.
- **시도·진단:** 시도별 Markdown은 이미 `garbage/` 아래 시도 폴더에 쌓인다. 횟수는 폴더 수로, 실패 이유는 진단 파일로 남긴다.
- **run 간 지문:** 지문은 게시된 브리프에 이미 들어 있어 다른 버전 폴더에서 읽어 계산할 수 있다.
- **실행 중인 외부 에이전트의 생존 여부:** DB로도 증명할 수 없다. 이전 명세도 이 한계를 인정했다. 이 확인은
  오케스트레이터가 실제 에이전트 상태를 조회해 판단한다.

## 결과

- 실행 사이에 공유하는 저장소가 없으므로 run 간 동시성, 공용 카운터, 첫 초기화 경합, `registry-stale` 재확인이 없다.
- 버전 번호는 활성 series의 버전 폴더를 배타적으로 생성해 확정한다(이미 있으면 다음 번호).
- 한 버전 폴더만으로 그 실행을 이해하고 이어 갈 수 있다.
- 검증기가 확인하지 않는 것(의미 품질, LLM이 쓴 문서가 앞 단계 변경 후 낡았는지)은 상태 명령으로 알 수 없다. 앞 단계 변경
  감지가 필요해지면 산출 문서에 입력 파일 해시를 함께 남기는 방식을 별도로 결정한다.

## 구현 상태

2026-11-23에 [SQLite 제거 명세](../spec/remove-sqlite-state.md)의 다섯 단계로 구현을 마쳤다. 상태 저장 계층, `artifact-state.ts`,
`read-artifact-state.ts`와 SQLite 전용 테스트는 삭제되었고, 생성 스킬은 상태·시도·입력·편집 판정·지문·게시 명령을 쓴다. 저장소에서
`bun:sqlite`를 import하는 코드는 없다.
