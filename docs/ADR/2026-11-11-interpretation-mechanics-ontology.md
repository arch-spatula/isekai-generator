# ADR: 해석과 게임 메커니즘의 복수 번역 온톨로지 도입

* **Status:** Accepted — 구현 미반영
* **Date:** 2026-11-11
* **Decision Owners:** Project Owner
* **Scope:** 통합 해석에서 전투·성장·위험 메커니즘 후보를 만드는 선택 하네스

---

# 1. Context

현재 전투 콘셉트 선택은 통합 해석에서 전투 거리, 힘의 매개체, 공간 활용, 전투 리듬과
숙련 방식 같은 축을 추출한다. 이 구조는 후보의 외형만 바꾸는 수렴을 줄였지만, 하나의
해석 경향을 너무 일찍 하나의 축 값으로 확정할 수 있다. 예를 들어 빠른 개입은 직접 공격,
추격, 공격 가로채기, 경로 단축이나 의사결정 시간 압축으로 각각 번역할 수 있다. 그러나
첫 번역이 배치와 영역 확장으로 고정되면 이후 후보도 설치물과 연결선 중심으로 수렴하기
쉽다.

해석 문구와 게임 직업을 일대일 대응하는 클래스 표는 이 문제를 해결하지 못한다. 필요한
것은 정답 사전이 아니라 한 해석 개념이 여러 상호작용으로 분기될 수 있고, 한 메커니즘도
여러 해석 개념을 표현할 수 있다는 관계를 명시하는 작은 탐색 어휘다.

# 2. Decision

해석 개념과 게임 메커니즘 사이의 **복수 번역 온톨로지**를 저장소에 버전 관리되는 YAML로
도입한다. 온톨로지는 특정 능력이나 최종 후보를 정답으로 지정하지 않고, 후보 생성기가
검토해야 할 가능한 번역 경로를 제공한다.

초기 관계는 다음 세 가지로 제한한다.

- `canTranslateTo`: 해석 개념이 표현될 수 있는 메커니즘 목록
- `expresses`: 메커니즘이 플레이 중 표현하는 해석 개념 목록
- `tensionsWith`: 함께 사용할 때 선택·비용·갈등을 만드는 개념 관계

초기 구현이 관계 방향을 중복 저장해야 하는지는 상세 spec에서 정한다. 동일 관계를 두
필드에 복사해 불일치가 생기지 않도록 하나를 원본으로 정하고 역방향 조회는 도구가 만들
수 있다.

예시 스키마는 다음과 같다. 아래 값은 형식 설명을 위한 합성 예시이며 고정 답안이 아니다.

```yaml
schemaVersion: 1
interpretationConcepts:
  rapid-intervention:
    canTranslateTo:
      - pursuit
      - interception
      - initiative-compression
    tensionsWith:
      - shared-burden
      - recovery-need
mechanics:
  interception:
    expresses:
      - rapid-intervention
      - protection
```

후보 생성기는 핵심 해석 긴장마다 서로 다른 메커니즘 번역을 최소 두 개 탐색한다. 모든
관계를 반드시 사용하거나 온톨로지에 없는 창작을 금지하지 않는다. 온톨로지 밖의 번역을
선택하면 근거와 새 관계 후보를 결과에 기록할 수 있지만, 같은 실행 중에 영구 온톨로지를
자동 수정하지 않는다.

온톨로지는 인물 이름, 출생정보, 차트 원문, 특정 로컬 아티팩트의 설정과 표현을 포함하지
않는다. 개념 ID와 관계는 게임 설계상 재사용 가능한 추상 수준을 유지한다.

# 3. Validation

결정적 validator는 다음 조건만 확인한다.

- YAML 스키마 버전과 ID가 유효하고 중복되지 않는다.
- 모든 관계 대상이 존재하거나 명시적인 확장 후보 형식을 따른다.
- 순환 관계가 허용되는 필드와 금지되는 계층 필드를 구분한다.
- 후보 생성 결과가 핵심 긴장별로 최소 두 개의 구조적으로 다른 번역을 기록한다.
- 최종 선택이 사용한 해석 ID와 메커니즘 번역 경로를 추적할 수 있다.

온톨로지가 완전한지, 번역이 재미있는지, 특정 후보가 더 적합한지는 의미 검토 대상이다.
노드 수나 관계 수를 품질 지표로 사용하지 않는다.

# 4. Rejected Alternatives

## 4.1 해석 개념과 직업·무기를 고정 대응

다양한 해석 맥락을 클래스 표로 축소하고 새로운 조합을 차단하므로 채택하지 않는다.

## 4.2 자유 산문 프롬프트만 확장

가능한 번역을 설명할 수는 있지만 누락과 반복 수렴을 결정적으로 검사하기 어렵다. 실행
입력도 계속 증가하므로 채택하지 않는다.

## 4.3 처음부터 외부 지식 그래프를 운영

현재 규모에서는 저장·질의 인프라가 관계 자체보다 복잡해진다. 버전 관리되는 작은 YAML과
결정적 검증으로 시작하고 실제 규모와 질의 요구가 확인된 뒤 재검토한다.

# 5. Consequences

## Positive

- 하나의 해석이 첫 번째로 떠오른 무기나 전투 축에 고착되는 현상을 줄인다.
- 같은 근거에서 이동·방어·공격·지원 중심 후보를 병렬로 탐색할 수 있다.
- 해석에서 능력까지의 변환 경로를 사람이 검토하고 도구가 추적할 수 있다.
- 특정 인물이나 과거 결과를 다음 생성에 노출하지 않고 설계 지식을 재사용한다.

## Negative

- 어휘 관리와 관계 검토 비용이 생긴다.
- 관계가 지나치게 많으면 후보 생성 입력이 비대해지고 선택이 형식적으로 변할 수 있다.
- 불완전한 온톨로지가 가능한 창작 범위 전체로 오인될 수 있다.
- 추상 ID만 맞추고 실제 플레이 인과는 약한 후보가 구조 검증을 통과할 수 있다.

# 6. Follow-up

1. 초기 개념 범위와 YAML 스키마를 상세 spec으로 정의한다.
2. 현재 전투 축에서 표현하기 어려운 상호작용을 최소 합성 사례로 조사한다.
3. 온톨로지 validator와 역방향 조회 도구를 구현한다.
4. 후보 brief에 해석 긴장과 복수 번역 경로를 기록하는 계약을 추가한다.
5. 합성 fixture로 단일 번역 고착과 온톨로지 밖 창작 허용을 함께 검증한다.
6. 실제 모델 생성 평가는 별도 로컬 실행으로 수행하고 원본을 영구 근거로 사용하지 않는다.
