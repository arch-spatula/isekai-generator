# ADR: 게임 개발 결과물의 아티팩트 정의

* **Status:** Accepted
* **Date:** 2026-11-02
* **Decision Owners:** Project Owner
* **Scope:** 이 저장소에서 생성하는 게임의 기획부터 배포까지의 결과물

---

# 1. Context

이 저장소는 개인화된 게임을 생성하는 하나의 게임 스튜디오 역할을 한다. 따라서 게임의
결과는 최종 실행 파일 하나만을 뜻하지 않는다. 기획, 구현, 검증, 빌드와 배포 과정에서
만들어지고 다음 단계의 입력 또는 출시 근거가 되는 결과물을 함께 관리해야 한다.

현재 문서에는 생성 작업의 상태와 산출물 목록을 저장한다는 방향이 있으나, 어떤 결과물을
아티팩트로 취급하고 언제 게임 개발이 완료되었다고 판단할지는 정의되어 있지 않다.

# 2. Decision

이 저장소에서 **아티팩트(artifact)** 는 한 게임의 기획부터 배포까지 생성된, 식별하고
추적할 수 있는 개발 결과물을 의미한다. 게임 하나의 아티팩트는 다음 계층을 포함한다.

## 2.1 기획 아티팩트

- 게임 콘셉트와 생성에 사용한 입력 및 해석 근거
- GDD, 내러티브, 캐릭터, 세계관과 레벨 디자인
- 기능, UI, 전투, 성장 및 콘텐츠 명세
- 주요 기술·제품 결정을 기록한 ADR

## 2.2 제작 아티팩트

- 게임 소스 코드와 프로젝트 설정
- 그래픽, 애니메이션, 음향, 음악, 폰트 등의 게임 에셋
- 에셋의 출처, 라이선스와 생성 정보를 확인할 수 있는 메타데이터
- 빌드와 패키징을 재현하는 스크립트 및 설정

## 2.3 검증 아티팩트

- 자동화 테스트 결과
- 플레이테스트 기록과 알려진 문제
- 지원 플랫폼별 빌드 검증 결과
- 출시 여부를 판단하는 검수 결과

## 2.4 빌드 아티팩트

- 개발 및 테스트용 빌드
- 지원 플랫폼에서 실행 가능한 파일
- 실행에 필요한 데이터와 런타임을 포함한 패키지
- 빌드를 식별하고 원본까지 역추적할 수 있는 버전 및 체크섬 정보

## 2.5 배포 아티팩트

- 사용자에게 전달하는 압축 파일, 설치 파일 또는 플랫폼별 배포 패키지
- 릴리스 노트와 알려진 문제
- 버전, 대상 플랫폼, 생성 시각과 대응 빌드를 기록한 릴리스 메타데이터
- 배포에 필요한 라이선스 및 고지 문서

# 3. Artifact Lineage

각 게임의 결과물은 다음 계보로 연결되어야 한다.

```text
생성 입력
    → 기획 아티팩트
    → 제작 아티팩트
    → 검증 아티팩트
    → 빌드 아티팩트
    → 배포 아티팩트
```

뒤 단계의 아티팩트는 자신을 만든 앞 단계와 게임 버전을 식별할 수 있어야 한다. 최종
배포 패키지에서 사용한 빌드, 소스 리비전, 주요 기획과 생성 입력까지 역추적할 수 있어야
한다. 같은 게임의 수정본을 덮어쓰지 않고 버전이 다른 아티팩트로 구분한다.

# 4. Storage Policy

- 문서, 소스 코드, 설정, 스크립트와 작은 메타데이터는 저장소에서 버전 관리한다.
- 재생성할 수 있는 중간 빌드와 대용량 바이너리는 소스와 분리된 아티팩트 저장 위치에
  둘 수 있다.
- 저장소 밖에 보관하는 아티팩트도 게임 ID, 버전, 경로 또는 식별자, 체크섬과 생성 상태를
  저장소 또는 산출물 목록에서 추적한다.
- 출생정보처럼 개인을 식별할 수 있는 생성 입력은 공개 아티팩트와 분리하고, 배포물에
  포함하지 않는다.
- 외부 에셋은 배포 권한을 확인할 수 없는 상태로 릴리스 아티팩트에 포함하지 않는다.

구체적인 디렉터리 구조, 아티팩트 저장소 제품과 보존 기간은 구현 시 별도 명세 또는
후속 ADR에서 정한다.

# 5. Independent Repository Promotion

생성된 게임이 계속 개발할 가치가 있다고 판단되면, 게임 전체 또는 선택한 하위
아티팩트를 이 저장소에서 분리하여 별도의 Git 저장소에 커밋할 수 있어야 한다. 하위
아티팩트에는 특정 게임의 GDD, 게임 프로젝트, 에셋 묶음, 빌드 도구 또는 그 조합이
포함될 수 있다.

독립 저장소로 승격하는 결과물은 다음 조건을 만족해야 한다.

- 무엇을 내보냈는지 나타내는 아티팩트 목록과 버전을 포함한다.
- 원본 게임 ID, 원본 저장소의 소스 리비전과 생성 입력을 식별할 수 있는 계보 정보를
  포함한다.
- 해당 아티팩트를 이해하고, 필요한 경우 빌드하거나 수정하는 데 필요한 문서, 소스,
  설정과 라이선스 고지를 함께 포함한다.
- 선택하지 않은 상위 또는 형제 아티팩트에 의존한다면 의존성을 함께 포함하거나 접근
  가능한 버전 고정 참조로 명시한다.
- 개인을 식별할 수 있는 생성 입력, 자격 증명, 로컬 전용 설정과 배포 권한이 없는 에셋은
  커밋하지 않는다.

승격은 원본 아티팩트를 이동하거나 덮어쓰는 작업이 아니라, 추적 가능한 독립 개발
단위를 만드는 작업이다. 별도 저장소에서 발생한 이후 변경은 그 저장소의 이력으로
관리하며, 원본과 다시 동기화할 필요가 생기면 동기화 방향과 충돌 정책을 별도로 정한다.

저장소 생성 방식, 원격 Git 호스팅 서비스, 커밋 단위와 자동 내보내기 절차는 후속 명세나
ADR에서 결정한다.

# 6. Completion Criteria

게임 개발 결과는 최소한 다음 조건을 만족할 때 완성된 배포 아티팩트로 간주한다.

- 승인된 기획과 명세를 식별할 수 있다.
- 대응하는 소스 리비전에서 빌드를 재현할 수 있다.
- 대상 플랫폼에서 실행을 검증했다.
- 필수 에셋의 출처와 배포 권한을 확인했다.
- 실행 파일 또는 설치 패키지, 릴리스 메타데이터와 필요한 고지 문서가 함께 존재한다.
- 배포 패키지에서 빌드와 주요 입력 아티팩트까지 역추적할 수 있다.

기획이나 소스 코드만 존재하는 상태는 유효한 중간 아티팩트이지만, 배포 가능한 게임의
완료 상태로 보지 않는다.

# 7. Consequences

## Positive

- 최종 실행 파일뿐 아니라 게임이 만들어진 과정 전체를 결과물로 보존할 수 있다.
- 생성된 게임의 빌드와 기획·소스·검증 결과 사이의 관계를 추적할 수 있다.
- 중간 결과와 배포 가능한 완료 상태를 구분할 수 있다.
- 빌드 재현, 라이선스 확인과 출시 검수의 기준이 생긴다.
- 마음에 드는 게임이나 하위 아티팩트를 독립 프로젝트로 이어서 개발할 수 있다.

## Negative

- 아티팩트별 메타데이터와 계보를 지속해서 관리해야 한다.
- 대용량 에셋과 플랫폼별 빌드를 저장할 별도 공간이 필요할 수 있다.
- 개인정보와 라이선스 검증이 배포 과정의 필수 단계가 된다.
- 별도 저장소로 승격한 뒤에는 원본과의 변경 이력 및 의존성 관계를 추가로 관리해야 한다.
