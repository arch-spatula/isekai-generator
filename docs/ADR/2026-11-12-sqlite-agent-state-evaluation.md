# ADR: SQLite와 목적별 CLI를 통한 에이전트 상태 관리 평가

* **Status:** Proposed — 도입 판단을 위한 평가안, 구현 미승인
* **Date:** 2026-11-12
* **Decision Owners:** Project Owner
* **Scope:** 생성 실행의 운영 상태·이력·지문 레지스트리와 에이전트용 읽기·쓰기 명령

## 배경

현재 생성 파이프라인은 전체 상태, 이벤트, 단계별 체크포인트, 시도별 입력·결과,
채택 기록과 전투·세계 지문을 여러 JSON 및 JSONL 파일로 관리한다. 에이전트는
일부 상황에서 여러 기록을 읽어 다음 작업, 재시도 가능 여부와 복구 절차를 결정한다.
이 과정에는 도구 호출 인자 작성, 반환 내용 읽기, 기록 간 대조와 판단 비용이 든다.

이미 [검증 실행 래퍼](../../scripts/run-logged-step.ts),
[전문 해석 시도 관리자](../../scripts/artifacts/specialist-attempt.ts),
[편집 관리자](../../scripts/artifacts/defensive-edit.ts)가 기록과 판정 일부를 자동화한다.
따라서 비교 기준은 JSON을 모두 수작업으로 다루는 가상의 시스템이 아니라 현재 구현이다.
스크립트 내부에서 JSON을 읽고 쓰더라도 그 내용이 모델에 전달되지 않으면 파일 크기만큼
모델 토큰이 소비되는 것은 아니다.

[이벤트 로그 명세](../spec/artifact-event-log.md)는 로그와 상태 파일이 단일 트랜잭션이
아니어서 중단 시 실제 기록을 대조하도록 한다. [세계 선택 명세](../spec/world-concept-selection.md)는
전투·세계 레지스트리의 부분 등록을 별도로 처리한다. [진행 인계 명세](../spec/artifact-progress-handoff.md)는
중단된 실행의 상태와 관련 기록을 확인하는 절차를 정의한다. 이처럼 저장 구조가
에이전트 운영 지침과 복구 로직에 영향을 준다.

## 제안과 현재 결정의 경계

**단일 로컬 SQLite 데이터베이스와 목적별 CLI를 평가 후보로 기록한다.** 이 ADR은
도입, 프로토타입 개발, 기존 데이터 이관이나 현행 스킬 변경을 승인하지 않는다.
현재 파일 기반 운영을 유지하며, 후속 작업이 승인되면 아래 비교와 수용 기준으로
도입 여부를 판단한다.

평가할 구조는 다음과 같다.

- 운영 상태의 원본은 하나의 DB로 통합한다. 실행·단계·시도·이벤트·채택 기록과
  전투·세계 지문이 후보이며, 논리적 구분과 단계별 입력 격리는 유지한다.
- 에이전트는 정해진 인자를 받는 쓰기 명령을 호출한다. 식별자·시각·시도 번호 생성,
  상태 전이 검증과 관련 이력 기록은 스크립트가 담당한다.
- 읽기 명령은 해당 작업에 필요한 현재 상태, 허용된 다음 작업, 관련 경로와 진단만
  반환한다. 전체 DB나 이벤트 이력을 기본 출력으로 제공하지 않는다.
- 재시도 예산과 선행 조건 등 결정적인 규칙은 코드로 판정한다. 해석 품질·의미 보존과
  창작 선택은 에이전트가 판단하고 그 결과를 명령으로 제출한다.
- 보고서·해석·GDD 본문은 파일로 유지한다. 모든 JSON 설정·교환 형식·창작 산출물을
  DB로 옮기거나 에이전트에게 SQL과 테이블 구조를 노출하는 것은 제안 범위가 아니다.

아래는 인터페이스 설명용 가상 명령이며 현재 실행 가능한 명령이 아니다.

```text
state attempt start --run <run-id> --stage saju
state attempt finish --attempt <attempt-id> --output <document-path>
state read next --run <run-id> --stage saju
state read issues --attempt <attempt-id>
```

시도 시작 명령은 상태 확인과 시도 예약을 함께 처리해야 한다. 읽기 결과를 근거로
에이전트가 임의 시도 번호를 지정하게 하면 조회와 실행 사이의 경쟁 조건이 남는다.
쓰기 명령은 재호출 시 중복 수행을 막거나 기존 결과를 돌려주는 정책을 명시해야 한다.
진단은 검증기 결과를 자동 저장하고, 의미 검토 사유만 에이전트가 작성하도록 평가한다.
출력에는 해당 단계에 허용된 정보만 포함하고 다른 체계·이전 실행의 본문을 섞지 않는다.

## 기대 효과와 추정의 한계

토큰 절약의 주된 원인은 저장 형식 교체가 아니라 **에이전트에게 전달하는 정보와
에이전트가 수행하는 기계적 판단의 감소**다.

| 변경 | 토큰 효과 | 로직 효과 |
| --- | --- | --- |
| 저장소만 JSON에서 SQLite로 교체 | 출력과 호출이 같으면 거의 없을 수 있음 | 파일 잠금·원자적 교체·기록 대조의 일부 감소 |
| 필요한 상태만 조회 | 불필요한 입력과 반복 조회 감소 | 여러 기록을 조합하는 절차 감소 |
| 상태·이벤트를 함께 갱신 | 기록 명령 작성과 후속 확인 감소 | 누락·부분 기록 처리 감소 |
| 재시도·다음 작업을 코드로 판정 | 기계적 판단 부담 감소 | 오케스트레이터와 스킬의 조건 분기 감소 |

실행별 관리 토큰과 전체 토큰을 측정하지 않았으므로 현재 절약률은 미확정이다.
다음 표는 예측이나 측정 결과가 아닌 계산 예시다.

> 전체 토큰 절약률 = 관리 절차의 전체 토큰 비중 × 관리 절차의 토큰 절감률

| 가정한 관리 토큰 비중 | 가정한 관리 토큰 절감률 | 계산한 전체 절약률 |
| --- | --- | --- |
| 5% | 70% | 3.5% |
| 15% | 70% | 10.5% |
| 30% | 70% | 21% |

본문 생성량이 큰 정상 실행에서는 전체 효과가 제한적일 수 있다. 실패·재시도·중단 복구가
많은 실행에서는 관리 비중이 커질 수 있다는 가설을 검증한다. 판단 토큰은 읽기 분량에
비례한다고 가정하지 않으며, 관측할 수 없는 사용량은 추정값과 구분한다.

## 대안

1. **현재 구조 유지:** 이관 비용이 없고 파일을 직접 확인하기 쉽다. 분산 기록의
   정합성 처리와 에이전트 운영 절차는 유지해야 한다.
2. **JSON을 유지하고 CLI만 통합:** 목적별 조회와 상태 전이 자동화로 상당한 토큰 절약을
   얻을 수 있다. SQLite의 추가 가치를 분리해 측정할 필수 비교군이다.
3. **SQLite와 CLI를 함께 도입:** 조회·제약조건과 DB 내 트랜잭션을 활용할 수 있다.
   스키마 변경, 백업·복구, 이관과 쓰기 경합 처리를 새로 관리해야 한다.

SQLite가 CLI 통합 대비 추가 가치를 입증하지 못하면 두 번째 대안을 선택할 수 있다.
범용 워크플로 엔진이나 서버형 DB 도입은 이 평가에 포함하지 않는다.

## 트랜잭션과 운영상의 한계

SQLite는 하나의 트랜잭션에 포함된 DB 변경의 원자성을 보장한다.
[공식 트랜잭션 설명](https://www.sqlite.org/transactional.html)에 따라 상태·이벤트·채택
기록 또는 두 지문 등록을 함께 반영할 수 있다. 단, 관련 쓰기가 같은 트랜잭션을 사용하도록
실제로 구현되어야 한다.

Markdown 파일 생성, 검증 프로세스, 에이전트 실행은 DB 트랜잭션에 포함되지 않는다.
파일 생성 후 DB 기록 전에 종료되는 경우에 대비해 출력 해시와 검증 결과를 대조하는
복구 절차가 여전히 필요하다. 실행 중인 에이전트의 생존 여부도 상태값만으로 확정하지 않는다.

SQLite는 동시에 한 쓰기 작업만 허용한다. 짧은 트랜잭션으로 예약·결과 반영을 끝내고,
에이전트 실행 중에는 트랜잭션을 유지하지 않는다. 쓰기 대기·시간 초과와 재호출 정책을
검증한다. 여러 컴퓨터가 네트워크 파일시스템의 DB를 직접 공유하는 운영은 가정하지 않는다.
[공식 적용 범위와 동시성 설명](https://www.sqlite.org/whentouse.html)을 따른다.

DB는 로컬 운영 데이터다. 기존 아티팩트를 영구 근거로 삼거나 개인정보·생성 본문을
커밋하지 않는다. 진행 Markdown이 필요하면 DB에서 재생성하는 표시용 결과로 취급하며,
DB와 파일을 독립적인 상태 원본으로 이중 기록하는 구조는 피한다.

## 후속 평가 방법과 채택 기준

후속 평가가 승인되면 같은 합성 입력·작업 순서로 현행 방식, JSON+통합 CLI,
SQLite+통합 CLI를 비교한다. 기존 로컬 실행의 보존을 전제로 하지 않고 최소 재현 자료는
커밋된 합성 fixture로 제공한다.

- 정상 완료, 검증 실패 후 재시도, 중단 후 재개, 병렬 시도 예약, 중복 완료 호출,
  DB 기록과 파일 게시 사이의 종료, 두 지문 등록 실패를 포함한다.
- 에이전트에게 전달한 지침·도구 결과의 입력 토큰, 명령·기록 작성의 출력 토큰,
  제공되는 경우 판단 토큰을 구분한다. 호출 수, 소요 시간과 오류율도 함께 기록한다.
- 관리 절차만의 절약률과 본문 생성을 포함한 전체 절약률을 각각 보고한다. 모델·설정·
  반복 횟수와 캐시 사용량을 남기고, 단일 실행 차이를 일반적인 절약률로 주장하지 않는다.
- 스킬에서 제거할 수 있는 기계적 판단 항목, 구현의 상태 전이·복구 분기, 중복 기록
  경로와 저장소별 잠금 처리를 비교한다. 코드 줄 수만으로 단순화를 판정하지 않는다.
- DB 스키마 갱신, 백업·복구, 기존 실행 처리 비용을 비교 결과에 포함한다. 기존 데이터
  이관과 종료 실행의 취급은 구현 전에 별도로 결정한다.

채택에는 입력 격리·진단 보존·시도 한도·중복 방지와 복구 시나리오의 동작 보존이 필요하다.
그 위에서 CLI 통합의 관리 토큰 감소가 반복 관측되고, SQLite가 JSON+CLI 대비 부분 기록과
정합성 처리의 복잡성을 줄여 추가 운영 비용을 정당화해야 한다. 수치 목표는 평가 착수 전에
정하며, 측정 없이 절약률을 채택 근거로 사용하지 않는다.

평가 결과로 SQLite 도입, JSON+CLI 통합 또는 현행 유지를 별도 결정한다.
