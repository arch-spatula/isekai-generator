# ADR: 생성 아티팩트 버전을 기준선과 실행 이력으로 구분

* **Status:** Accepted
* **Date:** 2026-11-04
* **Decision Owners:** Project Owner
* **Scope:** `artifacts/vX.Y.Z`에 저장하는 차트 보고서와 개인화 GDD 생성 실행

---

# 1. Context

현재 생성기는 `artifacts/`에서 가장 큰 버전을 찾고 patch를 1 올린다. 그 결과 모든 실행이
`v0.1.x`에 누적되며, 전투 원형 후보 비교처럼 프롬프트와 파이프라인의 품질 기준이 크게
바뀌어도 버전에서 그 변화를 알 수 없다. 반대로 매 실행마다 minor를 자동으로 올리면 아직
검증 중인 실험과 채택된 생성 기준선을 구별할 수 없다.

기존 `v0.1.0`~`v0.1.27`은 서로 다른 입력과 파이프라인 상태에서 생성된 실험 결과다. 이
이력을 다시 번호 매기거나 내용의 일관성을 맞추는 것보다, 앞으로 어떤 기준선에서 어떤
실행이 이루어졌는지를 분명히 기록하는 편이 중요하다.

이 버전은 문서 형식의 `schema-version`, 게임의 출시 버전과 패키지 의존성의 Semantic
Versioning이 아니다. 생성 파이프라인의 채택 세대와 실행 이력을 식별하는 저장소 내부
버전이다.

# 2. Decision

생성 아티팩트 버전 `vMAJOR.MINOR.PATCH`를 다음처럼 사용한다.

- `MAJOR`: 생성 아티팩트 계약이 안정화되기 전까지 `0`으로 유지한다. `1` 승격 조건은
  별도 ADR에서 결정한다.
- `MINOR`: 실험을 거쳐 프로젝트 기준선으로 명시적으로 채택한 프롬프트·파이프라인
  세대다. 실행만으로 자동 증가하지 않는다.
- `PATCH`: 활성 minor 안에서 할당한 생성 시도 번호다. 성공 여부와 관계없이 실행을
  시작할 때 1 증가하며 재사용하지 않는다.

따라서 `v0.2.7`은 “채택된 0.2 기준선으로 할당한 여덟 번째 실행”을 뜻한다. patch의 차이는
품질 우열이나 호환성 수준을 뜻하지 않는다.

## 2.1 Minor 승격

minor 승격은 다음 근거가 준비된 뒤 사람이 명시적으로 수행한다.

- 해결하려는 문제와 관찰 근거가 incident 또는 동등한 문서에 있다.
- 채택할 결정과 계약이 ADR 및 spec에 반영되어 있다.
- 구현과 결정적 validator가 완료되었다.
- 대표 입력을 사용한 회귀 생성과 이전 기준선 비교가 끝났다.
- 알려진 회귀와 미해결 문제가 기록되어 있다.
- 기준선으로 사용할 Git source revision을 식별할 수 있다.

조건을 자동 점수로 판정하지 않는다. 승격 명령은 활성 series와 기준선 메타데이터를
갱신할 뿐, 기존 아티팩트를 이동하거나 이름을 바꾸지 않는다.

새 minor의 `.0`은 과거 결과를 이름만 바꾼 복사본이 아니라, 승격된 기준선으로 새로
생성하는 첫 기준선 확인 시도에 사용한다. `.0`이 모든 validator를 통과하면 기준선 확인
실행이 되며, 실패해도 그 번호는 보존하고 다음 시도는 `.1`이 된다.

## 2.2 Patch 할당과 실행 상태

차트 단독 생성과 전체 GDD 생성은 현재 같은 `artifacts/` 이름 공간에 있으므로 하나의
patch 순서를 공유한다. 실행을 시작하기 전에 버전 디렉터리와 실행 manifest를 먼저
생성하여 번호를 예약한다. 실행 결과는 `succeeded`, `failed`, `cancelled` 중 하나로
기록한다. 프로세스가 비정상 종료되어 상태가 갱신되지 않아도 디렉터리가 남으므로 다음
실행이 같은 번호를 재사용하지 않는다.

각 실행은 생성 종류와 목적을 별도로 기록한다. 버전 번호 자체에 `chart`, `deep`,
`incident-reproduction` 같은 의미를 인코딩하지 않는다.

## 2.3 기준선과 스키마의 분리

활성 minor와 그 기준 Git revision은 저장소에서 추적하는 series 설정을 단일 기준으로
삼는다. 각 아티팩트의 실행 manifest는 할당 버전, 생성 종류, 목적, mode, source revision,
기준선과 상태를 기록한다.

Markdown·JSON 파일 형식의 `schema-version`은 계속 각 문서 계약에서 독립적으로 관리한다.
스키마가 바뀌었다는 이유만으로 minor를 자동 승격하지 않으며, minor가 승격되어도 모든
스키마 버전을 함께 올리지 않는다.

## 2.4 기존 이력과 다음 기준선

기존 `v0.1.x`는 최초 실험 series로 보존한다. 누락된 실행 manifest를 추측하여 소급
생성하거나 버전을 변경하지 않는다.

`v0.2`의 후보 기준선은 전투 원형 후보 비교뿐 아니라 현재 확인된 세계관의 바다·군도
문법 수렴에 대한 완화책과 검증까지 포함하는 것을 목표로 한다. 해당 작업이 완료되기
전에 번호만 `v0.2.x`로 바꾸지 않는다. 조건이 충족되면 명시적으로 승격한 뒤 새
`v0.2.0` 회귀 생성을 수행한다.

# 3. Rejected Alternatives

## 3.1 가장 큰 전체 버전의 patch만 계속 증가

구현은 단순하지만 채택된 생성 기준의 변화를 표현하지 못한다. 현재 `v0.1.x` 누적 문제가
계속되므로 채택하지 않는다.

## 3.2 실행할 때마다 minor 자동 증가

단순 실험과 채택된 개선을 같은 수준으로 취급하고 기준선의 의미를 약하게 만든다.
minor는 사람의 승격 결정으로만 변경한다.

## 3.3 성공한 실행만 patch 소비

실패 번호를 다시 사용하면 로그나 외부 참조가 서로 다른 시도를 가리킬 수 있고 실패
이력이 사라진다. 시도를 할당하는 순간 번호를 소비한다.

## 3.4 기존 v0.1.x를 새 기준에 맞게 재번호 부여

과거 실행 당시의 기준선과 상태를 완전하게 복원할 수 없으며 기존 경로와 지문
레지스트리 참조를 깨뜨린다. 기존 번호는 그대로 둔다.

# 4. Consequences

## Positive

- 버전만으로 채택된 생성 기준선과 그 안의 개별 시도를 구분할 수 있다.
- 실패와 취소를 포함한 실행 번호가 재사용되지 않아 조사와 재현성이 좋아진다.
- 아티팩트 버전과 파일 스키마 버전의 의미가 섞이지 않는다.
- minor 승격 전 회귀 검증과 알려진 문제 기록이 명시적인 품질 관문이 된다.

## Negative

- 실행마다 작은 manifest와 상태 갱신이 필요하다.
- minor 승격에 판단과 문서화 절차가 추가된다.
- 기존 v0.1.x에는 새 manifest가 없어 새 series보다 계보 정보가 적다.
- 차트 단독 실행도 공용 patch를 소비하므로 번호가 연속된 GDD 개수를 뜻하지 않는다.
