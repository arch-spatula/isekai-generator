# 방어문구 편집 검증 예외와 이벤트 상태 병합 오류

> 상태: 코드 결함 수정·합성 회귀 완료 — secondary 정책 검토 미완료
> 발견일: 2026-11-11
> 범위: 방어문구 편집 제출 실패의 기록·재시도와 전문 해석 시도 이벤트 분류

## 기대 동작과 실제 동작

방어문구 편집자가 잘못된 `secondary.target`을 제출하면 관리 도구는 해당 제출만
`editing-failed`로 기록하고 다음 허용 범위의 편집 시도를 준비해야 한다. 원문이나 준비된
input의 해시가 바뀌었거나 기록·게시가 실패한 경우에만 실행을 중단해야 한다.

실제로는 추가 검토 대상이 원문에 없을 때 `Invalid secondary target` 예외가
`finishDefensiveEdit` 밖으로 전파됐다. `result.json`이 기록되지 않아 다음 `prepare`는 직전
실패를 확인할 수 없었고, 문장 범위에서 항목 범위로 진행할 수 없었다. 잘못된 편집은
게시되지 않았지만 허용된 복구 경로도 함께 차단됐다.

같은 시기에 별도의 rebase 병합 결함도 발견됐다. 전문 해석 결과가 방어문구 편집으로
넘어가야 하는 `editing-required`인데 이벤트 선택식은 이를 `validation_failed`로
분류했다. 진단이 없는 정상 편집 인계에서는 실패 이벤트에 필수인 `reason`과 `issues`가
없어 이벤트 검증 예외가 발생했고, 시도 결과 기록까지 막았다. 두 결함 모두 생성 본문을
최종 경로에 게시하기 전에 발생했다.

## 개인정보 없는 최소 합성 재현

첫 번째 결함은 유효한 합성 전문 해석과 다음과 같은 추가 검토 결정만으로 재현된다.

```json
{
  "secondary": [
    {
      "id": "review-1",
      "target": "S-99",
      "status": "preserved",
      "reason": "존재 여부를 잘못 판단한 합성 검토",
      "editIds": []
    }
  ]
}
```

합성 문서에는 `S-99`가 없다. 이전 동작은 `Invalid secondary target`을 throw하고 결과를
남기지 않았다. 수정 동작은 원문과 같은 후보를 보존하고 안전한 `editing-contract`
진단을 가진 `editing-failed` 결과를 기록한다. 다음 prepare는 그 결과와 후보 해시를
확인한 뒤 다음 scope를 할당한다.

두 번째 결함은 validator 진단이 0개인 유효한 합성 전문 해석으로 재현된다. 결과 상태는
`editing-required`이며 문서를 게시하지 않고 편집 단계로 넘겨야 한다. 이전 병합 코드는
사유와 진단이 없는 `validation_failed`를 만들었고 이벤트 스키마가 이를 거부했다.
수정 동작은 이 인계를 `validation_succeeded`로 기록한다.

이 사례들은 실제 해석 본문, 출생정보, 실명이나 특정 로컬 실행에 의존하지 않는다.

## 원인

편집 관리자는 편집자 제출 계약 오류와 관리자 자신의 운영·무결성 오류를 같은 예외
경로로 처리했다. 대상·링크·범위·리뷰 완결성 검사는 모델 제출을 평가하는 경계인데도,
원본 변조나 파일 기록 실패처럼 재시도를 허용하면 안 되는 오류와 구별되지 않았다.

이벤트 결함은 rebase 뒤 상태 판정과 이벤트 판정이 하나의 조건식에 잘못 결합된 것이
원인이다. 현재 결과 타입에 없는 성공 상태를 비교하고 나머지 상태를 실패로 모으면서,
편집 인계 상태와 진단 유무의 조합을 표현하지 못했다.

## 수정 경계

[방어문구 편집 관리 모듈](../../scripts/artifacts/defensive-edit.ts)은 준비된 input과 원본,
source 및 제출의 source hash를 먼저 확인한다. 이 무결성 검사가 끝난 뒤 발생하는 제출
형식, review 대상·링크, 편집 범위와 미해결 사유 계약 오류는 다음과 같이 기록한다.

- 상태는 `editing-failed`로 기록한다.
- 오류 코드는 `editing-contract`로 구분하고 고정된 검증 메시지만 보존한다.
- 원문을 변경하지 않은 후보와 그 해시를 기록해 다음 허용 scope에서 재검토할 수 있게 한다.
- `editing-failed`는 결과 기록 전에 안전한 사유와 진단이 있는 `validation_failed` 이벤트를
  남긴다. 실행 실패와 통과도 각각 `execution_failed`, `validation_succeeded`로 기록한다.
- 원본·input·source hash 불일치, lock, 부모 실행 상태, 후보·결과·진행 기록과 게시 실패는
  계속 throw하며 자동 재시도를 열지 않는다.

[전문 해석 시도 관리자](../../scripts/artifacts/specialist-attempt.ts)는 결과 상태별 이벤트를
명시적으로 나눈다. `editing-required`는 `validation_succeeded`, 구조 검증 실패는 안전한
사유와 진단이 있는 `validation_failed`, 실행 실패는 안전한 사유와 진단이 있는
`execution_failed`로 기록한다. `editing-required`는 여전히 전문 문서를 게시하지 않는다.

상세 계약은 [방어문구 편집 명세](../spec/specialist-defensive-phrase-editing.md)와
[이벤트 기록 모듈](../../scripts/artifacts/artifact-events.ts)를 따른다. 전날 발견한 해시 계약 혼선과
수용 검증은 [방어문구 편집 해시 계약 인시던트](2026-11-10-defensive-editor-hash-contract.md)에
별도로 기록돼 있다.

## 확인한 검증과 한계

구현과 테스트 작성은 서로 다른 역할이 맡았다. 잘못된 secondary target이
`editing-failed`로 기록되고 다음 scope가 준비되는 합성 회귀, 준비된 원본·input 변조가
계속 복구 불가능한 오류인 사례, 게시 실패가 복구 가능한 제출 오류로 바뀌지 않는 사례를
각각 실행해 통과를 확인했다. 전문 해석 이벤트 수정은 전문 시도·방어 편집·이벤트 관련
테스트 묶음에서 42개 테스트와 445개 assertion 통과를 확인했다.

새 편집 제출 오류 경계의 테스트는 독립 읽기 전용 리뷰에서 승인됐고, 리뷰 지적을 반영한
최종 관련 테스트는 48개 통과했다. 이는 관련 범위의 검증 결과이며 전체 test suite 통과를
뜻하지 않는다. 실제 모델을 사용한 새 편집 실행과 전체 개인화 GDD 생성 품질·비용 평가는
수행하지 않았다.

## 미해결 정책 검토

조사 과정에서 `secondary`는 사용자에게 보여 주는 알림 리포트가 아니라, 편집자가 자동
진단 밖의 표현을 찾기 위해 내부적으로 전체 문서를 추가 탐색하고 각 대상을 편집·보존·
확대·보류로 판정하는 계약임을 다시 확인했다. 이번 수정은 그 제출의 실패를 복구 가능하게
만들 뿐, `secondary`의 이름·필수성·사용자 노출 여부나 잘못된 추가 대상에 허용할 재시도
정책을 새로 결정하지 않는다. 이 의미가 스킬과 관리 인터페이스에서 충분히 명확한지,
운영자가 별도 알림으로 오해할 여지가 있는지는 후속 정책 검토로 남긴다.
