# 컨텍스트 부족 시 품질 유지와 인계 계약 부재

## 상태와 확인 범위

- 상태: 해결 필요 — 계약 공백 확인, 설계·구현 미완료.
- 작성일: 2026-11-05.
- 범위: 전문 해석, 통합 해석, 전투·세계 선택, GDD 작성 에이전트와 상위 오케스트레이터.
- 우선 원칙: 억지로 완료하는 것보다 해석·설계 품질 유지가 중요하다.
- 확인한 사실은 현재 계약에 품질 유지를 위한 자발적 인계 경로가 없다는 점이다.
  실제 아티팩트의 품질 저하가 토큰 부족 때문에 발생했다는 재현 증거는 아직 없다.

이 문서는 문제 기록과 후속 설계 요구다. 새 상태나 인계 기능을 이미 구현한 것으로 보지 않는다.

## 배경

0.3 기준선에 도입한 아티팩트 루트 `TODO.md`는 단계 상태, 에이전트 ID, 산출물 경로와
중단 후 확인 순서를 남긴다. 이는 작업이 어디까지 진행됐는지 복원하는 데 도움이 된다.
그러나 에이전트가 남은 컨텍스트로 충분한 품질을 유지할 수 없다고 판단했을 때 무엇을
저장하고 어떤 결과로 반환할지는 정의하지 않는다.

프로젝트 소유자는 토큰이 부족한 상황에서도 어떻게든 끝내는 행동보다 품질을 유지하는
중단·인계를 우선해야 한다고 명시했다. 진행 표시만으로 이 요구가 해결되지는 않는다.

## 현재 코드·스킬에서 확인한 공백

| 현재 계약 | 한계 |
| --- | --- |
| 전문 에이전트는 한 번 작성·검증하고 결과를 반환 | 문서가 미완성인 채로 인계하는 반환 계약이 없음 |
| 전문 해석 결과는 passed / validation-failed / execution-failed | 품질을 지키기 위한 인계를 검증 실패·실행 오류와 구별할 수 없음 |
| 전문 해석은 최초 생성 포함 최대 3회 | 정상적인 컨텍스트 교체도 실패로 취급하면 복구 예산을 소모할 수 있음 |
| 진행 기록은 단계 상태·에이전트·시도 번호를 저장 | 질문별 완료 범위, 남은 근거, 미검증 부분과 상세 인계 내용을 표현하지 않음 |

## 예상되는 실패 양상 — 아직 재현되지 않은 위험

1. 에이전트가 종료를 우선해 후반 질문·시기·관계를 짧은 일반론으로 대체한다.
2. 모든 evidence ID를 인용하지만 개별 구조나 상호작용의 해석은 빠진다.
3. 생활 영역 요약은 채우지만 체계 고유 해석·개인별 부록이 얕아진다.
4. 미완성 문서를 완성본으로 전달하고 통합 단계가 누락된 내용을 전제로 진행한다.
5. 단순히 새 에이전트를 실행해 이미 해석한 부분을 반복하고 남은 부분을 계속 놓친다.
6. 컨텍스트 교체를 반복 실패로 계산해 3회 한도를 소진하거나, 반대로 무제한 인계로 비용이 늘어난다.

이 목록은 점검할 가설이다. 기존 책임 회피 문구 재발이나 특정 아티팩트의 결함을
토큰 부족의 결과로 단정하지 않는다.

## 해결에 필요한 동작

### 1. 소진 전에 품질 위험을 판단

정확한 잔여 토큰 수를 에이전트가 항상 알 수 있다고 가정하지 않는다. 아직 답하지 않은
질문 수, 남은 자료·근거, 필요한 상호작용 해석, 작성·검증·인계 작업량을 기준으로
현재 컨텍스트에서 품질을 유지할 수 있는지 판단하도록 설계한다.

판단 시점은 초기 과제 파악 후와 큰 구간을 마친 뒤를 포함해야 한다. 토큰이 거의 남지
않아 기록조차 못 하는 상황까지 기다리지 않는다. 모든 질문을 얕게 줄여 완료하는 것은
정상적인 해결책으로 인정하지 않는다.

### 2. 미완성 결과와 인계 내용을 별도로 보존

이어서 작업할 사람이 필요한 정보는 다음과 같다.

- 동일 run·단계·체계·논리적 시도의 식별 정보
- 사용한 원천 자료, 프롬프트·스킬·모드와 그 버전을 구분할 정보
- 미완성 문서의 정확한 경로와 보존된 내용의 식별 정보
- 작성한 구간과 검증까지 마친 구간의 구분
- 아직 답하지 않은 고정 질문과 누락·미검증 근거 목록
- 추가 설명·재검토가 필요한 항목과 현재 해결되지 않은 불일치
- 실행한 검증과 그 결과, 아직 실행하지 않은 검증
- 다음 에이전트가 수행할 구체적인 작업 순서

단계 체크 표시만으로 이를 대신하지 않는다. 내부 사고 과정, 대화 전체, 원시 출생정보,
다른 체계의 해석이나 다른 버전 자료를 인계문에 복제하지 않는다. 필요한 원문은 허용된
파일 경로로 전달한다. 하위 에이전트에게 루트 TODO 전체를 넘기는 방식도 피한다.

### 3. 실패와 구별되는 미완료 반환

품질을 보존하려고 인계하는 결과는 성공도 검증 실패도 실행 오류도 아니다. 상위
오케스트레이터가 이를 명시적으로 식별해 미완성 결과를 후속 단계에 전달하지 않아야 한다.
구체적인 결과 이름과 저장 스키마는 후속 설계에서 정한다.

진행 기록의 단계는 미완료로 남겨야 한다. 정확한 단계 상태 표현, 에이전트 종료와
인계 기록 완료의 확인 순서, 결과 저장 실패 시 동작도 함께 정의해야 한다.

### 4. 새 컨텍스트에서 동일 과제를 이어서 완성

다음 에이전트는 격리된 새 컨텍스트에서 허용된 원천 자료와 동일 단계 인계만 읽는다.
기존 부분의 내용을 무조건 신뢰하지 말고 완료·미완료 경계를 확인한 뒤 남은 과제를
수행한다. 이전 부분을 전부 재생성하거나 부분 문서를 맹목적으로 이어 붙이지 않는다.

이전 스냅샷을 보존하면서 최종 후보를 조립하는 방식, 항목 ID·근거 연결의 중복과 충돌,
프롬프트가 도중 변경된 경우의 처리를 정해야 한다. 완성 후에는 전체 문서를 검증하고,
품질 기준을 충족한 결과만 정식 경로에 게시한다.

### 5. 인계 예산과 오류 복구 예산 분리

정상 인계 때문에 검증 실패 재시도 한도를 소모하지 않도록 하는 방향을 검토한다.
그렇다고 무제한 실행을 허용하지는 않는다. 인계 횟수·진행 정체·전체 비용이나 시간에
대한 별도 종료 기준이 필요하다. 다음 인계에서도 같은 미완료 목록만 반복되면 과제
분할 등 다른 해결책을 검토하도록 해야 한다.

## 구현 전에 결정할 사항

1. 에이전트가 품질 위험을 판단할 구체적인 체크 시점과 신호는 무엇인가?
2. 인계 반환값과 단계 상태를 어떻게 표현하고, 강제 종료와 어떻게 구분할 것인가?
3. `garbage/` 아래 인계·스냅샷 경로 및 논리적 시도와 컨텍스트 실행의 번호 관계는 무엇인가?
4. 기존 한 번 작성 규칙과 3회 검증 복구 한도에 인계를 어떻게 연결할 것인가?
5. 여러 컨텍스트의 작업을 합칠 때 누락·중복·모순과 ID 안정성을 어떻게 확인할 것인가?
6. 문서 형식 통과 외에 깊이·구체성·개인화 품질을 어떻게 평가할 것인가?
7. 반복 인계 또는 인계 저장 실패에서 언제 멈추고 무엇을 사용자에게 보고할 것인가?

위 항목을 확정하기 전에 상태 이름이나 예산 정책을 현재 구현에 임의로 추가하지 않는다.

## 재현·수용 기준

- 제한된 작업 예산을 주거나 특정 구간에서 인계를 유도하는 통제된 실행을 마련한다.
  실제 잔여 토큰을 정확히 측정할 수 없는 환경에서도 시험할 수 있어야 한다.
- 인계 시 미완성 결과가 성공 처리·정식 게시·후속 단계 입력으로 사용되지 않는다.
- 인계 저장 후 기존 에이전트가 종료되고, 새 에이전트가 전달된 자료만으로 남은 과제를 식별한다.
- 완료한 구간을 불필요하게 다시 생성하지 않고 누락된 질문·근거·상호작용을 끝낸다.
- 최종 결과는 전체 validator를 통과하며, 여유 있는 실행과 비교해 해석 범위·관계 설명·
  개인별 구체성이 축소되지 않았는지 별도로 검토한다. 글자 수나 ID 포함만으로 품질을 판정하지 않는다.
- 정상 인계와 실제 검증 실패가 별도로 기록되고 각 한도와 종료 조건을 지킨다.
- 반복 인계, 기록 도중 중단, 부분 검증 실패, 병렬 체계 중 하나의 인계를 시험한다.
- 다른 체계·이전 버전·대화 이력이 인계 경로로 유입되지 않는다.

진행 로그가 존재하거나 스킬에 “품질을 우선한다”는 문장을 추가한 것만으로 해결 완료로
판정하지 않는다. 위 흐름의 계약·구현·통제된 재현과 품질 비교가 필요하다.
