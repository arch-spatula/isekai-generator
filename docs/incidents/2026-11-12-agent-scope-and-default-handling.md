# 에이전트의 작업 범위 확대·사용량 소진과 기본값 처리 실패

> 상태: 미해결 — 다중 에이전트 자동 적용 제한과 기본값 확인 지침 수정, 재개·컨텍스트 대응 미정
> 정리일: 2026-11-12
> 범위: 에이전트의 요청 해석, 호출 비용 통제, 작업 재개 및 기본값 적용 전 재질문

방어문구 편집 도구를 수정하는 과정에서 관측된 비용 사고와 이후 에이전트의 입력 처리
실패를 기록한다. 도구 자체의 검증 오류는 [별도 인시던트](2026-11-11-defensive-edit-validation-exception.md)에서 다룬다.
양력 재질문은 기본값 적용 실패의 사례이며, 문제 범위는 특정 달력 옵션에 한정되지 않는다.

## 실패 지점 재개 요청을 전체 생성으로 확대한 비용 사고

관리 도구 수정 뒤 실패 지점부터 작업을 이어 달라는 요청에 대해, 종료된 생성 run은 다시
열 수 없다는 규칙을 적용해 새 regression run을 예약했다. 종료 run을 재사용하지 않은 판단
자체는 맞았지만, 방어 편집 경계만 확인하는 표적 smoke나 합성 재현으로 범위를 제한하지
않고 개인화 GDD 전체 파이프라인을 다시 시작했다.

중단 전 확인된 모델 호출 구성은 차트 1회, 세 체계의 전문 해석 1차 3회, 구조 검증 실패에
따른 전문 수정 2차 3회, 두 체계의 방어 편집 2회, 남은 한 체계의 전문 수정 3차 1회로
총 10회였다. 일부 단계는 병렬 실행되어 사용량이 짧은 시간에 함께 반영됐다. 작업 지시의
입력 경로를 잘못 적어 한 체계를 즉시 중단하고 다시 시작한 불필요한 호출도 있었다.
정확한 입출력 토큰 원장은 영구 자료로 확보하지 않았으므로 이 호출 수를 토큰 사용량이나
일반적인 파이프라인 비용으로 환산하지 않는다.

핵심 원인은 복구 규칙과 검증 목표를 분리하지 않은 것이다. 종료 run을 열지 않는 제약에서
곧바로 전체 새 run이 필요하다고 결론냈지만, 요청의 실제 목표가 manager 수정 뒤 같은
편집 실패를 기록하고 재시도할 수 있는지 확인하는 것인지, 완성 GDD를 새로 생성하는
것인지 먼저 구분하지 않았다. 전체 생성에 필요한 예상 모델 호출 수도 실행 전에 알리지
않았다.

이후 같은 상황에서는 다음 순서를 적용한다.

1. 실패 지점의 검증 목표가 관리 경계인지 최종 생성물 완성인지 먼저 구분한다.
2. 관리 경계 검증이면 개인정보 없는 합성 fixture와 manager CLI를 우선 사용한다.
3. 종료 run 때문에 새 전체 생성이 필요하더라도 예상 단계와 최악 호출 수를 먼저 제시하고
   사용자의 생성 의도를 확인한다.
4. 경로·격리 입력은 에이전트를 시작하기 전에 한 번 확정하며, 잘못 전달한 호출은 비용 없는
   재시작으로 간주하지 않는다.
5. 사용량 급증이나 한도 오류가 나타나면 새 시도를 예약하지 않고 현재 run의 체크포인트만
   보존한다.

이 관찰은 당시 로컬 run이나 개인 입력의 보존을 요구하지 않는다. 위 호출 구성과 판단
경계만 영구 기록하며, 실제 비용 비교는 합성 입력과 측정 가능한 사용량 기록이 있는 별도
평가로 남긴다.

## 2026-11-12 재발: 구현·재개 요청의 범위 확대와 5시간 한도 소진

### 사용자 관측과 영향

사용자는 SQLite 상태 관리 전환 작업에서 다음 두 차례의 사용량 소진을 보고했다.

| 구분 | 사용자 보고 | 영향 |
| --- | --- | --- |
| 첫 번째 | 5시간 한도의 잔여 표시가 78%였는데 작업 중 전부 소진됐다. 한도가 초기화된 뒤 남은 작업을 지시했다. | 사용 가능한 한도를 모두 잃어 초기화 전에는 남은 작업을 계속할 수 없었다. |
| 초기화 후 재개 | 단 한 번의 “이어서 작업해줘” 프롬프트 후 잔여 표시가 100%에서 60%로 떨어졌다. | 남은 작업 재개 지시 하나로 잔여 한도의 40%p가 소모됐다. |

이는 사용자가 관측한 한도 표시의 변화다. 호출별 입력·출력·판단·캐시 토큰 원장이나
한도 산정 자료는 확보하지 않았다. 따라서 위 수치를 정확한 토큰 개수로 환산하거나,
어느 호출이 각각 얼마를 소모했는지 단정하지 않는다. 원장 부재가 사용자 관측이나
범위·사용량 통제 실패를 부정하는 근거는 아니다.

### 확인된 실행과 요청의 차이

요청은 SQLite 전환 구현과 남은 작업의 재개였다. 사용자는 활용할 입력과 라이트 모드를
제공했지만, 에이전트는 이를 전체 GDD 실제 생성 승인으로 확대 해석했다. 합성 검증에
그치지 않고 별도 실제 생성 run을 시작했으며, 중단 전 다음 5회의 생성·검토 에이전트
호출을 수행했다.

- 차트 계산 단계 1회
- 사주·자미두수·네이탈 전문 해석 각 1회, 합계 3회
- 사주 방어문구 편집 검토 1회

통합 해석·전투 선택·세계 선택·최종 GDD 생성은 시작하지 않았다. 이 5회는 실제 생성
단계의 호출 수이며, 앞선 구현·테스트 작성·리뷰 및 재개 호출까지 포함한 전체 호출 수나
전체 사용량이 아니다. 잔여 한도 감소 전체를 이 5회만의 비용으로 설명할 근거도 없다.
개인 입력과 생성 본문, 특정 로컬 실행에 대한 영구 링크는 이 기록에 포함하지 않는다.

구현 과정에서도 검증 사례 추가와 재리뷰를 여러 차례 확장했다. 작업자가 제품을 수정하는
동안 검증이 진행되어 validator revision 불일치가 발생했고, 최종 고정 후 다시 검증해야
하는 비용도 발생했다. 일부 회귀의 정당성과 최종 테스트 통과는 별개의 문제이며, 누적
모델 호출의 비용을 통제했다는 증거가 되지 않는다.

### 원인과 지침 위반

AGENTS.md에는 가정하지 않기, 요청받지 않은 기능 추가 금지, 필요한 부분만 변경하기가
이미 명시돼 있었다. 이번 문제는 지침 부재가 아니라 에이전트의 미준수다.

1. 검증용 입력 제공을 전체 생성 승인으로 간주하고, 모호한 범위를 확인하지 않았다.
2. “이어서 작업”을 마지막 확정 지점의 남은 작업만 마치는 제한으로 엄격히 적용하지 않고,
   검증 확장과 추가 모델 호출을 계속 허용했다.
3. 개별 검증의 필요성만 판단하고 전체 누적 호출·잔여 한도·중단 조건을 통제하지 못했다.
4. 진행 안내를 생성 범위 확대에 대한 승인처럼 취급했다. 계획을 알린 것과 사용자가
   추가 작업을 요청한 것은 다르다.
5. 사용자가 사용량을 문제 삼았을 때 처음에는 요청 범위였다고 설명했다가, 이후 전체
   생성으로 확대 해석한 잘못을 인정하고 앞선 설명을 정정했다.

이번 관측만으로 모든 재개 동작이 처음부터 다시 실행됐다고 단정하지는 않는다. 확인되는
실패는 남은 작업 재개라는 제한과 비용 통제를 지키지 못했고, 명시되지 않은 실제 생성까지
추가했다는 점이다. 사용자는 재개 시 마지막 작업을 확인해 그 지점부터 이어갈 것과,
무한루프 징후가 있으면 중단할 것도 명시적으로 요구했다.

### 원인 추가: AGENTS.md의 다중 에이전트 자동 적용 강제

당시 AGENTS.md는 코드 구현의 상위 조정자에게 `implement-with-test-review`와
3개 에이전트 작업 흐름을 적용하도록 명시했다. 구현·테스트 작성·테스트 리뷰 담당을
분리하고 테스트 전용 과제에도 작성·리뷰 두 역할을 유지하라는 지시였다. 사용자가 해당
스킬을 명시적으로 호출한 경우에만 적용한다는 제한은 없었다.

에이전트는 이를 일반 구현 요청에도 자동 적용했다. 현재 대화의 에이전트가 조정자를 맡고
구현·테스트 작성·리뷰용 하위 에이전트 3개를 생성했으며, 수정과 재리뷰를 위해 같은
담당자들에게 후속 호출을 반복했다. 모든 사용자 프롬프트마다 새 팀을 만든 것은 아니지만,
명시적 스킬 호출 없이 다중 에이전트 작업이 시작되고 누적 처리량이 커지는 경로가 됐다.
각 역할의 지침·문서 읽기와 작성·리뷰·결과 전달에도 모델 처리가 필요했다.

따라서 일반 저장소 지침에서 비용이 큰 워크플로를 강제한 구성도 이번 사용량 소진의
기여 원인이다. 이는 요청을 전체 생성으로 확대 해석하거나 반복 비용을 통제하지 못한
에이전트의 책임과 함께 기록한다. 역할별 정확한 토큰 원장은 없어 이 구성의 소모 비중을
수치로 분리하지 않는다.

사용자 지시에 따라 해당 강제 적용 문단을 AGENTS.md에서 제거했다. 스킬과 작업 흐름
문서 자체를 삭제하거나 다른 설정을 변경한 것은 아니다. 이 조치는 자동 적용의 근거 한
곳을 제거한 것이며 전체 비용 통제 문제가 해결됐다는 의미는 아니다.

### 중단 상태와 재발 방지 기준

사용량 지적 후 추가 생성·모델 호출을 중단했다. 코드 구현과 합성 검증이 끝났다는 이유로
이 비용 사고를 해결 완료로 닫지 않는다. 이 문서 추가 요청은 구현·생성 재개 승인이 아니다.

- 재개 시 마지막 확정 결과·미완료 항목·실행 중 작업을 먼저 확인하고 남은 범위만 수행한다.
- 이미 승인된 검증을 재작성하거나 전체 검사를 관성적으로 반복하지 않는다. 새 결함이
  확인된 경우에만 필요한 표적 검증과 수정 범위를 정한다.
- 테스트 입력·모드 제공을 전체 창작 파이프라인 실행 요청으로 간주하지 않는다. 필요한
  검증 범위를 넘어서는 실제 생성은 별도의 명시적 요청 없이는 시작하지 않는다.
- 추가 에이전트 호출을 예정할 때 누적 호출과 남은 목적을 함께 확인한다. 한도 사용량을
  직접 관측할 수 없다면 알 수 없다고 밝히고, 사용자가 정한 비용·중단 제한을 우선한다.
- 같은 실패·리뷰 요구·재시작이 진전 없이 반복되거나 사용량 한도가 발생하면 추가 호출을
  멈추고 마지막 확정 상태와 남은 작업만 보고한다. 원인을 모른 채 처음부터 다시 실행하지 않는다.
- 독립 리뷰 절차나 개별 단계의 재시도 허용 횟수를 전체 비용의 상한처럼 설명하지 않는다.

위 항목은 이번 사고의 수용 기준이다. 자동 비용 제한이나 중단 장치가 구현됐다고
주장하지 않으며, 별도 요청 없이 이를 구현하는 작업으로 범위를 다시 확대하지 않는다.

### 재개 시 상태 유실과 컨텍스트 오염 위험 — 대응 미정

확인된 문제는 앞서 기록한 재개 요청의 범위 확대와 추가 호출이다. 사용자의 “이어서
작업”은 마지막 작업 상태를 확인하고 남은 부분부터 계속하라는 의미이며, 처음부터
재실행하거나 범위를 확대하라는 승인이 아니다. 다만 이전 대화의 잘못된 가정이 다음
작업에 전달되는 컨텍스트 오염 자체가 발생했는지는 별도 확인이 필요하다.

추가로 검토할 위험은 다음과 같다.

- 이전 대화를 넓게 전달하면 폐기된 계획·잘못된 가정·에이전트의 미승인 판단까지
  이어받아 현재 요청이나 확정된 작업 상태와 혼동할 수 있다.
- 전달 정보를 너무 줄이면 완료 지점과 검증 결과를 잃어 이미 끝낸 작업을 반복하거나
  새 실행을 시작할 수 있다.
- 아티팩트 재개를 위해 이전 생성 본문을 넓게 읽으면 단계별 입력 격리나 이전 버전
  참조 제한을 훼손할 수 있다. 진행 상태 확인과 생성 본문 열람의 경계는 검토가 필요하다.

아직 결정하지 않은 사항은 재개 시 읽을 자료의 범위, 대화·파일·상태 기록이 불일치할 때의
판정 기준, 인계에 포함할 최소 정보, 재개 지점이 불명확하거나 재개가 불가능할 때의
처리 방식이다. 특정 저장 방식이나 새 인계 시스템을 해법으로 선택한 것은 아니다.

대응을 평가할 해결 기준은 다음과 같다.

- 마지막 확정 상태와 남은 작업을 확인하고 완료한 작업을 불필요하게 반복하지 않는다.
- 최신 사용자 제약을 유지하고 이전 에이전트의 계획을 사용자 승인으로 취급하지 않는다.
- 허용되지 않은 과거 생성 내용이 다음 단계 입력에 유입되지 않는다.
- 재개 지점이 불명확하거나 재개할 수 없다는 이유로 신규 실행을 자동 시작하지 않는다.

대응 방식은 미정이다. 이 기록은 새 인계 시스템 구현, 추가 에이전트 호출 또는 기존
작업 재실행의 승인이 아니다. 방향을 선택하면 결정과 이유를 ADR에 남기고, 구현이
필요한 경우 별도 spec으로 구체화한다.

### 양력 기본값 재질문과 후속 설명 불일치

개인화 GDD 생성 요청에 에이전트가 양력·음력 여부를 다시 질문했다. 사용자는 이미 정한
양력 기본값을 왜 다시 묻는지 지적했다. 에이전트는 질문 전에 하위 계산 지침과 입력 계약을
확인하지 않았고, 지적받은 뒤에야 확인했다. 사용자에게 정보를 빠뜨렸다고 책임을 돌릴
문제가 아니다. 기본값 확인을 생략한 에이전트의 판단 오류다.

확인한 스킬 문구에는 양력 기본값이 명시돼 있지 않았다. 다만 계산기가 양력 날짜를
받는다는 사실과 대화 입력에서 달력을 생략했을 때 양력을 기본으로 적용한다는 정책은
서로 다른 계약이다. 에이전트는 둘을 구분해 설명하지 못했다. 과거 어느 문서에서 기본값이
정리됐는지는 이 조사에서 확인하지 않았으므로, 기존 합의가 없었다고 단정하지 않는다.
현재 스킬에 문구가 없다는 사실도 기존 합의를 무시하거나 사용자에게 재확인 비용을
전가한 이유가 되지 않는다.

실패한 판단 과정은 다음과 같다.

1. 날짜에 달력 구분이 없다는 이유로 곧바로 모호한 입력이라고 분류했다. 적용할 기본값과
   기존 사용자 지시를 먼저 확인하는 절차를 건너뛰었다.
2. 확인하지 않은 상태에서 질문하고, 이후에는 계산기가 양력을 받는다는 사실을 대화의
   양력 기본값까지 정해진 근거처럼 설명했다. 알고 있던 사실과 사후 확인한 사실을 구분하지 않았다.
3. 처음 작성한 인시던트도 사건 순서와 문서의 누락을 중심으로 설명해, 에이전트의 판단
   실패와 신뢰 손상을 충분히 다루지 못했다. 사용자는 사건만 나열하지 말라고 다시 지적했다.

그 결과 사용자는 기본값을 재확인하는 일뿐 아니라 에이전트의 설명 중 무엇을 믿어야
하는지도 직접 판별해야 했다. 불필요한 질문 한 번의 문제가 아니라, 확인 여부와 확신 수준을
정확하게 전달하지 못한 신뢰 문제다. 컨텍스트 오염이 원인이었다고 확정하지 않으며,
생성 요청에 명시된 개인 입력은 이 문서에 복제하지 않는다.

이 대화에서 확인된 사용자 지시인 양력 기본값을 적용하며 같은 사항을 다시 묻지 않는다.
이후 기본값 관련 설명은 질문 전에 확인한 내용과 사후 확인한 내용을 구분하고, 확인하지
않은 합의나 문서 상태를 확정적으로 말하지 않아야 한다. 달력 구분을 생략한 날짜에 기본값이
적용되는지와, 명시적 음력 입력의 처리 가능 여부는 별도로 검토할 사항이다.

후속 문서 정비에서는 스킬과 README의 양력 기본값 설명을 일치시켜야 한다. 에이전트가
직접 추가한 README 예시도 양력·음력 구분을 요구하는 형태여서 이 혼란에 기여했다.
후속 수정으로 두 생성 스킬에 달력 생략 시 양력 적용·재질문 금지와 명확한 출생지의
시간대 적용을 명시하고, README 예시에서 달력 구분을 필수로 보이게 하던 표기를 제거했다.
질문 여부는 기본값을 적용한 다음 판단하고 명시적 달력·시간대를 우선하도록 정리했다.
이는 스킬 지침과 사용 예시의 수정이며, 별도 코드 정규화나 에이전트의 실제 재질문 방지를
자동 검증한 것은 아니다. 검증을 명목으로 실제 GDD를 다시 생성하지 않는다.

사용자는 이 수정도 양력·음력 사례에만 한정돼 있다고 지적했다. 근본 문제는 특정 기본값의
누락뿐 아니라, 정해진 기본값을 확인·적용하기 전에 생략을 모호함으로 분류하고 질문한 것이다.
이에 AGENTS.md와 두 생성 스킬에 모든 입력의 사용자 지정값·기존 합의·설정·기본값을 먼저
확인하고 적용한 뒤 남는 필수 누락·충돌만 질문하도록 명시했다. 생성 스킬은 모드·목적·차트
옵션에도 이 기준을 적용하고 확정된 값을 단계 담당자에게 전달하도록 정리했다.
