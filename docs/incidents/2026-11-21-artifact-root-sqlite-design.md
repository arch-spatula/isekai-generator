# 실행 상태 SQLite를 아티팩트 루트에 둔 설계 오류

## 상태

- 상태: SQLite 폐기 결정·문서 갱신 완료, 아티팩트 루트 DB 삭제 완료, 코드 제거 전
- 후속 결정: [실행 상태 SQLite를 각 버전 폴더 루트에 둔다](../ADR/2026-11-21-per-version-sqlite-state.md) → 같은 날 [진행 상태를 버전 폴더의 파일에서 계산](../ADR/2026-11-21-drop-sqlite-file-derived-progress.md)으로 대체
- 원래 결정: [SQLite와 목적별 CLI ADR](../ADR/2026-11-12-sqlite-agent-state-evaluation.md)
- 관련 명세: [SQLite 상태 관리·작업 재개 명세](../spec/sqlite-artifact-state.md)

## 요약

SQLite 전환을 설계·구현한 Codex 에이전트는 실행 상태 DB를 아티팩트 루트 `artifacts/state.sqlite`에
저장소당 하나로 두었다. 생성 결과는 실행마다 자기 버전 폴더(`artifacts/<version>/`, 가상 예: `v0.5.1`)를 루트로 갖는다.
DB를 그 폴더 밖 아티팩트 루트에 둘 이유가 없었다. 그런데도 굳이 루트에 두었고, 그 결과 필요 없는
복잡성만 늘었다.

프로젝트 소유자의 판단은 분명하다. DB의 목적은 한 버전의 작업을 이어서 할 때 그 버전 안에서 참조하는
것이었다. 버전 폴더는 이미 서로 격리되어 있으므로 버전 폴더마다 DB를 두면 실행 사이의 동시성을 걱정할
필요가 없었다. 아티팩트 루트의 공용 DB는 이 의도와 정반대인 크게 잘못된 설계다.

## 기대 동작과 실제 설계

| 항목 | 기대 동작 | 실제 설계 |
| --- | --- | --- |
| DB 위치 | 각 버전 폴더 루트 | 아티팩트 루트 하나 |
| DB가 담는 범위 | 그 버전의 run 하나 | 저장소의 모든 run과 모든 지문 |
| 버전 번호 확정 | 버전 폴더의 배타적 생성 | DB의 series 카운터 + 폴더 이름 확인 + 폴더 배타적 생성 |
| 실행 사이 동시성 | 폴더 격리로 경합 없음 | 한 DB 파일에 모든 run이 쓰므로 경합 처리 필요 |
| 작업 재개 | 그 버전 폴더만 열면 됨 | 루트 DB에서 run을 찾아 버전 폴더와 대조 |

원래 명세는 "run별 DB는 만들지 않는다"고 명시했다. 하지만 버전 폴더별 DB를 대안으로 검토한 기록도,
루트에 두어야 하는 이유도 남기지 않았다. 원래 ADR의 대안 비교는 JSON과 SQLite 중 무엇을 쓸지만 다루고,
DB를 어디에 둘지는 비교하지 않았다.

## 늘어난 불필요한 복잡성

공용 DB 하나 때문에 생긴 설계 요소다. 버전 폴더별 DB였다면 모두 필요 없었다.

- **series 카운터 테이블:** 버전 번호를 DB에서 세고, 폴더 이름과 다시 맞추고, 폴더 배타적 생성까지 함께 쓰는
  삼중 확인.
- **동시 첫 초기화:** 여러 실행이 처음으로 동시에 DB를 만들 때 스키마를 한 번만 초기화하는 규칙과 그 회귀 테스트.
- **실행 간 지문 경합:** 지문 비교 시점의 registry revision을 저장하고, 확정할 때 다른 run이 먼저 등록했는지 다시
  확인하는 `registry-stale` 차단과 그 뒤의 재검토 경로.
- **저장소 식별과 경로 대조:** 잘못된 루트에서 다른 DB를 쓰거나 DB만 복사된 경우를 감지하는 규칙.
- **실행 간 쓰기 경합 시험:** 별도 프로세스 경합, 다른 run의 동시 등록 같은 회귀 시나리오.

## 영향

- **버전 폴더만으로 실행을 이해하거나 이어 갈 수 없다.** 폴더와 상태 기록이 떨어져 있어, 한 버전을 옮기거나
  들여다볼 때 루트 DB가 함께 필요하다.
- **명세 전반이 오염되었다.** 공용 DB 전제가 ADR 2개, 명세 6개, 파이프라인 문서, 스킬 지침까지 퍼졌다.
- **에이전트의 컨텍스트가 오염되었다.** 이후 작업자가 루트 DB를 정상 구조로 받아들였다. 2026-11-21 세션에서도
  Claude 에이전트가 루트 DB를 전제로 "SQLite 실행 관리 밖의 경로" 같은 트레이드오프를 설명했고, 프로젝트
  소유자가 바로잡았다.

## 조치

- 2026-11-21: [버전 폴더별 SQLite ADR](../ADR/2026-11-21-per-version-sqlite-state.md)을 채택하고, 공용 DB를 전제한
  ADR·명세·파이프라인 문서를 새 결정에 맞게 고쳤다.
- 2026-11-21: 프로젝트 소유자 요청으로 아티팩트 루트의 `state.sqlite`와 WAL·SHM 파일을 삭제했다. 삭제 당시 DB에는
  실행 3건(미완료 1건, 성공 2건)과 지문 4행이 있었다. 이관하지 않았다.

- 2026-11-21: 버전 폴더별 DB로 옮기는 결정을 다시 검토한 결과, SQLite만이 해 줄 수 있는 일이 없다고 판단했다. 진행 위치는
  파일과 검증기로 계산할 수 있고, 시도·진단은 `garbage/` 시도 폴더의 파일로, run 간 지문은 게시된 브리프로 대신할 수 있다.
  [파일 기반 진행 상태 ADR](../ADR/2026-11-21-drop-sqlite-file-derived-progress.md)으로 SQLite 상태 저장소 자체를 쓰지 않기로 했다.

## 남은 일

- **코드 제거:** 현재 코드(`scripts/artifacts/artifact-state-store.ts` 등)는 여전히 `artifacts/state.sqlite`를 연다.
  단계표·상태 명령·파일 기반 시도 기록으로 바꾸기 전에 SQLite 파이프라인으로 새 실행을 예약하면 루트 DB가 다시 생긴다.
- **스킬 지침:** `generate-personalized-gdd` 스킬의 `registry-stale` 처리 안내는 현재 코드 동작과 맞춰 두었으므로
  코드 변경과 함께 고친다.
